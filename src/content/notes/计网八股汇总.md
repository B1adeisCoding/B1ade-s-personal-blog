## OSI 七层模型与 TCP/IP 四层模型

**类别**：计算机网络 / 基础 / 网络分层

### 两种模型对比

```
OSI 七层                  TCP/IP 四层             典型协议/设备
─────────────────────────────────────────────────────────────
应用层                 ┐
表示层                 ├─ 应用层               HTTP, HTTPS, DNS, FTP, SMTP, SSH
会话层                 ┘

传输层                 ── 传输层               TCP, UDP

网络层                 ── 网际层               IP, ICMP, ARP, OSPF（路由器）

数据链路层             ┐
物理层                 ├─ 网络接口层           以太网, Wi-Fi（交换机、网卡）
                       ┘
```

### 每层的核心职责

| 层 | 核心问题 | 类比 |
|---|---------|------|
| **应用层** | 数据的语义和格式（"要传什么"） | 写信的内容 |
| **传输层** | 端到端的可靠传输（"怎么保证送到"） | 快递公司（TCP 保证签收，UDP 扔了就走） |
| **网络层** | 路由寻址（"往哪送"） | 导航规划路线 |
| **网络接口层** | 物理链路上的帧传输 | 公路/铁路 |

### 数据封装过程

```
发送端（自上而下封装）：

应用层：  [HTTP 数据]
传输层：  [TCP 头 | HTTP 数据]                      → 段（Segment）
网络层：  [IP 头 | TCP 头 | HTTP 数据]               → 包（Packet）
链路层：  [帧头 | IP 头 | TCP 头 | HTTP 数据 | 帧尾]  → 帧（Frame）

接收端（自下而上解封装）：逐层剥掉头部
```

## TCP 与 UDP 的区别

**类别**：计算机网络 / 传输层 / TCP vs UDP

| 对比项 | **TCP** | **UDP** |
|--------|---------|---------|
| 连接 | **面向连接**（三次握手） | **无连接**（直接发） |
| 可靠性 | **可靠**（确认、重传、排序） | **不可靠**（发了就不管） |
| 传输方式 | **字节流** | **数据报** |
| 有序性 | **保证有序**（序列号） | **不保证有序** |
| 流量控制 | **有**（滑动窗口） | **没有** |
| 拥塞控制 | **有**（慢启动、拥塞避免等） | **没有** |
| 头部开销 | **20 字节** | **8 字节** |
| 传输效率 | 较低（可靠性开销） | **较高** |
| 应用场景 | HTTP, FTP, 邮件, 数据库 | DNS, 视频直播, 游戏, VoIP |

### 一句话总结

> TCP 是打电话——先拨号建立连接，通话过程中确认对方听到了，挂断时要告别。  
> UDP 是发传单——扔出去就完事，不管对方收没收到。

## TCP 三次握手

**类别**：计算机网络 / 传输层 / TCP 连接建立

### 流程

```
客户端（Client）                         服务端（Server）
    │                                       │
    │  状态：CLOSED                          │  状态：LISTEN
    │                                       │
    │──── ① SYN=1, seq=x ────────────────→  │
    │  状态：SYN_SENT                        │
    │                                       │
    │  ←── ② SYN=1, ACK=1, seq=y, ack=x+1  │
    │                                       │  状态：SYN_RCVD
    │                                       │
    │──── ③ ACK=1, seq=x+1, ack=y+1 ────→  │
    │  状态：ESTABLISHED                     │  状态：ESTABLISHED
    │                                       │
    │          双方可以开始传输数据             │
```

### 每一步在干什么

| 步骤 | 发送方 | 内容 | 目的 |
|------|--------|------|------|
| ① | 客户端 → 服务端 | SYN=1, seq=x | 客户端请求建立连接，告知自己的初始序列号 x |
| ② | 服务端 → 客户端 | SYN=1, ACK=1, seq=y, ack=x+1 | 服务端同意连接，告知自己的初始序列号 y，确认收到了 x |
| ③ | 客户端 → 服务端 | ACK=1, ack=y+1 | 客户端确认收到了 y |

### 为什么是三次，不是两次？

```
两次握手的问题——历史连接干扰：

  场景：客户端发了一个 SYN，但网络延迟很久
  客户端以为丢了 → 重新发 SYN → 正常建立连接 → 数据传完 → 关闭

  这时第一个 SYN 到了服务端 → 服务端以为是新连接 → 返回 SYN-ACK
  如果只有两次握手 → 连接直接建立 → 服务端白白分配资源等数据 → 浪费

  三次握手 → 客户端收到这个过期的 SYN-ACK 后发现不对 → 发 RST 拒绝 → 服务端释放

核心原因：
  第三次握手让客户端有机会告诉服务端"这个连接请求是否有效"，
  防止历史重复连接导致服务端资源浪费。
```

### 三次握手还能确认什么

```
① → 服务端确认：客户端的发送能力 ✓，自己的接收能力 ✓
② → 客户端确认：自己的发送能力 ✓，自己的接收能力 ✓，服务端的发送能力 ✓，服务端的接收能力 ✓
③ → 服务端确认：自己的发送能力 ✓，客户端的接收能力 ✓

三次握手后，双方都确认了彼此的收发能力
两次不够（服务端不确定客户端的接收能力）
四次没必要（三次已经够了）
```

## TCP 四次挥手

**类别**：计算机网络 / 传输层 / TCP 连接关闭

### 流程

```
客户端（主动关闭方）                          服务端（被动关闭方）
    │                                          │
    │  状态：ESTABLISHED                        │  状态：ESTABLISHED
    │                                          │
    │──── ① FIN=1, seq=u ──────────────────→   │
    │  状态：FIN_WAIT_1                         │
    │                                          │
    │  ←── ② ACK=1, seq=v, ack=u+1            │
    │  状态：FIN_WAIT_2                         │  状态：CLOSE_WAIT
    │                                          │  （服务端可能还有数据要发）
    │                                          │
    │  ←── ③ FIN=1, ACK=1, seq=w, ack=u+1     │
    │                                          │  状态：LAST_ACK
    │                                          │
    │──── ④ ACK=1, seq=u+1, ack=w+1 ───────→  │
    │  状态：TIME_WAIT                          │  状态：CLOSED
    │  （等待 2MSL）                             │
    │  状态：CLOSED                             │
```

### 为什么是四次，不是三次？

```
TCP 是全双工的 → 两个方向的数据传输是独立的

  客户端说"我发完了"（FIN）→ 服务端说"收到"（ACK）
  但服务端可能还没发完自己的数据
  等服务端也发完了 → 服务端说"我也发完了"（FIN）→ 客户端说"收到"（ACK）

  所以需要四次：两个方向各需要一个 FIN + 一个 ACK

  ② 和 ③ 能合并吗？
  可以，如果服务端收到 FIN 时恰好也没有数据要发了，可以把 ACK 和 FIN 合在一起发
  → 三次挥手（实际中也是存在的，TCP 延迟确认机制可能触发）
```

### TIME_WAIT 状态

```
为什么客户端发完最后一个 ACK 后不直接关，要等 2MSL？

MSL = Maximum Segment Lifetime，报文最大生存时间（通常 30s~60s，2MSL = 1~4 分钟）

原因 1：确保最后一个 ACK 能到达服务端
  如果最后一个 ACK 丢了 → 服务端会重发 FIN → 客户端还在 TIME_WAIT 可以重新 ACK
  如果客户端直接关了 → 服务端重发的 FIN 没人回 → 服务端永远关不掉

原因 2：让旧连接的残留报文在网络中消亡
  等 2MSL 后，该连接的所有报文都已过期销毁
  新连接不会收到上一个连接的残留数据
```

### TIME_WAIT 过多的问题

```
高并发短连接场景（如 HTTP 1.0）：
  每个请求建一次 TCP → 用完关 → 进入 TIME_WAIT → 大量端口被占用
  端口默认 65535 个 → 端口耗尽 → 新连接建不了

解决方案：
  1. 开启 tcp_tw_reuse：允许复用 TIME_WAIT 的端口（需开启 TCP 时间戳）
  2. 开启 tcp_tw_recycle：加速 TIME_WAIT 回收（NAT 下有坑，Linux 4.12 后已移除）
  3. 用长连接（HTTP Keep-Alive）减少连接创建/销毁
  4. 调小 MSL 时间（不推荐，可能有残留报文问题）
```

## TCP 可靠传输机制

**类别**：计算机网络 / 传输层 / TCP 可靠性

### 核心机制一览

| 机制 | 解决的问题 |
|------|-----------|
| **序列号 + 确认号** | 保证数据有序、不丢 |
| **超时重传** | 数据丢了就重发 |
| **滑动窗口** | 流量控制 + 提升效率 |
| **拥塞控制** | 避免网络拥堵 |
| **校验和** | 检测数据损坏 |

### 序列号与确认号

```
发送端：每个字节都有一个序列号（seq）
接收端：返回确认号（ack）= 期望收到的下一个字节的序号

例子：
  发送端发 seq=1, 长度=100 → 数据字节 1~100
  接收端收到 → 返回 ack=101（意思是"1~100 我收到了，下一个给我 101"）
  
  发送端再发 seq=101, 长度=200 → 数据字节 101~300
  接收端收到 → 返回 ack=301

作用：
  - 接收端可以按序列号重新排序（解决乱序）
  - 接收端可以根据序列号去重（解决重复）
  - 发送端根据确认号知道哪些数据已送达（解决丢包）
```

### 超时重传（RTO）

```
发送数据后启动计时器 → 超时没收到 ACK → 重传

RTT（Round-Trip Time）：数据往返时间
RTO（Retransmission Timeout）：重传超时时间，基于 RTT 动态计算

  RTO 太小 → 频繁重传（可能数据没丢只是延迟了）
  RTO 太大 → 等太久才重传（效率低）

  RTO 的经典算法：
    SRTT = (1 - α) × SRTT + α × RTT_sample     （加权移动平均）
    RTO = SRTT + 4 × RTTVAR                      （加一个方差 buffer）
```

### 快速重传

```
不等超时，通过重复 ACK 触发重传：

  发送：seg1, seg2, seg3, seg4, seg5
  接收：收到 seg1 → ACK 2
        seg2 丢了
        收到 seg3 → ACK 2（我还在等 seg2）
        收到 seg4 → ACK 2（我还在等 seg2）
        收到 seg5 → ACK 2（我还在等 seg2）

  发送端收到 3 个重复 ACK(2) → 不等超时，立即重传 seg2

  优点：比超时重传更快发现丢包
```

## TCP 滑动窗口与流量控制

**类别**：计算机网络 / 传输层 / 流量控制

### 为什么需要流量控制

```
发送端发太快 → 接收端来不及处理 → 接收缓冲区满了 → 后续数据被丢弃 → 要重传 → 效率更差

流量控制：让发送端的发送速率匹配接收端的处理能力
```

### 滑动窗口机制

```
发送端维护一个"发送窗口"，接收端通过 ACK 中的 Window 字段告知自己的接收能力

┌────────────┬─────────────────────┬───────────────────┐
│ 已发送已确认 │  已发送未确认（窗口内） │  可发但还没发（窗口内） │ 不可发（窗口外）
└────────────┴─────────────────────┴───────────────────┘
              ←──── 发送窗口大小（由接收端 Window 决定）────→

接收端：
  ACK 报文中带 Window = 接收缓冲区剩余大小
  如果 Window = 0 → 发送端停止发送（等待窗口更新）

窗口滑动：
  每收到一个 ACK → 窗口左边界右移 → 右边界也右移（如果接收端 Window 没变小）
  → 新的数据变为"可发送"
```

### 零窗口与探测

```
接收端 Window = 0 → 发送端停止发送
但如果接收端恢复了，窗口更新的 ACK 丢了怎么办？
→ 双方死锁（发送端以为窗口还是 0，接收端以为发送端该发了）

解决：零窗口探测（ZWP, Zero Window Probe）
  发送端定期发送一个 1 字节的探测报文
  → 接收端返回当前 Window 大小
  → 如果 Window > 0 → 恢复发送
```

## TCP 拥塞控制

**类别**：计算机网络 / 传输层 / 拥塞控制

### 流量控制 vs 拥塞控制

```
流量控制：发送端 vs 接收端（点对点，怕接收端来不及）
拥塞控制：发送端 vs 网络（全局，怕网络拥堵）

实际发送窗口 = min(接收窗口 rwnd, 拥塞窗口 cwnd)
```

### 四大算法

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  cwnd                                                        │
│   ↑                                                          │
│   │              ssthresh                                    │
│   │   慢启动     ┌──────────── 拥塞避免（线性增长）            │
│   │  （指数增长） │                                           │
│   │          ╱ │          ╱                                  │
│   │        ╱   │        ╱                                    │
│   │      ╱     │      ╱   ← 丢包！                           │
│   │    ╱       │    ╱                                        │
│   │  ╱         │  ╱       ssthresh = cwnd/2                  │
│   │╱           │╱         cwnd = 1（Tahoe）或 cwnd/2（Reno）  │
│   └────────────┴──────────────────────→ 时间                 │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### ① 慢启动（Slow Start）

```
初始 cwnd = 1 MSS
每收到一个 ACK → cwnd 翻倍（指数增长）

  第 1 轮：cwnd = 1 → 发 1 个
  第 2 轮：cwnd = 2 → 发 2 个
  第 3 轮：cwnd = 4 → 发 4 个
  第 4 轮：cwnd = 8 → 发 8 个
  ...指数级增长

当 cwnd >= ssthresh（慢启动阈值）→ 切换到拥塞避免
```

#### ② 拥塞避免（Congestion Avoidance）

```
cwnd >= ssthresh 后：
  每个 RTT，cwnd 只加 1 MSS（线性增长）

  目的：接近网络容量时小心翼翼地试探，别一下子打满
```

#### ③ 快速重传（Fast Retransmit）

```
收到 3 个重复 ACK → 认为丢包了 → 立即重传（不等超时）
```

#### ④ 快速恢复（Fast Recovery）

```
收到 3 个重复 ACK 后（说明网络还没彻底拥堵，只是丢了个别包）：

Reno 算法：
  ssthresh = cwnd / 2
  cwnd = ssthresh（减半，不是归 1）
  进入拥塞避免阶段（线性增长）

对比 Tahoe 算法（更早期）：
  ssthresh = cwnd / 2
  cwnd = 1（直接回到慢启动）
  → 太激进了，Reno 更合理
```

## HTTP 与 HTTPS

**类别**：计算机网络 / 应用层 / HTTP

### HTTP 基础

```
HTTP = HyperText Transfer Protocol（超文本传输协议）

特点：
  - 无状态：每个请求独立，服务端不记住上一个请求
  - 基于 TCP：HTTP/1.x 和 HTTP/2 基于 TCP，HTTP/3 基于 UDP（QUIC）
  - 请求-响应模型：客户端发请求 → 服务端返响应
```

### HTTP 状态码

| 分类 | 含义 | 常见 |
|------|------|------|
| **1xx** | 信息性 | 100 Continue |
| **2xx** | 成功 | **200** OK, **201** Created, **204** No Content |
| **3xx** | 重定向 | **301** 永久重定向, **302** 临时重定向, **304** Not Modified（缓存命中） |
| **4xx** | 客户端错误 | **400** Bad Request, **401** 未认证, **403** Forbidden, **404** Not Found |
| **5xx** | 服务端错误 | **500** Internal Server Error, **502** Bad Gateway, **503** Service Unavailable |

### HTTP 请求方法

| 方法 | 含义 | 幂等 | 安全 |
|------|------|------|------|
| **GET** | 获取资源 | ✓ | ✓ |
| **POST** | 创建资源 / 提交数据 | ✗ | ✗ |
| **PUT** | 全量更新资源 | ✓ | ✗ |
| **PATCH** | 部分更新资源 | ✗ | ✗ |
| **DELETE** | 删除资源 | ✓ | ✗ |
| **HEAD** | 同 GET，但不返回 body | ✓ | ✓ |
| **OPTIONS** | 查询支持的方法（CORS 预检） | ✓ | ✓ |

### GET vs POST

| 对比项 | GET | POST |
|--------|-----|------|
| 参数位置 | URL 查询字符串（?key=val） | 请求体（Body） |
| 长度限制 | 受 URL 长度限制（浏览器通常 2KB~8KB） | 理论无限制 |
| 可见性 | 参数暴露在 URL | 参数在 Body 里 |
| 缓存 | 可被缓存 | 默认不缓存 |
| 幂等性 | 幂等（多次请求结果一样） | 非幂等 |
| 语义 | 获取数据 | 提交/创建数据 |

### HTTP 版本演进（速览）

```
HTTP/1.0 → 短连接
HTTP/1.1 → 长连接 + 管线化（仍有队头阻塞）
HTTP/2   → 多路复用 + 头部压缩 + 二进制帧（TCP 层队头阻塞仍在）
HTTP/3   → 基于 QUIC/UDP，彻底解决队头阻塞 + 0-RTT + 连接迁移
```

## HTTP/1.0、1.1、2.0、3.0 详细区别

**类别**：计算机网络 / 应用层 / HTTP 版本对比

### 总览对比表

| 对比项 | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|--------|----------|----------|--------|--------|
| 年份 | 1996 | 1997 | 2015 | 2022 |
| 传输层 | TCP | TCP | TCP | **QUIC (UDP)** |
| 连接模型 | 短连接 | **长连接** | 长连接 + 多路复用 | 长连接 + 多路复用 |
| 协议格式 | 文本 | 文本 | **二进制帧** | 二进制帧 |
| 头部压缩 | 无 | 无 | **HPACK** | **QPACK** |
| 队头阻塞 | 有（连接级） | 有（请求级） | **HTTP 层解决**，TCP 层仍在 | **彻底解决** |
| 服务端推送 | 无 | 无 | **支持** | 支持 |
| 建连延迟 | 1 RTT (TCP) | 1 RTT (TCP) | 1 RTT (TCP) + TLS | **0~1 RTT** |
| 连接迁移 | 不支持 | 不支持 | 不支持 | **支持** |

### 一、HTTP/1.0 — 短连接时代

```
核心特征：一个请求一个连接

  客户端                          服务端
    │── TCP 三次握手 ──────────→  │     ┐
    │── GET /index.html ───────→  │     │ 第 1 个请求
    │  ←── 200 OK + HTML ───────  │     │
    │── TCP 四次挥手 ──────────→  │     ┘
    │                              │
    │── TCP 三次握手 ──────────→  │     ┐
    │── GET /style.css ────────→  │     │ 第 2 个请求
    │  ←── 200 OK + CSS ────────  │     │
    │── TCP 四次挥手 ──────────→  │     ┘
    │                              │
    │── TCP 三次握手 ──────────→  │     ┐
    │── GET /app.js ───────────→  │     │ 第 3 个请求
    │  ←── 200 OK + JS ─────────  │     │
    │── TCP 四次挥手 ──────────→  │     ┘

  每个请求都要：建连 → 传数据 → 断连
  一个网页加载几十个资源 = 几十次 TCP 握手挥手
```

**问题**：
- 每次请求都要重新三次握手 + 四次挥手 → **延迟高**
- 频繁创建/销毁连接 → **服务端资源浪费**
- 无 Host 头 → 一个 IP 只能对应一个域名（虚拟主机搞不了）

### 二、HTTP/1.1 — 长连接与管线化

#### 改进 1：持久连接（Keep-Alive）

```
默认开启 Connection: keep-alive → 一个 TCP 连接复用多个请求

  客户端                          服务端
    │── TCP 三次握手 ──────────→  │     ┐
    │                              │     │
    │── GET /index.html ───────→  │     │
    │  ←── 200 OK + HTML ───────  │     │
    │                              │     │ 同一个 TCP 连接
    │── GET /style.css ────────→  │     │
    │  ←── 200 OK + CSS ────────  │     │
    │                              │     │
    │── GET /app.js ───────────→  │     │
    │  ←── 200 OK + JS ─────────  │     │
    │                              │     │
    │── TCP 四次挥手 ──────────→  │     ┘

  只需一次握手，多个请求复用同一连接
```

#### 改进 2：管线化（Pipelining）

```
不用等上一个响应回来就发下一个请求：

  没有管线化（串行）：
    请求 A → 等响应 A → 请求 B → 等响应 B → 请求 C → 等响应 C

  有管线化（并行发送，但响应仍串行）：
    请求 A →
    请求 B →（不等 A 的响应）
    请求 C →（不等 B 的响应）
    ← 响应 A
    ← 响应 B（必须等 A 的响应发完才能发 B 的）
    ← 响应 C
```

#### 仍未解决的问题：HTTP 队头阻塞（HOL Blocking）

```
虽然请求可以并行发，但响应必须按请求顺序返回：

  请求顺序：A → B → C
  响应必须：A → B → C（即使 B 和 C 先处理完也要等 A）

  如果 A 的处理很慢（比如大文件、慢查询）：
    A 卡住 → B 的响应等 A → C 的响应等 B → 全堵了

  这就是 HTTP/1.1 的队头阻塞

浏览器的临时解法：
  对同一个域名开 6~8 个并行 TCP 连接
  → 并行度提升但连接数暴增 → 服务端压力大
  → 域名分片（把资源放到多个子域名）更是无奈之举
```

#### 其他改进

```
- Host 头：同一 IP 可以托管多个域名（虚拟主机）
- 断点续传：Range 头支持请求资源的部分内容
- 缓存控制：Cache-Control, ETag, If-None-Match 等精细化缓存策略
- 分块传输（Chunked Transfer）：不需要预先知道 Content-Length，边生成边发送
```

### 三、HTTP/2 — 多路复用

#### 核心改进 1：二进制帧（Binary Framing）

```
HTTP/1.x 是文本协议：
  GET /index.html HTTP/1.1\r\n
  Host: example.com\r\n
  \r\n

HTTP/2 是二进制协议，所有数据被拆分成帧（Frame）：

  帧格式：
  ┌────────────┬────────────┬──────────────────┐
  │ Length (3B) │ Type (1B)  │ Stream ID (4B)   │ ...
  └────────────┴────────────┴──────────────────┘

  帧类型：
    HEADERS 帧：携带请求/响应头
    DATA 帧：携带请求/响应体
    SETTINGS 帧：连接配置
    PUSH_PROMISE 帧：服务端推送
    ...

好处：
  - 解析效率更高（文本需要逐字符扫描，二进制直接按字段读取）
  - 更紧凑，传输更高效
```

#### 核心改进 2：多路复用（Multiplexing）— 最重要的改进

```
HTTP/1.1 的问题：
  一个 TCP 连接内，请求/响应必须排队（队头阻塞）
  → 想并行就得开多个连接

HTTP/2 的方案：
  一个 TCP 连接上可以并行传输多个请求和响应
  每个请求/响应对分配一个 Stream ID → 用帧的 Stream ID 区分属于哪个请求

  ┌─────────── 一个 TCP 连接 ──────────────┐
  │                                        │
  │  Stream 1: [HEADERS帧] [DATA帧] ...    │  → 请求 A
  │  Stream 3: [HEADERS帧] [DATA帧] ...    │  → 请求 B
  │  Stream 5: [HEADERS帧] [DATA帧] ...    │  → 请求 C
  │                                        │
  │  实际传输是交错的：                       │
  │  [S1-HEADERS] [S3-HEADERS] [S1-DATA]   │
  │  [S5-HEADERS] [S3-DATA] [S5-DATA] ...  │
  │                                        │
  └────────────────────────────────────────┘

  请求 A 慢了不影响 B 和 C → HTTP 层队头阻塞解决了

  对比：
    HTTP/1.1：6~8 个 TCP 连接，每个连接串行处理
    HTTP/2：1 个 TCP 连接，所有请求并行处理
    → 连接数大幅减少，服务端压力下降
```

#### 核心改进 3：头部压缩（HPACK）

```
HTTP/1.x 的问题：
  每个请求都带一大堆重复头部（User-Agent, Accept, Cookie...）
  一个请求头可能几百字节 ~ 几 KB
  100 个请求 = 重复发了 100 次几乎一样的头部

HTTP/2 HPACK 压缩：
  ① 静态表：61 个常见头部字段（:method GET, :status 200 等）直接用索引号
  ② 动态表：连接期间出现过的头部缓存起来，后续用索引引用
  ③ 霍夫曼编码：字符串压缩

  效果：
    第一个请求：发完整头部 → 同时加入动态表
    后续请求：大部分头部只发索引号（1~2 字节）
    → 头部大小压缩 80%~90%
```

#### 核心改进 4：服务端推送（Server Push）

```
HTTP/1.x：
  客户端请求 HTML → 解析后发现需要 CSS → 再请求 CSS → 解析后发现需要 JS → 再请求 JS
  串行发现依赖 → 延迟高

HTTP/2 Server Push：
  客户端请求 HTML → 服务端知道你一定需要 CSS 和 JS
  → 在返回 HTML 的同时主动推送 CSS 和 JS
  → 客户端不用再请求

  实际应用有限：推送策略难把控，可能推了客户端缓存里已有的资源
  → Chrome 2022 年已移除 Server Push 支持
```

#### HTTP/2 仍未解决的问题：TCP 层队头阻塞

```
HTTP/2 在 HTTP 层通过多路复用解决了队头阻塞
但底层仍然是 TCP → TCP 自己的队头阻塞还在：

  TCP 把所有 Stream 的帧都混在一个字节流里传输
  如果某个 TCP 包丢了 → TCP 要重传 → 重传期间整个连接阻塞
  → 所有 Stream 都被卡住（即使丢的包只属于 Stream 1）

  TCP 看到的：[S1数据][S3数据][S1数据][S5数据]...
                             ↑ 这个包丢了
  → TCP 重传这个包之前，后面的所有数据都不能交给上层
  → Stream 3 和 Stream 5 无辜躺枪

  在弱网环境（丢包率高）下，HTTP/2 可能反而比 HTTP/1.1（多连接）更慢
```

### 四、HTTP/3 — 基于 QUIC 彻底解题

#### 为什么换掉 TCP

```
HTTP/2 的 TCP 队头阻塞无法在 TCP 层面解决
→ TCP 协议已经固化在操作系统内核和中间设备中，改不动
→ 唯一出路：换一个传输层协议

HTTP/3 选择了 QUIC（Quick UDP Internet Connections）：
  基于 UDP 实现，但在应用层自己做了可靠传输
  → 绕开了 TCP 的限制
```

#### 核心改进 1：彻底解决队头阻塞

```
QUIC 中每个 Stream 是独立的：

  TCP 的问题：
    所有 Stream 共享一个 TCP 字节流 → 一个包丢了全员等待

  QUIC 的方案：
    每个 Stream 有自己独立的流控和重传
    Stream 1 丢包 → 只阻塞 Stream 1 的重传
    Stream 3 和 Stream 5 不受影响 → 继续交付数据

  ┌────────── QUIC 连接 ──────────┐
  │  Stream 1: [丢包→重传]  阻塞   │
  │  Stream 3: [正常接收]  不受影响  │
  │  Stream 5: [正常接收]  不受影响  │
  └──────────────────────────────┘
```

#### 核心改进 2：更快的建连（0-RTT / 1-RTT）

```
TCP + TLS 1.2 建连：
  TCP 三次握手：1 RTT
  TLS 握手：2 RTT
  总共：3 RTT 才能开始传数据

TCP + TLS 1.3 建连：
  TCP 三次握手：1 RTT
  TLS 1.3 握手：1 RTT
  总共：2 RTT

QUIC 首次建连：
  QUIC 把传输层握手和加密握手合并
  首次建连：1 RTT（QUIC 握手 + TLS 1.3 同时完成）

QUIC 恢复连接（0-RTT）：
  之前连过的服务端 → 客户端缓存了加密参数
  → 第一个包就可以携带加密的应用数据
  → 0 RTT 就开始传数据

  对比：
    TCP + TLS 1.2：3 RTT
    TCP + TLS 1.3：2 RTT
    QUIC 首次：1 RTT
    QUIC 恢复：0 RTT  ← 移动端体验大幅提升
```

#### 核心改进 3：连接迁移

```
TCP 连接由四元组标识：(源IP, 源端口, 目的IP, 目的端口)
  手机从 WiFi 切到 4G → 源 IP 变了 → TCP 连接断了 → 要重新握手

QUIC 连接由 Connection ID 标识：
  手机从 WiFi 切到 4G → IP 变了但 Connection ID 没变
  → QUIC 连接继续使用，不需要重新握手
  → 用户无感知切换

  场景：坐地铁刷视频，WiFi 和 4G 来回切
    TCP：每次切换断连 → 重连 → 视频卡顿
    QUIC：无缝切换 → 视频不中断
```

#### 核心改进 4：头部压缩 QPACK

```
HTTP/2 的 HPACK 有问题：
  HPACK 动态表在一个连接的所有 Stream 间共享
  → 更新动态表的帧丢了 → 后续所有 Stream 解头部都卡住
  → 又引入了队头阻塞

QUIC 的 QPACK：
  用两个单向 Stream 传递动态表更新（encoder/decoder stream）
  → 数据 Stream 可以选择只用静态表 + 已确认的动态表条目
  → 避免了头部解码的队头阻塞
```

### 五、队头阻塞的演进（核心线索）

```
这是 HTTP 版本演进的核心驱动力：

HTTP/1.0：
  连接级队头阻塞 → 一个连接一次只能处理一个请求
  解法 → HTTP/1.1 持久连接

HTTP/1.1：
  请求级队头阻塞 → 响应必须按顺序返回，前面的慢了后面全等
  解法 → HTTP/2 多路复用

HTTP/2：
  TCP 层队头阻塞 → 一个 TCP 包丢了，所有 Stream 都被卡住
  解法 → HTTP/3 用 QUIC 替代 TCP

HTTP/3：
  Stream 级独立 → 彻底解决队头阻塞 ✓

每一代 HTTP 的核心进化，都是在解决上一代的队头阻塞问题
```

### 六、面试话术

> **HTTP/1.0 vs 1.1**："1.0 是短连接，每个请求独占一个 TCP 连接；1.1 默认长连接复用 TCP，支持管线化，但响应必须按序返回，存在 HTTP 层队头阻塞。1.1 还加了 Host 头支持虚拟主机、Range 断点续传、更完善的缓存机制。"
>
> **HTTP/1.1 vs 2.0**："最大的改进是多路复用——一个 TCP 连接上用 Stream ID 区分多个并行的请求/响应，彻底解决了 HTTP 层队头阻塞。另外从文本协议变成二进制帧格式，HPACK 头部压缩减少了 80%~90% 的冗余头部，还支持服务端推送。但底层仍然是 TCP，TCP 丢包会阻塞整个连接的所有 Stream。"
>
> **HTTP/2 vs 3.0**："HTTP/3 用 QUIC 协议替换 TCP，QUIC 基于 UDP 但自己实现了可靠传输。核心优势：一是每个 Stream 独立重传，彻底解决队头阻塞；二是建连更快，首次 1 RTT，恢复连接 0 RTT；三是连接迁移，用 Connection ID 标识连接而非四元组，网络切换不断连。"
>
> **一句话串起来**："HTTP 每代升级的核心线索就是解决队头阻塞：1.0 连接级阻塞 → 1.1 长连接但请求级阻塞 → 2.0 多路复用解决 HTTP 层但 TCP 层仍阻塞 → 3.0 用 QUIC 替换 TCP 彻底解决。"

### HTTPS = HTTP + TLS

```
HTTP 的问题：
  明文传输 → 数据可被窃听
  无身份验证 → 可能连到假服务器（中间人）
  无完整性校验 → 数据可被篡改

HTTPS 通过 TLS/SSL 解决：
  加密：对称加密保证数据不被窃听
  认证：数字证书 + CA 保证服务端身份
  完整性：MAC 保证数据不被篡改
```

## HTTPS / TLS 握手流程

**类别**：计算机网络 / 应用层 / HTTPS

### TLS 1.2 握手（RSA 密钥交换）

```
客户端                                          服务端
  │                                               │
  │── ① Client Hello ──────────────────────────→  │
  │   （支持的 TLS 版本、加密套件列表、随机数 C）     │
  │                                               │
  │  ←── ② Server Hello ─────────────────────── │
  │   （选定的加密套件、随机数 S、服务端证书）         │
  │                                               │
  │  ③ 客户端验证证书                               │
  │   → 用 CA 公钥验签 → 确认服务端身份              │
  │   → 生成预主密钥（Pre-Master Secret）            │
  │   → 用服务端公钥加密 PMS                         │
  │                                               │
  │── ④ 发送加密后的 PMS ─────────────────────→   │
  │                                               │
  │  双方用 C + S + PMS 计算出对称密钥（Session Key） │
  │                                               │
  │── ⑤ Change Cipher Spec + Finished ────────→  │
  │  ←── ⑥ Change Cipher Spec + Finished ──────  │
  │                                               │
  │  ═══ 后续用对称密钥加密通信 ═══                  │
```

### 为什么不全程用非对称加密

```
非对称加密（RSA/ECDHE）：安全但慢（比对称加密慢 100~1000 倍）
对称加密（AES）：快但密钥分发困难

解决：用非对称加密交换对称密钥 → 后续用对称加密通信
→ 兼顾安全性和性能
```

### 证书链验证

```
服务端证书不是 CA 根证书直接签的，通常是一条链：

  根 CA 证书（内置在浏览器/OS 中，绝对信任）
    └── 签发了 → 中间 CA 证书
                    └── 签发了 → 服务端证书（example.com）

  验证过程：
    ① 取出服务端证书 → 看签发者是谁 → 找到中间 CA 证书
    ② 用中间 CA 的公钥验证服务端证书的签名 ✓
    ③ 取出中间 CA 证书 → 看签发者是谁 → 找到根 CA 证书
    ④ 用根 CA 的公钥验证中间 CA 证书的签名 ✓
    ⑤ 根 CA 是预置信任的 → 整条链验证通过
```

## DNS 域名解析

**类别**：计算机网络 / 应用层 / DNS

### DNS 是什么

```
DNS（Domain Name System）：域名 → IP 地址的翻译系统
  人记域名：www.baidu.com
  机器用 IP：220.181.38.148
  DNS 负责把域名翻译成 IP
```

### 解析流程

```
用户输入 www.baidu.com → 浏览器/OS 开始解析：

  ① 浏览器 DNS 缓存 → 有就直接用
  ② OS DNS 缓存 → 有就直接用
  ③ hosts 文件 → 有就直接用
  ④ 本地 DNS 服务器（递归查询） → 有缓存就返回
  ⑤ 本地 DNS → 根域名服务器（.） → 返回 .com 的 NS 地址
  ⑥ 本地 DNS → .com 顶级域服务器 → 返回 baidu.com 的 NS 地址
  ⑦ 本地 DNS → baidu.com 权威服务器 → 返回 www.baidu.com 的 IP
  ⑧ 本地 DNS 缓存结果 → 返回给客户端

  浏览器缓存 → OS 缓存 → hosts → 本地DNS → 根 → 顶级 → 权威
```

### 递归查询 vs 迭代查询

```
递归查询：客户端 → 本地 DNS
  客户端问一次，本地 DNS 替它跑完全流程，最终返回结果

迭代查询：本地 DNS → 根/顶级/权威
  本地 DNS 每次只得到一个"指引"，自己一步步去问
```

## 从输入 URL 到页面显示发生了什么

**类别**：计算机网络 / 综合 / 经典面试题

```
① DNS 解析
   浏览器缓存 → OS 缓存 → hosts → 本地 DNS → 根 → 顶级 → 权威
   得到目标 IP

② TCP 三次握手
   客户端与服务器建立 TCP 连接

③ TLS 握手（如果是 HTTPS）
   协商加密算法、交换密钥、验证证书

④ 发送 HTTP 请求
   构造请求报文（方法、URL、Header、Body）→ 发给服务端

⑤ 服务端处理请求
   Web 服务器（Nginx）→ 应用服务器（Tomcat/Go）→ 读 DB/缓存 → 构造响应

⑥ 返回 HTTP 响应
   状态码 + 响应头 + 响应体（HTML）

⑦ 浏览器解析渲染
   解析 HTML → 构建 DOM 树
   解析 CSS → 构建 CSSOM 树
   DOM + CSSOM → 渲染树（Render Tree）
   布局（Layout）→ 绘制（Paint）→ 合成（Composite）→ 显示

⑧ TCP 四次挥手（连接关闭时）
```

## Cookie、Session、Token

**类别**：计算机网络 / 应用层 / 会话管理

### 为什么需要会话管理

```
HTTP 是无状态的 → 服务端不知道"这次请求和上次请求是不是同一个人"
→ 需要机制来维持用户状态（如登录状态）
```

### Cookie

```
原理：
  服务端在响应头中设置 Set-Cookie → 浏览器存储
  后续每次请求自动携带 Cookie → 服务端识别用户

  ① 客户端登录 → 服务端验证 → 响应头：Set-Cookie: session_id=abc123
  ② 客户端后续请求 → 请求头自动带：Cookie: session_id=abc123

特点：
  - 存在客户端（浏览器）
  - 大小限制：4KB
  - 自动携带 → 有 CSRF 风险
  - 可设置 HttpOnly（JS 不能读）、Secure（仅 HTTPS）、SameSite（防 CSRF）
```

### Session

```
原理：
  服务端创建 Session 对象，存储用户状态
  生成一个 Session ID → 通过 Cookie 传给客户端
  客户端每次请求带上 Session ID → 服务端查找对应 Session

  服务端维护：{ "abc123": { userId: 1, role: "admin", loginTime: ... } }

特点：
  - 状态存在服务端（内存/Redis）
  - Session ID 通过 Cookie 传递
  - 服务端有存储开销
  - 分布式环境下有问题 → 需要 Session 共享（Redis 集中存储）
```

### Token（JWT）

```
原理：
  登录成功 → 服务端生成 Token（包含用户信息 + 签名）→ 返回给客户端
  客户端存储（localStorage/Cookie）→ 每次请求放在 Authorization 头
  服务端收到 Token → 验签 → 解析出用户信息 → 不需要查数据库

JWT 结构：Header.Payload.Signature
  Header：算法和类型（{"alg":"HS256","typ":"JWT"}）
  Payload：用户信息（{"userId":1,"role":"admin","exp":...}）
  Signature：HMAC-SHA256(Header + Payload, 服务端密钥)

特点：
  - 无状态：服务端不存储，只验签 → 天然适合分布式
  - Token 自包含用户信息 → 减少查库
  - 不可撤销：一旦签发，在过期前无法主动失效（除非用黑名单）
  - 体积较大（Base64 编码后几百字节）
```

### 三者对比

| 对比项 | Cookie | Session | Token (JWT) |
|--------|--------|---------|-------------|
| 存储位置 | 客户端 | **服务端** | 客户端 |
| 传输方式 | 自动（Cookie 头） | Cookie 传 Session ID | 手动（Authorization 头） |
| 跨域 | 不支持（SameSite 限制） | 不支持 | **支持** |
| 服务端开销 | 无 | **有**（存储 Session） | 无（只验签） |
| 分布式 | — | 需要共享存储 | **天然支持** |
| 安全风险 | CSRF | CSRF | **XSS**（存 localStorage 时） |

## 跨域与 CORS

**类别**：计算机网络 / 应用层 / 安全

### 什么是跨域

```
浏览器同源策略：协议 + 域名 + 端口 三者完全相同才是同源

  http://a.com:80  vs  http://a.com:80     → 同源 ✓
  http://a.com     vs  https://a.com       → 跨域 ✗（协议不同）
  http://a.com     vs  http://b.com        → 跨域 ✗（域名不同）
  http://a.com:80  vs  http://a.com:8080   → 跨域 ✗（端口不同）

  跨域时：浏览器会阻止前端 JS 读取响应内容（请求其实发出去了，服务端也处理了）
```

### CORS 解决跨域

```
CORS（Cross-Origin Resource Sharing）：服务端声明"允许谁跨域访问我"

简单请求（GET/POST/HEAD，且 Header 简单）：
  浏览器直接发请求 → 带上 Origin 头
  服务端返回 Access-Control-Allow-Origin: https://a.com → 浏览器放行

预检请求（PUT/DELETE，或自定义 Header）：
  ① 浏览器先发 OPTIONS 预检请求 → 问服务端"这个跨域请求你接受吗？"
  ② 服务端返回允许的方法、Header、Origin
  ③ 浏览器确认后 → 再发实际请求

关键响应头：
  Access-Control-Allow-Origin: https://a.com（或 *）
  Access-Control-Allow-Methods: GET, POST, PUT
  Access-Control-Allow-Headers: Content-Type, Authorization
  Access-Control-Allow-Credentials: true（允许携带 Cookie）
```

## TCP 粘包与拆包

**类别**：计算机网络 / 传输层 / 粘包

### 什么是粘包 / 拆包

```
TCP 是字节流协议 → 没有消息边界 → 接收端不知道一条消息从哪开始、到哪结束

粘包：两条消息粘在一起
  发送：[消息A][消息B]
  接收：[消息A消息B]  → 分不清 A 和 B 的边界

拆包：一条消息被拆成多次接收
  发送：[消息A]
  接收：[消息A前半段] ... [消息A后半段]

注意：UDP 是数据报协议，有明确的消息边界，不存在粘包问题
```

### 解决方案

```
方案 1：固定长度
  每条消息固定 N 字节，不够补空
  简单但浪费空间

方案 2：分隔符
  每条消息以特定字符结尾（如 \r\n）
  接收端按分隔符切割
  要处理消息体内包含分隔符的问题

方案 3：长度前缀（最常用）
  消息格式：[4字节长度][消息内容]
  接收端先读 4 字节 → 知道消息长度 → 再读对应长度的内容
  HTTP 的 Content-Length 就是这个思路

方案 4：更高层协议处理
  HTTP/2 用帧（Frame），每个帧有 Length 字段
  Protobuf、Thrift 等序列化协议自带长度信息
```

## WebSocket

**类别**：计算机网络 / 应用层 / 双向通信

### HTTP 的局限

```
HTTP 是请求-响应模型 → 服务端不能主动推送
需要服务端推送时：
  - 轮询（Polling）：客户端定时发请求 → 浪费资源
  - 长轮询（Long Polling）：请求挂起直到有数据 → 占连接
  - WebSocket：真正的全双工通信
```

### WebSocket 特点

```
  - 全双工：客户端和服务端都可以主动发消息
  - 基于 TCP：一次握手后保持长连接
  - 低开销：建连后数据帧很小（2~10 字节头部 vs HTTP 几百字节头部）
  - 兼容 HTTP：通过 HTTP Upgrade 升级为 WebSocket

握手过程：
  客户端：GET /chat HTTP/1.1
          Upgrade: websocket
          Connection: Upgrade
          Sec-WebSocket-Key: xxx

  服务端：HTTP/1.1 101 Switching Protocols
          Upgrade: websocket
          Connection: Upgrade
          Sec-WebSocket-Accept: yyy

  → 之后双方直接收发 WebSocket 帧，不再用 HTTP 格式

  适用场景：实时聊天、在线游戏、股票行情、协同编辑
```

## HTTP 长连接方式全景对比

**类别**：计算机网络 / 应用层 / 长连接与服务端推送

### 为什么需要"长连接"

```
HTTP 原始模型是请求-响应：
  客户端主动问 → 服务端被动答
  服务端没法主动推消息给客户端

但很多场景需要：
  - 服务端主动推送（消息通知、实时数据更新）
  - 频繁的数据交互（聊天、协同编辑）
  - 减少重复建连的开销（高频 API 调用）

各种"长连接"方案本质上就是在解决这些问题
```

### 一、HTTP Keep-Alive（持久连接）

```
这不是"服务端推送"方案，而是 TCP 连接复用优化。

HTTP/1.0：默认短连接，每个请求独占一个 TCP
  请求 A → 建连 → 传数据 → 断连
  请求 B → 建连 → 传数据 → 断连（重复握手挥手）

HTTP/1.1：默认 Keep-Alive，一个 TCP 连接复用多个请求
  请求 A → 建连 → 传数据 → 连接保持
  请求 B → 复用连接 → 传数据 → 连接保持
  ...
  空闲超时后才断连

  请求头：Connection: keep-alive（1.1 默认开启）
  关闭：  Connection: close

核心价值：
  - 省去重复的 TCP 三次握手 + 四次挥手
  - 减少 TIME_WAIT 状态的端口占用
  - TLS 握手也只做一次

局限：
  - 仍然是请求-响应模型 → 服务端不能主动推送
  - 队头阻塞（1.1 管线化下响应必须按序返回）
  - 空闲连接占用服务端资源（需要合理设 timeout）
```

### 二、短轮询（Short Polling）

```
最简单粗暴的"伪实时"方案：客户端定时发请求

  客户端                              服务端
    │── GET /messages ──────────→  │
    │  ←── 200 OK (无新数据) ──────  │
    │   等 3 秒                      │
    │── GET /messages ──────────→  │
    │  ←── 200 OK (无新数据) ──────  │
    │   等 3 秒                      │
    │── GET /messages ──────────→  │
    │  ←── 200 OK (有新消息！) ─────  │
    │   等 3 秒                      │
    │── GET /messages ──────────→  │
    │  ...循环                       │

优点：实现最简单，兼容所有浏览器
缺点：
  - 大量无效请求（大部分时候没有新数据，白问了）
  - 实时性差（最坏情况要等一个轮询间隔）
  - 浪费带宽和服务端资源
  - 轮询间隔是矛盾：间隔短 → 请求太多；间隔长 → 延迟高

适用：实时性要求不高的简单场景（如后台管理页面定时刷新）
```

### 三、长轮询（Long Polling）

```
短轮询的改进版：请求挂起直到有数据才返回

  客户端                              服务端
    │── GET /messages ──────────→  │
    │                               │  没有新数据 → 不返回，hold 住连接
    │   （挂起等待...）               │
    │                               │  ...过了 10 秒...
    │                               │  有新消息了！
    │  ←── 200 OK (新消息) ─────────  │
    │                               │
    │── GET /messages ──────────→  │  立即再发一个长轮询请求
    │   （继续挂起等待...）            │
    │                               │
    │   超过超时时间（如 30 秒）        │
    │  ←── 204 No Content ─────────  │  超时返回空，客户端立即再发
    │── GET /messages ──────────→  │
    │   ...                         │

优点：
  - 比短轮询节省请求（有数据才返回）
  - 实时性好（数据来了立即推送）
  - 兼容性好（纯 HTTP，无特殊协议）

缺点：
  - 服务端需要 hold 大量挂起的连接（占用线程/连接池资源）
  - 每次收到数据后要重新建立轮询请求（有短暂真空期）
  - 服务端需要设超时（防止连接无限挂起）
  - 高并发下服务端压力大

适用：消息通知、Web 端即时通讯（WebSocket 普及前的主流方案）
```

### 四、SSE（Server-Sent Events）

```
HTTP 原生的服务端推送方案：服务端通过一个长连接持续推送数据

  客户端                              服务端
    │── GET /stream ───────────→   │
    │   Accept: text/event-stream   │
    │                               │
    │  ←── HTTP/1.1 200 OK          │
    │      Content-Type: text/event-stream
    │                               │
    │  ←── data: {"msg":"hello"}    │  推送第 1 条
    │  ←── data: {"msg":"world"}    │  推送第 2 条
    │      ...                      │
    │  ←── data: {"msg":"update"}   │  推送第 N 条
    │      ...                      │  连接一直保持
    │                               │

SSE 数据格式（纯文本，非常简单）：
  data: 消息内容\n\n            → 一条消息
  event: update\ndata: {...}\n\n → 带事件类型
  id: 123\ndata: {...}\n\n      → 带 ID（断线重连时可以从这个 ID 续上）
  retry: 5000\n                 → 告诉客户端重连间隔（ms）

浏览器端使用：
  const es = new EventSource('/stream');
  es.onmessage = (e) => console.log(e.data);
  es.addEventListener('update', (e) => { ... });

优点：
  - HTTP 原生支持，不需要特殊协议
  - 自动重连（浏览器内置，断线后自动重新连接）
  - 支持事件 ID（断线重连后可以从上次的 ID 继续）
  - 轻量（纯文本，实现简单）

缺点：
  - 单向推送（只能服务端 → 客户端，客户端要发数据还得另外发 HTTP 请求）
  - 基于 HTTP/1.1 时每个 SSE 连接占一个 TCP 连接（浏览器有 6 连接限制）
  - 不支持二进制数据
  - IE/旧浏览器不支持（现代浏览器都支持）

适用：
  - 实时数据推送（股票行情、新闻 feed）
  - ChatGPT/大模型流式输出（token 一个一个吐出来）← 典型场景
  - 监控面板实时刷新
```

### 五、WebSocket

```
真正的全双工长连接协议

  客户端                              服务端
    │── HTTP Upgrade 请求 ────────→  │  (握手阶段，还是 HTTP)
    │  ←── 101 Switching Protocols   │
    │                                │
    │  ══════ WebSocket 连接建立 ═════ │  (之后不再是 HTTP)
    │                                │
    │── 消息 A ────────────────────→  │  客户端主动发
    │  ←── 消息 B ──────────────────  │  服务端主动推
    │── 消息 C ────────────────────→  │  双向随时发
    │  ←── 消息 D ──────────────────  │
    │      ...                       │

优点：
  - 真正的全双工：双方都可以随时主动发消息
  - 低开销：握手后数据帧头部 2~10 字节（vs HTTP 头部几百字节）
  - 支持二进制数据
  - 高实时性：无需反复建连，消息即时到达

缺点：
  - 有状态连接 → 服务端需要维护每个连接的状态（内存开销）
  - 无法利用 HTTP 缓存、CDN 等基础设施
  - 需要处理心跳（检测连接是否还活着）
  - 穿越代理/防火墙可能有问题（某些企业网络不支持 Upgrade）
  - 连接中断后需要自己实现重连逻辑

适用：实时聊天、在线游戏、协同编辑、股票交易
```

### 六、总览对比

| | 短轮询 | 长轮询 | SSE | WebSocket |
|---|--------|--------|-----|-----------|
| 方向 | 客户端 → 服务端 | 客户端 → 服务端 | **服务端 → 客户端** | **双向** |
| 实时性 | 差（轮询间隔） | 好 | 好 | **最好** |
| 服务端开销 | 低（无状态） | 中（hold 连接） | 中 | 高（有状态） |
| 实现复杂度 | 最简单 | 简单 | 简单 | 较复杂 |
| 协议 | HTTP | HTTP | HTTP | WebSocket |
| 自动重连 | 客户端控制 | 客户端控制 | **浏览器内置** | 需自己实现 |
| 二进制支持 | ✓ | ✓ | ✗ | **✓** |
| 兼容性 | 最好 | 好 | 好（IE 除外） | 好 |
| 典型场景 | 简单定时刷新 | Web IM（早期） | LLM 流式输出、行情 | 聊天、游戏、协同 |

### 七、怎么选

```
决策树：

  需要双向通信吗？
  ├── 是 → WebSocket
  └── 否 → 只需要服务端推送？
            ├── 是 → SSE（轻量、自动重连、HTTP 原生）
            └── 否 → 只是客户端定期获取数据？
                      ├── 实时性要求高 → 长轮询
                      └── 实时性要求不高 → 短轮询

  特殊场景：
  - LLM 流式输出 → SSE（ChatGPT 就是用的 SSE）
  - 在线游戏 → WebSocket（双向 + 低延迟 + 二进制）
  - 后台管理页面定时刷新 → 短轮询（最简单）
  - 消息推送 → SSE 或 WebSocket（看是否需要客户端上行）
```

### 八、面试话术

> **HTTP 长连接有哪些方式？**
> "首先 HTTP Keep-Alive 是 TCP 连接复用，不是服务端推送。真正实现'服务端主动推消息'有四种方案：**短轮询**最简单但浪费资源；**长轮询**请求挂起直到有数据再返回，减少无效请求但服务端 hold 连接有压力；**SSE** 是 HTTP 原生的服务端推送，单向推、自动重连、纯文本，适合行情推送和 LLM 流式输出；**WebSocket** 是真正的全双工协议，双方都能随时发消息，开销最小但有状态、需要自己做重连。简单场景用 SSE，双向通信用 WebSocket。"

## 面试回答模板

> **TCP 三次握手**："第一次客户端发 SYN 告知初始序列号，第二次服务端回 SYN+ACK 告知自己的序列号并确认客户端的，第三次客户端发 ACK 确认服务端的。三次而非两次的原因是防止历史重复连接导致服务端白白建连浪费资源。"
>
> **TCP 四次挥手**："全双工，两个方向各需要一个 FIN+ACK。主动关闭方最后进入 TIME_WAIT 等 2MSL——一是确保最后的 ACK 能到达对方（丢了可以重发 FIN），二是让旧连接的残留报文在网络中消亡。"
>
> **TCP vs UDP**："TCP 面向连接、可靠（确认重传、流控、拥塞控制）、字节流，适合要求可靠传输的场景。UDP 无连接、不可靠、数据报、头部小（8字节）、效率高，适合实时性要求高的场景如直播、游戏。"
>
> **HTTPS 原理**："HTTP + TLS。用非对称加密交换对称密钥（安全但慢），后续用对称加密传输数据（快）。通过 CA 证书链验证服务端身份，通过 MAC 保证数据完整性。"
>
> **从输入 URL 到页面显示**："DNS 解析域名得到 IP → TCP 三次握手 → TLS 握手（HTTPS）→ 发送 HTTP 请求 → 服务端处理返回响应 → 浏览器解析 HTML/CSS 构建渲染树 → 布局绘制显示。"
>
> **Cookie vs Session vs Token**："Cookie 存客户端自动携带、Session 存服务端通过 Cookie 传 ID（分布式要共享存储）、Token (JWT) 自包含用户信息只需验签（天然适合分布式）。"

## HTTPS 八股速记（TLS、解决问题、连接建立）

**类别**：计算机网络 / 应用层 / HTTPS

### 一、HTTPS 和 TLS 是什么

```
HTTPS = HTTP + TLS

TLS（Transport Layer Security，传输层安全协议）是 SSL 的升级版。
常说"SSL 证书"、"SSL 握手"，工程上基本都指 TLS（主流是 TLS 1.2 / 1.3）。

分层上看：
  HTTP（应用层）
  TLS（应用层与传输层之间的安全层）
  TCP（传输层，HTTP/1.1 与 HTTP/2）
  UDP + QUIC（HTTP/3）
```

### 二、HTTPS 解决了什么问题

```
纯 HTTP 三大问题：
  1) 机密性（Confidentiality）缺失：明文传输，可被窃听
  2) 完整性（Integrity）缺失：报文可被篡改
  3) 身份认证（Authentication）缺失：可能连到假服务器（中间人攻击）

HTTPS 对应方案：
  1) 机密性：对称加密（AES-GCM/ChaCha20-Poly1305）
  2) 完整性：消息认证码/AEAD 校验，篡改可检测
  3) 身份认证：数字证书 + CA 信任链 + 域名校验
```

### 三、为什么要"非对称 + 对称"混合加密

```
只用对称加密：快，但密钥怎么安全分发？
只用非对称加密：安全，但性能开销大、吞吐低

TLS 做法：
  握手阶段：用非对称机制协商共享密钥
  数据阶段：用对称加密传输应用数据

结论：兼顾安全和性能
```

### 四、TLS 1.2 建连流程（高频面试）

```
客户端                                                  服务端
  │                                                       │
  │── ① ClientHello ───────────────────────────────────→  │
  │   TLS版本、支持的加密套件、随机数 client_random         │
  │                                                       │
  │  ←── ② ServerHello + Certificate (+ ServerKeyExchange)│
  │      选择的套件、随机数 server_random、证书链           │
  │                                                       │
  │  ③ 客户端验证证书链/域名/有效期                         │
  │     （不通过则告警并终止）                              │
  │                                                       │
  │── ④ ClientKeyExchange ─────────────────────────────→  │
  │   （RSA时代是发加密的 PMS；ECDHE 时代是发密钥交换参数）  │
  │                                                       │
  │── ⑤ ChangeCipherSpec + Finished ───────────────────→  │
  │  ←── ⑥ ChangeCipherSpec + Finished ─────────────────  │
  │                                                       │
  │           之后开始用会话密钥加密 HTTP 数据               │
```

```
补充：
  - 现代 TLS1.2 常用 ECDHE，而不是纯 RSA 密钥交换
  - ECDHE 具备前向保密（PFS）
```

### 五、TLS 1.3 建连流程（重点变化）

```
TLS 1.3 核心变化：
  1) 握手往返减少：通常 1-RTT 完成（比 1.2 更快）
  2) 默认前向保密：移除 RSA 密钥交换，主推 (EC)DHE
  3) 弱算法下线：移除大量不安全/过时套件
  4) 支持 0-RTT：会话恢复可首包带应用数据（有重放风险）

典型 1-RTT：
  ClientHello(含 key share) ->
  <- ServerHello(含 key share) + EncryptedExtensions + Certificate + Finished
  -> Finished
  握手完成后传应用数据
```

### 六、证书校验在校验什么

```
客户端拿到证书后主要看：
  1) 证书链是否能链到受信任根 CA
  2) 证书签名是否合法（上级 CA 公钥验签）
  3) 域名是否匹配（CN/SAN 与访问域名一致）
  4) 是否在有效期内
  5) 是否被吊销（CRL/OCSP，实际常结合策略）

任一失败：浏览器提示证书不安全
```

### 七、常见追问：中间人攻击为什么难成功

```
中间人想伪造服务端，需要伪造一张"浏览器信任"的证书。
但证书需要受信任 CA 签名，攻击者拿不到 CA 私钥，通常无法伪造有效证书。
所以浏览器在证书校验阶段会拦截异常，攻击难以成功。
```

### 八、常见追问：前向保密（PFS）是什么

```
前向保密：即使未来服务器私钥泄露，也不能解密历史抓包流量。

原因：
  历史会话密钥来自临时密钥交换（如 ECDHE），不是直接由服务器长期私钥推出。
```

### 九、常见追问：0-RTT 的优缺点

```
优点：恢复会话时时延更低，可首包发应用数据
缺点：0-RTT 数据可能被重放，不适合非幂等操作（如支付、下单）

实践建议：
  0-RTT 仅用于幂等请求（GET 等），敏感写操作禁用
```

### 十、面试 30 秒话术（可直接背）

> HTTPS 本质是 HTTP 加 TLS，主要解决了 HTTP 明文传输带来的窃听、篡改和身份伪造问题。TLS 在握手阶段通过证书校验服务端身份，并通过非对称机制协商会话密钥，后续用对称加密传输数据，兼顾安全和性能。TLS1.3 相比 1.2 进一步减少握手时延、默认前向保密，并支持 0-RTT 会话恢复，但 0-RTT 要注意重放风险。
