## 线程间通信方式

**类别**：Java 并发 / 线程通信 / JUC

### 一、总览

线程间通信的本质就是两件事：**共享数据**和**协调执行顺序**。

```
Java 线程间通信方式：

  共享内存类（读写同一块数据）：
    ① volatile
    ② synchronized
    ③ Lock + Condition
    ④ 原子类（Atomic*）

  消息传递类（通过某种机制通知/等待）：
    ⑤ wait() / notify() / notifyAll()
    ⑥ Lock + Condition 的 await() / signal()
    ⑦ CountDownLatch
    ⑧ CyclicBarrier
    ⑨ Semaphore
    ⑩ BlockingQueue
    ⑪ Future / CompletableFuture
    ⑫ Thread.join()
    ⑬ LockSupport.park() / unpark()
```

---

### 二、逐个讲解

#### 1. volatile —— 轻量级可见性保证

```java
volatile boolean flag = false;

// 线程 A
flag = true;

// 线程 B
while (!flag) {
    // 如果不加 volatile，B 可能永远看不到 flag 变成 true
    // 因为 B 可能一直读的是自己 CPU 缓存里的旧值
}
```

**作用**：
- **可见性**：一个线程修改 volatile 变量后，其他线程立即可见（强制从主内存读写，不走 CPU 缓存）
- **有序性**：禁止指令重排序（通过内存屏障实现）
- **不保证原子性**：`i++` 这种读-改-写操作不是原子的，volatile 保护不了

**适用场景**：状态标志位（如上面的 flag）、双重检查锁定的单例模式。

#### 2. synchronized —— 互斥 + 可见性 + 有序性

```java
private int count = 0;
private final Object lock = new Object();

// 线程 A 和线程 B 都调
synchronized (lock) {
    count++;
    // 同一时刻只有一个线程能进入这个代码块
    // 退出 synchronized 时把修改刷回主内存
    // 进入 synchronized 时从主内存重新读取
}
```

**三种用法**：

```java
// 1. 修饰实例方法 → 锁的是 this
public synchronized void method() { }

// 2. 修饰静态方法 → 锁的是 Class 对象
public static synchronized void method() { }

// 3. 修饰代码块 → 锁的是指定对象
synchronized (lockObj) { }
```

**保证**：原子性 + 可见性 + 有序性（三个都保证）。

#### 3. wait() / notify() / notifyAll() —— 等待-通知机制

```java
// 必须在 synchronized 块内调用（因为要持有锁）

// 线程 A：等待条件
synchronized (lock) {
    while (!condition) {   // 用 while 不用 if，防止虚假唤醒
        lock.wait();       // 释放锁，进入等待队列，线程挂起
    }
    // 条件满足，继续执行
}

// 线程 B：通知
synchronized (lock) {
    condition = true;
    lock.notify();         // 唤醒一个等待中的线程（不释放锁，等退出 synchronized 才释放）
    // lock.notifyAll();   // 唤醒所有等待中的线程
}
```

**关键细节**：
- `wait()` 会**释放锁**并挂起线程，被唤醒后要**重新竞争锁**
- `notify()` **不释放锁**，要等退出 synchronized 块才释放
- 必须用 `while` 循环检查条件，不能用 `if`（防止虚假唤醒 spurious wakeup）
- `notify()` 随机唤醒一个线程，`notifyAll()` 唤醒所有（推荐用 `notifyAll()`，更安全）

#### 4. Lock + Condition —— wait/notify 的增强版

```java
ReentrantLock lock = new ReentrantLock();
Condition condition = lock.newCondition();

// 线程 A：等待
lock.lock();
try {
    while (!conditionMet) {
        condition.await();      // 类似 wait()，释放锁并等待
    }
} finally {
    lock.unlock();
}

// 线程 B：通知
lock.lock();
try {
    conditionMet = true;
    condition.signal();         // 类似 notify()
    // condition.signalAll();   // 类似 notifyAll()
} finally {
    lock.unlock();
}
```

**比 wait/notify 强在哪**：

| 特性 | wait/notify | Lock + Condition |
|------|------------|-----------------|
| 多条件等待 | 只有一个等待队列 | **可以创建多个 Condition**，精确唤醒 |
| 可中断等待 | 不支持 | `await()` 可以响应中断 |
| 超时等待 | `wait(long)` | `await(long, TimeUnit)` 更灵活 |
| 公平性 | 不可控 | `ReentrantLock(true)` 支持公平锁 |

**经典用法**：生产者-消费者问题中，一个 Condition 给生产者（notFull），一个给消费者（notEmpty）。

```java
Condition notFull = lock.newCondition();
Condition notEmpty = lock.newCondition();

// 生产者
lock.lock();
while (queue.isFull()) notFull.await();
queue.add(item);
notEmpty.signal();    // 只唤醒消费者，不会误唤醒其他生产者
lock.unlock();

// 消费者
lock.lock();
while (queue.isEmpty()) notEmpty.await();
item = queue.poll();
notFull.signal();     // 只唤醒生产者
lock.unlock();
```

#### 5. CountDownLatch —— 等待 N 个线程完成

```java
CountDownLatch latch = new CountDownLatch(3);  // 计数器 = 3

// 线程 A、B、C 各自完成任务后 countDown
new Thread(() -> { doTask(); latch.countDown(); }).start();  // 3→2
new Thread(() -> { doTask(); latch.countDown(); }).start();  // 2→1
new Thread(() -> { doTask(); latch.countDown(); }).start();  // 1→0

// 主线程等待，直到计数器归零
latch.await();
System.out.println("三个任务都完成了");
```

**特点**：**一次性的**，计数器归零后不能重置。

**适用**：主线程等待多个子线程初始化完成、多个服务就绪后再开闸放流量。

#### 6. CyclicBarrier —— N 个线程互相等待到齐

```java
CyclicBarrier barrier = new CyclicBarrier(3, () -> {
    System.out.println("三个线程都到齐了，开始下一阶段");
});

// 三个线程各自跑到 barrier 处等待
new Thread(() -> { phase1(); barrier.await(); phase2(); }).start();
new Thread(() -> { phase1(); barrier.await(); phase2(); }).start();
new Thread(() -> { phase1(); barrier.await(); phase2(); }).start();
```

**和 CountDownLatch 的区别**：

| | CountDownLatch | CyclicBarrier |
|---|---|---|
| 谁等谁 | 一个线程等 N 个线程 | N 个线程互相等 |
| 复用 | 一次性 | **可重复使用**（Cyclic 循环的意思） |
| 到齐后 | 等待线程继续 | 可触发回调 + 所有线程继续 |

#### 7. Semaphore —— 控制并发访问数量

```java
Semaphore semaphore = new Semaphore(3);  // 最多 3 个线程同时访问

// 每个线程
semaphore.acquire();    // 获取许可（许可不够就阻塞）
try {
    accessResource();   // 同时最多 3 个线程在这里
} finally {
    semaphore.release();  // 释放许可
}
```

**适用**：限流（如数据库连接池最多 N 个连接）、资源访问控制。

#### 8. BlockingQueue —— 阻塞队列（生产者-消费者首选）

```java
BlockingQueue<String> queue = new ArrayBlockingQueue<>(10);

// 生产者
queue.put(item);    // 队列满了就阻塞，直到有空位

// 消费者
item = queue.take(); // 队列空了就阻塞，直到有数据
```

**常用实现**：

| 实现 | 底层 | 特点 |
|------|------|------|
| ArrayBlockingQueue | 数组 | 有界，创建时指定大小 |
| LinkedBlockingQueue | 链表 | 可选有界（默认 Integer.MAX_VALUE ≈ 无界） |
| PriorityBlockingQueue | 堆 | 无界，按优先级出队 |
| SynchronousQueue | 无缓冲 | 放入和取出必须一一配对（直接传递） |
| DelayQueue | 堆 | 延迟出队，元素到期才能取出 |

**为什么是线程通信的首选**：把锁、条件等待、线程安全全部封装好了，使用者只需要 `put()` 和 `take()`，不用自己管锁。

#### 9. Future / CompletableFuture —— 异步结果获取

```java
// Future：提交任务后拿到一个凭证，需要结果时再取
Future<String> future = executor.submit(() -> {
    return longRunningTask();
});
String result = future.get();  // 阻塞等待结果

// CompletableFuture：链式异步编排（不阻塞）
CompletableFuture.supplyAsync(() -> queryDB())
    .thenApply(data -> process(data))
    .thenAccept(result -> sendResponse(result));
```

**CompletableFuture 比 Future 强在哪**：

| | Future | CompletableFuture |
|---|---|---|
| 获取结果 | `get()` 阻塞 | `thenApply()` 非阻塞回调 |
| 链式调用 | 不支持 | 支持（`thenApply → thenCompose → thenCombine`） |
| 异常处理 | 只能 try-catch | `exceptionally()` / `handle()` |
| 组合多个任务 | 不支持 | `allOf()` / `anyOf()` |

#### 10. Thread.join() —— 等待另一个线程结束

```java
Thread t = new Thread(() -> doSomething());
t.start();
t.join();  // 当前线程阻塞，直到 t 执行完毕
System.out.println("t 执行完了");
```

最简单的线程间协调方式。底层是用 `wait()` 实现的。

#### 11. LockSupport.park() / unpark() —— 最底层的线程阻塞工具

```java
Thread t = new Thread(() -> {
    LockSupport.park();    // 阻塞当前线程
    System.out.println("被唤醒了");
});
t.start();

Thread.sleep(1000);
LockSupport.unpark(t);     // 唤醒指定线程
```

**和 wait/notify 的区别**：

| | wait/notify | LockSupport |
|---|---|---|
| 需要锁 | 必须在 synchronized 内 | **不需要锁** |
| 唤醒目标 | notify 随机唤醒一个 | **unpark 精确唤醒指定线程** |
| 调用顺序 | 先 wait 后 notify | **unpark 可以先于 park 调用**（许可机制） |

`LockSupport` 是 `AQS` 和 `Condition` 的底层实现基础。

### 三、对比总结

| 通信方式 | 核心能力 | 适用场景 | 复杂度 |
|---------|---------|---------|--------|
| volatile | 可见性 | 简单状态标志 | 低 |
| synchronized | 互斥 + 可见性 | 临界区保护 | 低 |
| wait/notify | 等待-通知 | 简单的条件等待 | 中 |
| Lock + Condition | 精确等待-通知 | 多条件等待（生产者-消费者） | 中 |
| CountDownLatch | 等待 N 个完成 | 主线程等子线程就绪 | 低 |
| CyclicBarrier | N 个互相等到齐 | 分阶段并行计算 | 低 |
| Semaphore | 控制并发数 | 限流、资源池 | 低 |
| BlockingQueue | 生产-消费解耦 | 线程池、消息传递 | 低 |
| CompletableFuture | 异步编排 | 异步任务链 | 中 |
| Thread.join() | 等线程结束 | 简单同步 | 低 |
| LockSupport | 底层阻塞/唤醒 | AQS 等框架内部 | 高 |

### 四、面试回答模板

> "Java 线程间通信主要分两大类：**共享内存**和**消息传递**。
>
> 共享内存方面：`volatile` 保证可见性但不保证原子性，适合状态标志；`synchronized` 和 `Lock` 保证互斥访问共享变量。
>
> 消息传递方面：最基础的是 `wait/notify`——在 synchronized 内调用，wait 释放锁并挂起，notify 唤醒等待线程。升级版是 `Lock + Condition`，可以创建多个 Condition 精确唤醒（比如生产者-消费者分别用 notFull 和 notEmpty 两个条件）。
>
> JUC 提供了更高级的工具：`CountDownLatch` 等待 N 个线程完成（一次性）；`CyclicBarrier` N 个线程互相等到齐（可复用）；`Semaphore` 控制并发访问数；`BlockingQueue` 封装了锁和条件等待，是生产者-消费者的首选实现。
>
> 最底层的是 `LockSupport.park/unpark`，不需要锁就能精确阻塞/唤醒指定线程，是 AQS 的实现基础。"

## 线程调度方法

**类别**：Java 并发 / 线程调度 / 线程控制

### 一、什么是线程调度

线程调度就是**操作系统 / JVM 决定哪个线程在什么时候获得 CPU 执行权**。Java 中线程调度分两个层面：

```
OS 层面：Java 线程是映射到操作系统内核线程的（1:1 模型）
         实际的 CPU 调度由 OS 的调度器完成（抢占式调度）
         Java 代码无法直接控制

Java 层面：提供了一些 API 来"建议"或"影响"调度行为
           比如优先级、让出 CPU、休眠、等待等
```

### 二、Java 中的线程调度方式

#### 1. 线程优先级 —— setPriority()

```java
Thread t = new Thread(() -> doSomething());
t.setPriority(Thread.MAX_PRIORITY);  // 10
t.setPriority(Thread.NORM_PRIORITY); // 5（默认）
t.setPriority(Thread.MIN_PRIORITY);  // 1
t.start();
```

```
优先级范围：1（最低）~ 10（最高），默认 5

注意：
  - 优先级只是给 OS 调度器的"建议"，不保证高优先级一定先执行
  - 不同 OS 对 Java 优先级的映射不同
    （Windows 有 7 级，Linux 很多版本基本忽略 Java 优先级）
  - 生产中几乎不用 setPriority 来控制调度，不可靠
```

#### 2. Thread.sleep() —— 让当前线程休眠

```java
// 当前线程放弃 CPU，休眠指定时间后重新进入就绪状态
Thread.sleep(1000);  // 休眠 1 秒

// 更精确的版本
TimeUnit.MILLISECONDS.sleep(500);
```

```
关键特性：
  - 不释放锁（在 synchronized 块内 sleep，锁不会放）
  - 休眠时间到了不代表立即执行，只是回到就绪状态等 CPU 调度
  - 可以被 interrupt() 打断 → 抛出 InterruptedException
```

**和 wait() 的区别**：

| | sleep() | wait() |
|---|---|---|
| 所属类 | Thread | Object |
| 释放锁 | **不释放** | **释放** |
| 使用条件 | 任何地方 | 必须在 synchronized 内 |
| 唤醒方式 | 时间到 / interrupt | notify / notifyAll / interrupt |
| 目的 | 暂停执行一段时间 | 等待某个条件被满足 |

#### 3. Thread.yield() —— 让出 CPU

```java
// 当前线程主动让出 CPU，回到就绪状态
// 给同优先级或更高优先级的线程一个执行机会
Thread.yield();
```

```
关键特性：
  - 只是"建议"让出，调度器可以忽略（让完可能又调度回自己）
  - 不释放锁
  - 不会阻塞线程（从运行态 → 就绪态，不是阻塞态）
  - 实际开发中很少用，行为不确定
```

**sleep(0) vs yield()**：

```
效果几乎相同，都是让出当前时间片
但语义不同：
  yield()：我愿意让给同优先级的线程
  sleep(0)：我休眠 0 毫秒（实际也是让出时间片）
```

#### 4. Thread.join() —— 等待另一个线程执行完

```java
Thread t1 = new Thread(() -> { /* 任务 1 */ });
Thread t2 = new Thread(() -> { /* 任务 2，依赖 t1 的结果 */ });

t1.start();
t1.join();    // 主线程阻塞，等 t1 执行完
t2.start();   // t1 完了再启动 t2

// 带超时的版本
t1.join(3000);  // 最多等 3 秒，超时就不等了
```

```
关键特性：
  - 底层是用 wait() 实现的（源码里是 while (isAlive()) wait(0)）
  - 会释放 join 调用时持有的锁（因为用的是 wait）
  - 可以被 interrupt() 打断
```

#### 5. Thread.interrupt() —— 中断线程

```java
Thread t = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        // 正常执行
        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            // sleep 被中断，重新设置中断标志
            Thread.currentThread().interrupt();
            break;
        }
    }
});

t.start();
t.interrupt();  // 设置中断标志 / 打断阻塞方法
```

```
interrupt() 不是"杀死"线程，而是：
  - 如果线程在 sleep/wait/join 等阻塞方法上 → 抛出 InterruptedException
  - 如果线程在正常运行 → 只是设置中断标志位为 true，线程自己决定怎么响应

三个相关方法：
  t.interrupt()                    设置中断标志
  t.isInterrupted()                查询中断标志（不清除）
  Thread.interrupted()             查询并清除中断标志（静态方法）
```

#### 6. Object.wait() / notify() —— 条件等待调度

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();     // 释放锁，线程挂起，等待被唤醒
    }
}

synchronized (lock) {
    condition = true;
    lock.notify();       // 唤醒一个等待中的线程
}
```

（详细内容在前面「线程间通信方式」部分已经讲过，此处不重复）

#### 7. LockSupport.park() / unpark() —— 底层阻塞调度

```java
// 阻塞当前线程
LockSupport.park();

// 唤醒指定线程（可以先于 park 调用）
LockSupport.unpark(targetThread);
```

（详细内容在前面「线程间通信方式」部分已经讲过）

### 三、线程状态与调度方法的关系

```
                    ┌─────────────────────────────────────┐
                    │                                     │
  NEW ──start()──→ RUNNABLE ←──notify()/unpark()── WAITING/TIMED_WAITING
                    │    ↑                                 ↑
                    │    │                                 │
                    │    └──── yield() ────┘               │
                    │         (就绪→就绪)                   │
                    │                                      │
                    ├──sleep(t)────→ TIMED_WAITING ────时间到──┘
                    ├──wait()──────→ WAITING ──────────────┘
                    ├──join()──────→ WAITING ──────────────┘
                    ├──park()──────→ WAITING ──────────────┘
                    │
                    └──run()结束──→ TERMINATED

  BLOCKED：等待获取 synchronized 锁时进入（和调度 API 无关）
```

各方法对线程状态的影响：

| 方法 | 当前线程状态变化 | 释放锁 | 释放 CPU |
|------|----------------|--------|---------|
| sleep(t) | RUNNABLE → TIMED_WAITING | ❌ | ✅ |
| yield() | RUNNABLE → RUNNABLE（就绪） | ❌ | ✅（建议性） |
| wait() | RUNNABLE → WAITING | ✅ | ✅ |
| wait(t) | RUNNABLE → TIMED_WAITING | ✅ | ✅ |
| join() | RUNNABLE → WAITING | ✅（底层是 wait） | ✅ |
| join(t) | RUNNABLE → TIMED_WAITING | ✅ | ✅ |
| park() | RUNNABLE → WAITING | ❌ | ✅ |
| interrupt() | 不改变状态，只设置标志或抛异常 | - | - |

### 四、面试回答模板

> "Java 线程调度主要靠 OS 的抢占式调度，Java 层面提供了几种 API 来影响调度：
>
> **sleep()** 让线程休眠指定时间，**不释放锁**，时间到后回到就绪态；**yield()** 主动让出 CPU 给同优先级线程，但只是建议性的，调度器可以忽略。这两个都不释放锁。
>
> **wait()** 释放锁并挂起，等待 notify 唤醒，必须在 synchronized 内使用；**join()** 底层就是 wait，等待另一个线程执行完。
>
> **interrupt()** 不是杀线程，是设置中断标志——如果线程在 sleep/wait/join 上会抛 InterruptedException，否则只是标志位置 true，线程自己检查决定是否退出。
>
> **LockSupport.park/unpark** 是最底层的阻塞原语，不需要锁，支持先 unpark 后 park，是 AQS 的实现基础。
>
> 关键区分：sleep 不释放锁、wait 释放锁；yield 是建议性让出、sleep 是强制休眠；interrupt 不是停止线程，是协作式中断。"

## ThreadLocal

**类别**：Java 并发 / 线程隔离 / 数据传递

### 一、ThreadLocal 是什么

ThreadLocal 提供**线程级别的局部变量**——每个线程都有自己独立的一份副本，线程之间互不干扰，不需要加锁。

```java
ThreadLocal<String> threadLocal = new ThreadLocal<>();

// 线程 A
threadLocal.set("A 的数据");
threadLocal.get();  // → "A 的数据"

// 线程 B
threadLocal.set("B 的数据");
threadLocal.get();  // → "B 的数据"（和 A 互不影响）
```

**一句话**：ThreadLocal 不是解决共享变量并发问题的，它是**让每个线程拥有自己的私有变量**，从根本上避免共享。

### 二、底层实现原理

```
每个 Thread 对象内部有一个 ThreadLocalMap：

Thread {
    ThreadLocal.ThreadLocalMap threadLocals;  // 每个线程自己的 map
}

ThreadLocalMap {
    Entry[] table;  // 数组存储，和 HashMap 类似
}

Entry extends WeakReference<ThreadLocal<?>> {
    Object value;   // 存储的值
    // key 是 ThreadLocal 对象本身（弱引用）
    // value 是实际的数据（强引用）
}
```

```
数据结构：

Thread A
  └── ThreadLocalMap
        ├── Entry[i]: key=threadLocal1(弱引用) → value="A的数据1"
        └── Entry[j]: key=threadLocal2(弱引用) → value="A的数据2"

Thread B
  └── ThreadLocalMap
        ├── Entry[i]: key=threadLocal1(弱引用) → value="B的数据1"
        └── Entry[j]: key=threadLocal2(弱引用) → value="B的数据2"
```

**set/get 的流程**：

```java
// set
public void set(T value) {
    Thread t = Thread.currentThread();       // 拿到当前线程
    ThreadLocalMap map = t.threadLocals;     // 拿到线程自己的 map
    if (map != null)
        map.set(this, value);               // key = 当前 ThreadLocal 对象，value = 数据
    else
        createMap(t, value);
}

// get
public T get() {
    Thread t = Thread.currentThread();
    ThreadLocalMap map = t.threadLocals;
    if (map != null) {
        Entry e = map.getEntry(this);       // 用当前 ThreadLocal 对象作为 key 查找
        if (e != null) return (T) e.value;
    }
    return setInitialValue();
}
```

**所以数据是存在 Thread 对象里的，不是存在 ThreadLocal 对象里。** ThreadLocal 只是一个"钥匙"，用来从当前线程的 map 里取对应的值。

### 三、内存泄漏问题（面试必问）

#### 泄漏是怎么发生的

```
Entry 的 key 是 ThreadLocal 的弱引用（WeakReference）
Entry 的 value 是强引用

当 ThreadLocal 对象被外部丢弃（没有强引用了）：
  → GC 回收 ThreadLocal 对象
  → Entry 的 key 变成 null（弱引用被回收了）
  → 但 Entry 的 value 还在！（强引用，GC 回收不了）
  → 这个 value 就泄漏了——既用不了（key 没了找不到），也回收不了

如果线程一直活着（比如线程池里的核心线程不会销毁）：
  → Thread → ThreadLocalMap → Entry(key=null, value=泄漏的数据)
  → 这条引用链一直在，value 永远不会被 GC
```

```
引用关系：

ThreadLocal 对象 ←─ 弱引用 ── Entry.key
                                Entry.value ──→ 实际数据（强引用）
                                     ↑
                            ThreadLocalMap
                                     ↑
                                  Thread（线程池中长期存活）

ThreadLocal 对象被 GC → key 变 null → value 成了"孤魂野鬼"
```

#### 为什么 key 要用弱引用

> "如果 key 也是强引用，那即使外部不再使用 ThreadLocal 对象，Entry 里的 key 还在强引用着它 → ThreadLocal 对象也泄漏了。弱引用至少保证了 ThreadLocal 对象本身能被回收。value 的泄漏是个代价，但可以通过主动 remove 来避免。"

#### 解决方案

```java
// 用完必须 remove！
ThreadLocal<UserInfo> userContext = new ThreadLocal<>();

try {
    userContext.set(currentUser);
    // 业务逻辑
    doSomething();
} finally {
    userContext.remove();  // 用完一定要 remove，防止内存泄漏
}
```

**ThreadLocalMap 自身也有清理机制**：在 `get()` / `set()` / `remove()` 时会顺带清理 key 为 null 的 Entry（探测式清理 + 启发式清理）。但这不可靠，不能依赖它，**必须手动 remove()**。

### 四、典型使用场景

#### 场景 1：用户上下文传递（最常见）

```java
// Web 应用中，拦截器设置当前用户信息
public class UserContext {
    private static final ThreadLocal<UserInfo> CONTEXT = new ThreadLocal<>();

    public static void set(UserInfo user) { CONTEXT.set(user); }
    public static UserInfo get() { return CONTEXT.get(); }
    public static void clear() { CONTEXT.remove(); }
}

// 拦截器
public boolean preHandle(request, response, handler) {
    UserInfo user = parseToken(request);
    UserContext.set(user);
    return true;
}

public void afterCompletion(request, response, handler, ex) {
    UserContext.clear();  // 请求结束清理
}

// 业务代码中任意位置
UserInfo user = UserContext.get();  // 不用层层传参
```

#### 场景 2：数据库连接 / 事务管理

```java
// Spring 的事务管理就是用 ThreadLocal 绑定 Connection
// 保证同一个线程（同一个请求）的多次 DB 操作用同一个连接 → 同一个事务
TransactionSynchronizationManager → ThreadLocal<Map<Object, Object>> resources
```

#### 场景 3：SimpleDateFormat 线程安全

```java
// SimpleDateFormat 不是线程安全的，多线程共用会出问题
// 用 ThreadLocal 让每个线程有自己的实例
private static final ThreadLocal<SimpleDateFormat> dateFormat =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

// 每个线程拿到的是自己的 SimpleDateFormat 实例，不存在并发问题
String date = dateFormat.get().format(new Date());
```

### 五、InheritableThreadLocal —— 父子线程传递

普通 ThreadLocal 的数据**无法传递给子线程**：

```java
ThreadLocal<String> tl = new ThreadLocal<>();
tl.set("父线程数据");

new Thread(() -> {
    tl.get();  // → null（子线程拿不到父线程的数据）
}).start();
```

InheritableThreadLocal 可以让**子线程继承父线程的数据**：

```java
InheritableThreadLocal<String> itl = new InheritableThreadLocal<>();
itl.set("父线程数据");

new Thread(() -> {
    itl.get();  // → "父线程数据"（子线程继承了）
}).start();
```

```
原理：Thread 创建时，如果父线程有 inheritableThreadLocals，
     子线程会在构造方法中把父线程的数据浅拷贝一份

局限：只在 new Thread() 创建时复制一次
     → 线程池里的线程是复用的，不是每次都 new
     → 线程池场景下 InheritableThreadLocal 不可靠
     → 需要用阿里的 TransmittableThreadLocal（TTL）来解决
```

### 六、ThreadLocal vs synchronized

| | ThreadLocal | synchronized |
|---|---|---|
| 思路 | 每个线程自己一份，**空间换时间** | 所有线程共享一份，加锁保护 |
| 性能 | 无锁，无竞争 | 有锁竞争开销 |
| 适用 | 数据本来就是线程独有的（用户上下文、连接、格式化器） | 数据必须被多个线程共享和修改（计数器、共享状态） |
| 数据一致性 | 每个线程看到自己的值 | 所有线程看到同一个最新值 |

### 七、面试回答模板

> "ThreadLocal 给每个线程提供独立的变量副本，线程之间互不干扰，不需要加锁。底层实现是**每个 Thread 对象持有一个 ThreadLocalMap**，key 是 ThreadLocal 对象（弱引用），value 是实际数据。数据存在线程里，ThreadLocal 只是一个查找的'钥匙'。
>
> **内存泄漏问题**：Entry 的 key 是弱引用，ThreadLocal 对象被 GC 后 key 变 null，但 value 是强引用不会被回收。在线程池场景下线程长期存活，value 就泄漏了。解决办法是**用完必须调 remove()**，放在 finally 块里保证执行。
>
> 典型场景：Web 应用的用户上下文传递（拦截器 set，业务层 get，结束 clear）、Spring 事务管理绑定 Connection、SimpleDateFormat 线程安全。
>
> 父子线程传递用 InheritableThreadLocal，但在线程池场景不可靠（线程复用不会重新拷贝），需要用阿里的 TransmittableThreadLocal。
>
> ThreadLocal 和 synchronized 思路不同：ThreadLocal 是**空间换时间**（每个线程一份副本），synchronized 是**时间换空间**（共享一份数据加锁保护）。"

## Java 内存模型（JMM）、volatile、内存屏障、happens-before、synchronized

**类别**：Java 并发 / 内存模型 / 可见性 / 有序性

### 一、为什么需要 JMM

现代 CPU 有多级缓存（L1/L2/L3），每个线程运行在不同 CPU 核心上，各自有自己的缓存副本：

```
线程 A（CPU 核心 1）          线程 B（CPU 核心 2）
┌──────────────┐            ┌──────────────┐
│ 工作内存       │            │ 工作内存       │
│ (CPU 缓存)    │            │ (CPU 缓存)    │
│ x = 0 (副本)  │            │ x = 0 (副本)  │
└──────┬───────┘            └──────┬───────┘
       │                           │
       └───────────┬───────────────┘
               ┌───▼───┐
               │ 主内存  │
               │ x = 0  │
               └───────┘
```

**三个核心问题**：

| 问题 | 描述 | 例子 |
|------|------|------|
| **可见性** | 线程 A 修改了 x，线程 B 看不到 | A 把 x 改成 1 写回主内存，B 还在读自己缓存里的 x=0 |
| **原子性** | 一个操作被其他线程看到中间状态 | `i++` 实际是读-改-写三步，可能被打断 |
| **有序性** | 编译器/CPU 重排序指令，执行顺序和代码顺序不同 | 代码写的 a=1; b=2; 实际执行可能是 b=2; a=1; |

**JMM（Java Memory Model）就是定义了一套规则，告诉你在什么条件下一个线程的修改对另一个线程是可见的、有序的。**

### 二、volatile

#### volatile 做了什么

```java
volatile boolean flag = false;
volatile int count = 0;
```

**保证两件事**：

```
1. 可见性：
   写 volatile 变量 → 立即刷回主内存
   读 volatile 变量 → 从主内存重新读取（不用缓存）
   → 一个线程修改了 volatile 变量，其他线程立即可见

2. 有序性（禁止重排序）：
   volatile 写之前的操作不会被重排到写之后
   volatile 读之后的操作不会被重排到读之前
   → 通过内存屏障实现
```

**不保证原子性**：

```java
volatile int count = 0;

// 线程 A 和线程 B 同时执行
count++;  // 不是原子操作！

// count++ 实际是三步：
// 1. 读 count 的值（从主内存）
// 2. +1
// 3. 写回 count（到主内存）
// 两个线程可能同时读到 0 → 都 +1 → 都写回 1 → 结果是 1 不是 2

// 需要原子性用 AtomicInteger 或 synchronized
```

#### volatile 的典型使用场景

**场景 1：状态标志位**

```java
volatile boolean shutdown = false;

// 线程 A
public void shutdown() { shutdown = true; }

// 线程 B
while (!shutdown) {
    doWork();
}
```

**场景 2：双重检查锁定单例（DCL）**

```java
public class Singleton {
    private static volatile Singleton instance;  // 必须加 volatile

    public static Singleton getInstance() {
        if (instance == null) {                  // 第一次检查（无锁）
            synchronized (Singleton.class) {
                if (instance == null) {           // 第二次检查（有锁）
                    instance = new Singleton();   // 这一步可能被重排序
                }
            }
        }
        return instance;
    }
}
```

**为什么 DCL 必须加 volatile**：

```
new Singleton() 实际分三步：
  ① 分配内存空间
  ② 调用构造方法初始化对象
  ③ 把引用指向内存地址（instance = 地址）

没有 volatile 时，②③ 可能被重排序为 ①③②：
  线程 A 执行到 ③ 但还没执行 ②（对象还没初始化完）
  线程 B 进来发现 instance != null → 直接返回
  → 拿到了一个没有初始化完的对象 → 程序出错

加了 volatile → 禁止重排序 → ①②③ 严格有序
```

### 三、内存屏障（Memory Barrier）

内存屏障是 **volatile 和 synchronized 实现可见性和有序性的底层机制**。

#### 四种屏障

```
LoadLoad 屏障：   Load1; LoadLoad;  Load2   → Load1 必须在 Load2 之前读取完成
StoreStore 屏障： Store1; StoreStore; Store2 → Store1 必须在 Store2 之前写入完成
LoadStore 屏障：  Load1; LoadStore; Store2   → Load1 必须在 Store2 之前读取完成
StoreLoad 屏障：  Store1; StoreLoad; Load2   → Store1 必须在 Load2 之前写入完成
                                              （最重的屏障，同时刷缓存）
```

#### volatile 的内存屏障规则

```
volatile 写操作：
  [前面的所有操作]
  StoreStore 屏障   ← 保证前面的写都刷到主内存了
  [volatile 写]
  StoreLoad 屏障    ← 保证 volatile 写对后续读可见

volatile 读操作：
  [volatile 读]
  LoadLoad 屏障     ← 保证 volatile 读完之后再读其他变量
  LoadStore 屏障    ← 保证 volatile 读完之后再写其他变量
  [后面的所有操作]
```

**简单记忆**：
- volatile **写**之前插入 StoreStore，之后插入 StoreLoad → 写之前的操作不会排到写后面
- volatile **读**之后插入 LoadLoad + LoadStore → 读之后的操作不会排到读前面

### 四、happens-before 规则

happens-before 是 JMM 定义的**偏序关系**：如果操作 A happens-before 操作 B，那么 A 的结果对 B **一定可见**。

#### 8 条 happens-before 规则

```
1. 程序顺序规则：
   同一个线程中，前面的操作 happens-before 后面的操作
   （单线程内代码顺序就是 happens-before 顺序）

2. volatile 规则：
   volatile 写 happens-before 后续对该 volatile 的读
   （写了就一定能被后面的读看到）

3. 锁规则（synchronized）：
   unlock happens-before 后续对同一把锁的 lock
   （线程 A 在 synchronized 块内的修改，线程 B 进入同一个 synchronized 块时一定能看到）

4. 线程启动规则：
   Thread.start() happens-before 线程内的所有操作
   （主线程在 start 之前的修改，子线程一定能看到）

5. 线程终止规则：
   线程内的所有操作 happens-before Thread.join() 返回
   （子线程的所有修改，在 join 返回后主线程一定能看到）

6. 中断规则：
   interrupt() 调用 happens-before 被中断线程检测到中断

7. 终结器规则：
   构造方法 happens-before finalize()

8. 传递性：
   如果 A happens-before B，B happens-before C
   → A happens-before C
```

#### 结合实例理解

```java
// volatile 规则 + 传递性
int a = 0;
volatile boolean flag = false;

// 线程 A
a = 42;          // ① 普通写
flag = true;     // ② volatile 写

// 线程 B
if (flag) {      // ③ volatile 读
    print(a);    // ④ → 一定能看到 a = 42
}

// 推导：
// ① happens-before ②（程序顺序规则）
// ② happens-before ③（volatile 规则：写 hb 后续读）
// ③ happens-before ④（程序顺序规则）
// 传递性：① happens-before ④
// 所以 ④ 一定能看到 ① 的结果 → a = 42
```

**这就是 volatile 除了保证自身可见性之外的"附带效果"——volatile 写之前的所有操作，对 volatile 读之后的所有操作都可见。**

### 五、synchronized 的内存语义

```java
synchronized (lock) {
    // 临界区代码
}
```

**synchronized 在内存层面做了什么**：

```
进入 synchronized（lock）：
  ① 清空工作内存中共享变量的缓存
  ② 从主内存重新读取最新值
  → 相当于一个"读屏障"

退出 synchronized（unlock）：
  ① 把工作内存中修改的共享变量刷回主内存
  ② 释放锁
  → 相当于一个"写屏障"
```

**所以 synchronized 保证三件事**：

| 特性 | 怎么保证的 |
|------|-----------|
| **原子性** | 同一时刻只有一个线程能进入临界区 |
| **可见性** | 进入时从主内存读，退出时刷回主内存 |
| **有序性** | 临界区内的操作不会和临界区外的操作重排序 |

### 六、synchronized 底层原理：对象头、Monitor、锁升级

**类别**：Java 并发 / synchronized / 底层机制

#### 6.1 Java 对象头（Object Header）

```
每个 Java 对象在内存中的布局：

  ┌──────────────────────────────────────┐
  │          对象头（Object Header）        │
  │  ┌──────────────────────────────┐    │
  │  │   Mark Word（标记字段）        │    │  ← synchronized 的核心，存锁状态
  │  │   64 位虚拟机中占 8 字节       │    │
  │  ├──────────────────────────────┤    │
  │  │   Klass Pointer（类型指针）    │    │  ← 指向类的元数据（知道这个对象是什么类）
  │  │   4 字节（压缩指针）/ 8 字节    │    │
  │  ├──────────────────────────────┤    │
  │  │   Array Length（数组长度）      │    │  ← 仅数组对象有
  │  └──────────────────────────────┘    │
  ├──────────────────────────────────────┤
  │          实例数据（Instance Data）      │  ← 对象的字段值
  ├──────────────────────────────────────┤
  │          对齐填充（Padding）            │  ← 凑齐 8 字节整数倍
  └──────────────────────────────────────┘
```

```
Mark Word 在不同锁状态下的内容（64 位 JVM）：

┌──────────────────────────────────────────────────────────────┐
│                          Mark Word (64 bit)                    │
├────────────────┬───────────┬─────────┬───────────────────────┤
│ 锁状态          │ 内容                                        │ 标志位   │
├────────────────┼───────────────────────────────────────┼──────┤
│ 无锁            │ hashcode(31) | age(4) | biased(1)=0  │ 01   │
│ 偏向锁          │ threadID(54) | epoch(2) | age(4) | 1  │ 01   │
│ 轻量级锁        │ 指向栈中锁记录（Lock Record）的指针     │ 00   │
│ 重量级锁        │ 指向 Monitor 对象的指针                 │ 10   │
│ GC 标记         │ 空                                     │ 11   │
└────────────────┴───────────────────────────────────────┴──────┘

关键点：
  - 锁信息就存在对象头的 Mark Word 里
  - synchronized 锁的是对象，本质上就是改这个对象的 Mark Word
  - 不同锁状态下 Mark Word 存的东西完全不同
```

#### 6.2 Monitor（监视器 / 管程）

```
Monitor 是 JVM 层面的同步机制，每个 Java 对象都可以关联一个 Monitor。

当 synchronized 升级为重量级锁时，对象的 Mark Word 指向一个 Monitor 对象：

  ┌──────────────── Monitor（ObjectMonitor）──────────────────┐
  │                                                           │
  │   _owner：当前持有锁的线程                                  │
  │                                                           │
  │   _EntryList：阻塞等待获取锁的线程队列（竞争锁的线程在这排队） │
  │                                                           │
  │   _WaitSet：调用了 wait() 的线程队列（等待被 notify 唤醒）    │
  │                                                           │
  │   _count：重入次数（同一线程多次 synchronized 嵌套）          │
  │                                                           │
  │   _recursions：重入计数                                     │
  │                                                           │
  └───────────────────────────────────────────────────────────┘
```

```
Monitor 的工作流程：

  线程 A                          Monitor                     线程 B
    │                               │                           │
    │── monitorenter ──────────→    │                           │
    │                          _owner = A                       │
    │                          _count = 1                       │
    │                               │                           │
    │   （线程 A 执行同步代码）        │                           │
    │                               │   ←── monitorenter ──── │
    │                               │   _owner != null          │
    │                               │   B 进入 _EntryList 阻塞   │
    │                               │                           │
    │── wait() ────────────────→    │                           │
    │   A 释放锁                     │                           │
    │   A 进入 _WaitSet              │                           │
    │                          _owner = null                    │
    │                               │   从 _EntryList 唤醒 B     │
    │                          _owner = B                       │
    │                               │                           │
    │                               │   B 执行同步代码             │
    │                               │                           │
    │                               │── notify() ─→ 唤醒 A      │
    │   A 从 _WaitSet 移到            │                           │
    │   _EntryList 重新竞争锁         │                           │
    │                               │── monitorexit ──────→     │
    │                          _owner = null                    │
    │                          _count = 0                       │
    │                               │                           │
    │── 重新竞争锁 ────────────→     │                           │
    │                          _owner = A                       │
```

#### 6.3 字节码层面：monitorenter / monitorexit

```java
// 同步代码块
synchronized (obj) {
    count++;
}
```

```
编译后的字节码：

  monitorenter          // 进入 Monitor
    aload_1             // 加载 count
    iconst_1
    iadd
    astore_1            // count++
  monitorexit           // 退出 Monitor（正常退出）
  goto end
  monitorexit           // 退出 Monitor（异常退出，确保锁一定释放）
  athrow
  end:

关键：
  - 编译器会自动生成两个 monitorexit → 保证即使抛异常也能释放锁
  - 这也是为什么 synchronized 不需要手动释放锁（对比 Lock 的 try-finally）
```

```java
// 同步方法
public synchronized void method() {
    count++;
}
```

```
同步方法不用 monitorenter/monitorexit，而是在方法的 access_flags 上加 ACC_SYNCHRONIZED 标志：

  flags: ACC_PUBLIC, ACC_SYNCHRONIZED

  JVM 在方法调用时检查这个标志：
    有 ACC_SYNCHRONIZED → 自动获取 Monitor → 方法结束自动释放
```

#### 6.4 锁升级（锁膨胀）— 无锁 → 偏向锁 → 轻量级锁 → 重量级锁

```
为什么要锁升级？

  重量级锁（Monitor）依赖操作系统 Mutex Lock → 需要用户态/内核态切换 → 很重
  但实际场景中：
    - 大多数时候只有一个线程在用锁 → 偏向锁
    - 少数时候有两个线程交替用锁（无真正竞争）→ 轻量级锁
    - 真正激烈竞争时才需要 → 重量级锁

  JDK 6 引入锁升级，根据竞争程度自动选择最轻量的锁 → 性能优化
```

##### 阶段 1：偏向锁（Biased Locking）

```
适用场景：只有一个线程反复进入同步块（最常见的情况）

原理：
  第一次获取锁时：
    通过 CAS 把线程 ID 写入 Mark Word → 标记为偏向锁
  后续同一线程再进入：
    只需检查 Mark Word 中的线程 ID 是不是自己 → 是就直接进入，无需任何同步操作

  Mark Word：[线程 ID | epoch | age | 1 | 01]
                                      ↑ biased=1 表示偏向锁
                                         ↑ 锁标志 01

  偏向锁几乎零开销 → 连 CAS 都省了（第一次之后）

撤销偏向锁：
  当另一个线程尝试获取锁 → 偏向锁不够用了 → 需要撤销
  撤销过程：
    ① 等到安全点（Safepoint，类似 GC 的 STW）
    ② 暂停持有偏向锁的线程
    ③ 检查该线程是否还在同步块内：
       - 不在 → 把 Mark Word 置为无锁 → 新线程可以重新偏向
       - 还在 → 升级为轻量级锁

  注意：
    JDK 15 默认关闭了偏向锁（-XX:-UseBiasedLocking）
    因为撤销偏向锁需要 STW，在高并发场景反而是负优化
```

##### 阶段 2：轻量级锁（Lightweight Lock）

```
适用场景：多个线程交替进入同步块，但几乎没有同时竞争

原理：
  ① 线程在自己的栈帧中创建 Lock Record（锁记录）
  ② 把 Mark Word 拷贝到 Lock Record 中（Displaced Mark Word）
  ③ 通过 CAS 尝试把 Mark Word 替换为指向 Lock Record 的指针

  成功 → 获取轻量级锁
  失败 → 说明有竞争

  Mark Word：[指向 Lock Record 的指针 | 00]
                                       ↑ 锁标志 00

  解锁：CAS 把 Displaced Mark Word 替换回 Mark Word

  ┌──────────────────────────────────────────────┐
  │  线程栈帧                                      │
  │  ┌─────────────────┐                          │
  │  │  Lock Record     │                          │
  │  │  ┌─────────────┐ │     ┌──────────────┐    │
  │  │  │ Displaced   │ │ ←── │ 对象 Mark Word │    │
  │  │  │ Mark Word   │ │     │ → 指向 LR 的  │    │
  │  │  │ (原始的MW)   │ │     │    指针       │    │
  │  │  ├─────────────┤ │     └──────────────┘    │
  │  │  │ obj 引用     │─┘→ 指向锁对象              │
  │  │  └─────────────┘                            │
  │  └─────────────────┘                          │
  └──────────────────────────────────────────────┘
```

```
轻量级锁的自旋（Spin）：

  CAS 失败（有竞争）→ 不立即阻塞，先自旋等一会儿
  因为持有锁的线程可能很快就释放了

  自旋就是空转 CPU（while 循环不停 CAS 尝试获取锁）

  JDK 6 引入自适应自旋（Adaptive Spinning）：
    - 上次自旋成功获取过锁 → 这次多转几圈
    - 上次自旋失败了 → 这次少转或不转
    JVM 自动调整，不需要手动设

  自旋超过阈值仍未获取到 → 升级为重量级锁
```

##### 阶段 3：重量级锁（Heavyweight Lock）

```
适用场景：真正的多线程激烈竞争

原理：
  Mark Word 指向一个 ObjectMonitor 对象（就是前面讲的 Monitor）

  Mark Word：[指向 Monitor 的指针 | 10]
                                    ↑ 锁标志 10

  竞争失败的线程：
    不再自旋（避免浪费 CPU）
    → 进入 Monitor 的 _EntryList → 操作系统层面阻塞（park）
    → 等持锁线程释放后被唤醒（unpark）

  代价：
    涉及用户态/内核态切换 → 比轻量级锁重很多
    但在高竞争下比自旋更合理（自旋浪费 CPU）
```

#### 6.5 锁升级全流程图

```
                    ┌──────────┐
                    │   无锁    │
                    │ (01, 0)  │
                    └────┬─────┘
                         │ 第一个线程进入 synchronized
                         ↓
                    ┌──────────┐
                    │  偏向锁   │  CAS 写入线程 ID 到 Mark Word
                    │ (01, 1)  │  后续同一线程直接进入（零开销）
                    └────┬─────┘
                         │ 另一个线程尝试获取 → 撤销偏向锁
                         ↓
                    ┌──────────┐
                    │ 轻量级锁  │  CAS 替换 Mark Word → Lock Record
                    │   (00)   │  竞争时自旋等待
                    └────┬─────┘
                         │ 自旋超过阈值 / 竞争激烈
                         ↓
                    ┌──────────┐
                    │ 重量级锁  │  Mark Word → Monitor 对象
                    │   (10)   │  竞争失败的线程 OS 级阻塞
                    └──────────┘

重要：锁只能升级不能降级（偏向→轻量→重量，单向不可逆）
```

#### 6.6 synchronized 的可重入性

```java
synchronized (obj) {           // 第 1 次获取锁 → _count = 1
    synchronized (obj) {       // 同一个线程再次获取同一把锁 → _count = 2
        synchronized (obj) {   // → _count = 3
            // ...
        }                      // → _count = 2
    }                          // → _count = 1
}                              // → _count = 0 → 释放锁
```

```
可重入的实现原理：
  Monitor 的 _owner 记录当前持锁线程
  如果 _owner == 当前线程 → 不需要重新获取锁，_count++
  每次退出一层 synchronized → _count--
  _count 减到 0 → 真正释放锁（_owner = null）

  如果不可重入会怎样？
  同一个线程嵌套 synchronized → 第二次获取时发现锁被占（被自己占的）
  → 自己等自己释放 → 死锁
```

#### 6.7 面试话术

> **synchronized 底层原理**："synchronized 锁的是对象，核心是对象头里的 Mark Word。Mark Word 在不同锁状态下存不同信息——无锁存 hashcode、偏向锁存线程 ID、轻量级锁存指向栈中 Lock Record 的指针、重量级锁存指向 Monitor 对象的指针。"
>
> **Monitor 是什么**："Monitor 是 JVM 层面的同步机制，每个被 synchronized 锁住的对象在升级为重量级锁后会关联一个 ObjectMonitor。Monitor 内部有三个核心结构：_owner 记录持锁线程，_EntryList 存放竞争锁被阻塞的线程，_WaitSet 存放调用了 wait() 的线程。字节码层面对应 monitorenter 和 monitorexit 指令。"
>
> **锁升级过程**："JDK 6 引入了锁升级优化，从无锁 → 偏向锁 → 轻量级锁 → 重量级锁，只升不降。偏向锁针对只有一个线程的场景，把线程 ID 写入 Mark Word，后续同一线程直接进入几乎零开销。当第二个线程来竞争时撤销偏向升级为轻量级锁，通过 CAS + 自旋尝试获取。自旋超过阈值仍未获取到就升级为重量级锁，Mark Word 指向 Monitor，竞争失败的线程在操作系统级别阻塞。这样大部分无竞争的场景避免了重量级锁的用户态/内核态切换开销。"

### 七、volatile vs synchronized
|---|---|---|
| 原子性 | ❌ 不保证 | ✅ 保证 |
| 可见性 | ✅ 保证 | ✅ 保证 |
| 有序性 | ✅ 禁止重排序 | ✅ 临界区有序 |
| 阻塞 | ❌ 不阻塞 | ✅ 会阻塞（拿不到锁就等） |
| 适用 | 一写多读的简单标志 | 需要原子性的复合操作 |
| 性能 | 高（无锁） | 较低（有锁竞争） |
| 粒度 | 单个变量 | 代码块 / 方法 |

### 七、面试回答模板

> "JMM 定义了多线程环境下共享变量的可见性、有序性规则。核心问题是每个线程有自己的工作内存（CPU 缓存），修改不一定能被其他线程看到，而且编译器/CPU 会重排序指令。
>
> **volatile** 保证可见性（读写都走主内存）和有序性（通过内存屏障禁止重排序），但不保证原子性。底层是在 volatile 写前插 StoreStore、写后插 StoreLoad 屏障，读后插 LoadLoad + LoadStore 屏障。典型场景是状态标志位和 DCL 单例。
>
> **synchronized** 保证原子性 + 可见性 + 有序性。进入时清空缓存从主内存读，退出时刷回主内存。比 volatile 重但能力更全。
>
> **happens-before** 是 JMM 的偏序关系：A happens-before B 就保证 A 的结果对 B 可见。8 条规则中最常用的是程序顺序规则、volatile 规则（写 hb 后续读）、锁规则（unlock hb 后续 lock）、传递性。volatile 的'附带效果'就是通过传递性实现的——volatile 写之前的所有操作，对 volatile 读之后的所有操作都可见。"

## AQS（AbstractQueuedSynchronizer）

**类别**：Java 并发 / JUC / 锁框架 / 底层原理

### 一、AQS 是什么

AQS 是 JUC 中**几乎所有锁和同步工具的底层骨架**。它不是一个锁，而是一个**抽象框架**，提供了排队、阻塞、唤醒的通用机制，具体的加锁/释放逻辑由子类实现。

```
基于 AQS 实现的工具：
  ReentrantLock        → 独占锁
  ReentrantReadWriteLock → 读写锁
  CountDownLatch       → 倒计数器
  Semaphore            → 信号量
  CyclicBarrier        → 栅栏（间接依赖）

AQS 是这些工具的"发动机"，它们只是不同的"车壳"
```

### 二、AQS 的核心结构

AQS 内部就两样东西：**一个 state 变量** + **一个 CLH 队列**。

```java
public abstract class AbstractQueuedSynchronizer {
    private volatile int state;       // 同步状态（核心）
    private transient volatile Node head;  // 队列头
    private transient volatile Node tail;  // 队列尾
}
```

#### state —— 同步状态

```
state 的含义由子类定义：

ReentrantLock：
  state = 0 → 锁空闲
  state = 1 → 被某个线程持有
  state > 1 → 重入了 state 次

Semaphore：
  state = 剩余许可数

CountDownLatch：
  state = 剩余计数
```

state 通过 **CAS** 修改，保证原子性：

```java
compareAndSetState(expect, update)  // CAS 修改 state
getState()                          // 读 state
setState(newState)                  // 写 state（在持有锁时用）
```

#### CLH 队列 —— 等待队列

当线程拿不到锁（修改 state 失败）时，就被包装成 **Node** 节点放入一个**双向链表队列**（CLH 变体）排队等待。

```
CLH 队列结构（双向链表）：

  head                                          tail
   ↓                                             ↓
┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐
│ Node │ ←→ │ Node │ ←→ │ Node │ ←→ │ Node │
│(哨兵) │    │线程 A │    │线程 B │    │线程 C │
│      │    │WAITING│    │WAITING│    │WAITING│
└──────┘    └──────┘    └──────┘    └──────┘

head 是哨兵节点（不关联线程），head.next 是下一个要被唤醒的线程
```

Node 的关键字段：

```java
static final class Node {
    volatile int waitStatus;     // 节点状态
    volatile Node prev;          // 前驱
    volatile Node next;          // 后继
    volatile Thread thread;      // 关联的线程
    Node nextWaiter;             // 条件队列中的后继（Condition 用）
}

// waitStatus 取值：
//   0：初始状态
//   SIGNAL(-1)：后继节点需要被唤醒（最常见）
//   CANCELLED(1)：线程已取消
//   CONDITION(-2)：在条件队列中等待
//   PROPAGATE(-3)：共享模式下传播唤醒
```

### 三、AQS 的两种模式

#### 独占模式（Exclusive）—— 一次只有一个线程能获取

```
代表：ReentrantLock

子类需要实现：
  tryAcquire(int arg)     尝试获取锁（CAS 修改 state）
  tryRelease(int arg)     尝试释放锁
```

#### 共享模式（Shared）—— 多个线程可以同时获取

```
代表：Semaphore、CountDownLatch、ReadWriteLock 的读锁

子类需要实现：
  tryAcquireShared(int arg)    尝试共享获取（返回 >= 0 表示成功）
  tryReleaseShared(int arg)    尝试共享释放
```

### 四、独占模式加锁流程（以 ReentrantLock 为例）

```java
// 调用 lock.lock() 最终走到 AQS 的 acquire()
public final void acquire(int arg) {
    if (!tryAcquire(arg) &&                    // ① 尝试获取锁
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg))  // ② 失败就入队等待
        selfInterrupt();
}
```

#### 完整流程

```
线程调用 lock()：

第 1 步：tryAcquire() —— 尝试 CAS 获取锁
  state == 0 → CAS(0, 1) 成功 → 设置当前线程为锁持有者 → 拿到锁，返回
  state > 0 且是当前线程 → state + 1（重入）→ 拿到锁，返回
  否则 → 获取失败，进入第 2 步

第 2 步：addWaiter() —— 把当前线程包装成 Node，CAS 加入队列尾部
  创建 Node(当前线程, EXCLUSIVE)
  CAS 设置为 tail → 入队成功
  如果 CAS 失败（竞争）→ enq() 自旋入队

第 3 步：acquireQueued() —— 在队列中自旋 + 阻塞等待
  for (;;) {
      如果前驱是 head → 再试一次 tryAcquire()
        成功 → 把自己设为 head，拿到锁，返回
        失败 → 继续下面

      检查前驱的 waitStatus：
        设为 SIGNAL(-1)（告诉前驱"释放锁时叫醒我"）
        → LockSupport.park() 阻塞当前线程
        → 等待被唤醒后回到循环开头再试
  }
```

```
图示：

线程 A 持有锁（state=1）
线程 B 来了：
  ① tryAcquire → state=1 失败
  ② addWaiter → B 加入队列尾部
  ③ acquireQueued → B 发现前驱不是 head 或 tryAcquire 失败
     → park() 阻塞

  head ←→ [B(WAITING)] = tail

线程 C 也来了：
  同样失败 → 加入队列

  head ←→ [B(WAITING)] ←→ [C(WAITING)] = tail
```

### 五、独占模式释放锁流程

```java
public final boolean release(int arg) {
    if (tryRelease(arg)) {          // ① 尝试释放（state - 1）
        Node h = head;
        if (h != null && h.waitStatus != 0)
            unparkSuccessor(h);     // ② 唤醒队列中下一个线程
        return true;
    }
    return false;
}
```

```
线程 A 调用 unlock()：

第 1 步：tryRelease()
  state - 1
  如果 state == 0 → 锁完全释放，清除锁持有者
  如果 state > 0 → 还有重入没释放完，返回 false

第 2 步：unparkSuccessor()
  找到 head 的后继节点（线程 B）
  LockSupport.unpark(B) → B 被唤醒
  B 回到 acquireQueued 循环 → tryAcquire 成功 → B 拿到锁
  B 把自己设为新的 head
```

```
释放前：
  head ←→ [B(WAITING)] ←→ [C(WAITING)]
  A 持有锁，state=1

释放后：
  [B=new head] ←→ [C(WAITING)]
  B 持有锁，state=1
```

### 六、共享模式流程（以 Semaphore 为例）

```
Semaphore(3)：初始 state = 3

线程 A acquire()：state CAS 3→2 成功 → 拿到许可
线程 B acquire()：state CAS 2→1 成功 → 拿到许可
线程 C acquire()：state CAS 1→0 成功 → 拿到许可
线程 D acquire()：state=0 失败 → 入队 park() 等待

线程 A release()：state CAS 0→1 → 唤醒队列中的 D
  D 被唤醒 → tryAcquireShared → state CAS 1→0 成功 → 拿到许可

共享模式的区别：
  释放时可能唤醒多个线程（如果 state 够用）
  用 doReleaseShared() 传播唤醒
```

### 七、Condition 条件队列

AQS 内部除了 CLH 同步队列，还有一个**条件队列（Condition Queue）**，用来实现 `Condition.await()` 和 `signal()`。

```
同步队列（CLH）：等待获取锁的线程排队
条件队列（Condition）：调用 await() 后释放锁并等待条件的线程排队

两个队列之间可以转移：
  await()：线程从同步队列 → 条件队列（释放锁，挂起）
  signal()：线程从条件队列 → 同步队列（重新排队竞争锁）
```

```
await() 流程：
  ① 把当前线程包装成 Node 加入条件队列
  ② 完全释放锁（state → 0，即使重入了也全部释放）
  ③ park() 阻塞

signal() 流程：
  ① 把条件队列的第一个 Node 转移到同步队列尾部
  ② unpark() 唤醒该线程
  ③ 该线程醒来后在同步队列中重新竞争锁

图示：
  同步队列：head ←→ [A] ←→ [B]
  条件队列：[C] → [D] → null

  signal() → C 从条件队列移到同步队列：
  同步队列：head ←→ [A] ←→ [B] ←→ [C]
  条件队列：[D] → null
```

### 八、公平锁 vs 非公平锁在 AQS 中的区别

```java
// 非公平锁的 tryAcquire（ReentrantLock 默认）
// 上来就直接 CAS 抢锁，不管队列里有没有人排队
if (state == 0) {
    if (compareAndSetState(0, 1)) {  // 直接抢
        setExclusiveOwnerThread(current);
        return true;
    }
}

// 公平锁的 tryAcquire
// 先检查队列里有没有人排在我前面
if (state == 0) {
    if (!hasQueuedPredecessors() &&  // 队列里没人排在我前面
        compareAndSetState(0, 1)) {
        setExclusiveOwnerThread(current);
        return true;
    }
}
```

```
非公平锁：新来的线程可以插队，直接 CAS 抢锁
  优点：吞吐量高（减少线程切换）
  缺点：可能导致队列中的线程饥饿

公平锁：新来的线程必须排队，先到先得
  优点：不会饥饿
  缺点：吞吐量低（每次都要检查队列 + 线程切换）

区别就一行代码：hasQueuedPredecessors()
```

### 九、AQS 核心设计总结

```
AQS = volatile state + CAS + CLH 队列 + LockSupport.park/unpark

  state：     用 volatile 保证可见性，用 CAS 保证原子修改
  CLH 队列：  双向链表，存放等待锁的线程
  park/unpark：线程的阻塞和唤醒
  模板方法模式：AQS 定义流程（acquire/release），子类实现 tryAcquire/tryRelease

  子类只需关心"state 怎么变"，排队、阻塞、唤醒全由 AQS 搞定
```

### 十、面试回答模板

> "AQS 是 JUC 中锁和同步工具的底层框架，核心是一个 **volatile int state** 和一个 **CLH 双向链表队列**。
>
> **加锁流程**：线程先 CAS 尝试修改 state（tryAcquire），成功就拿到锁；失败就包装成 Node 加入 CLH 队列尾部，然后 `LockSupport.park()` 阻塞。队列中的线程只有前驱是 head 时才有资格尝试获取锁。
>
> **释放流程**：修改 state（tryRelease），然后 `LockSupport.unpark()` 唤醒队列中 head 的后继节点，被唤醒的线程回到循环重新 tryAcquire。
>
> **两种模式**：独占模式（ReentrantLock）一次只能一个线程持有，共享模式（Semaphore、CountDownLatch）允许多个线程同时获取。
>
> **公平 vs 非公平**：区别就在 tryAcquire 里是否调用 `hasQueuedPredecessors()` 检查队列——非公平锁直接 CAS 抢（可插队），公平锁先查有没有人排队。
>
> **Condition**：AQS 还维护了条件队列，`await()` 把线程从同步队列转移到条件队列并释放锁，`signal()` 把线程从条件队列转回同步队列重新竞争锁。
>
> 本质就是**模板方法模式**——AQS 定义了排队、阻塞、唤醒的通用流程，子类只需要实现 tryAcquire/tryRelease 告诉框架'state 怎么变'就行了。"

## Java 线程池

**类别**：Java 并发 / JUC / 线程池 / ThreadPoolExecutor

### 一、为什么需要线程池

```
不用线程池：
  每来一个任务就 new Thread() → 执行完销毁
  问题：
    ① 线程创建和销毁有开销（内核态操作）
    ② 大量任务 → 大量线程 → 内存耗尽 / CPU 频繁切换
    ③ 线程数量不可控

用线程池：
  提前创建好一批线程 → 复用 → 任务来了直接执行，不用反复创建销毁
  好处：
    ① 降低资源消耗（复用线程）
    ② 提高响应速度（不用等线程创建）
    ③ 线程数量可控（防止资源耗尽）
```

### 二、ThreadPoolExecutor 的 7 个参数

```java
public ThreadPoolExecutor(
    int corePoolSize,                  // 核心线程数
    int maximumPoolSize,               // 最大线程数
    long keepAliveTime,                // 非核心线程空闲存活时间
    TimeUnit unit,                     // 存活时间单位
    BlockingQueue<Runnable> workQueue,  // 任务队列
    ThreadFactory threadFactory,       // 线程工厂
    RejectedExecutionHandler handler   // 拒绝策略
)
```

#### 逐个解释

| 参数 | 含义 | 类比 |
|------|------|------|
| **corePoolSize** | 核心线程数，即使空闲也不会销毁（除非设了 allowCoreThreadTimeOut） | 公司正式员工 |
| **maximumPoolSize** | 最大线程数 = 核心 + 非核心 | 正式员工 + 临时工的总上限 |
| **keepAliveTime** | 非核心线程空闲多久后被销毁 | 临时工没活干多久就辞退 |
| **unit** | keepAliveTime 的时间单位 | 秒/毫秒/分钟 |
| **workQueue** | 任务等待队列 | 排队等候区 |
| **threadFactory** | 创建线程的工厂（可以自定义线程名、是否守护线程等） | HR 部门 |
| **handler** | 队列满 + 线程数达到最大时的拒绝策略 | 排队区也满了怎么办 |

### 三、任务执行流程（核心！面试必问）

```
提交一个任务 execute(task)：

  ① 当前线程数 < corePoolSize？
     → YES：创建新的核心线程执行任务（即使其他核心线程是空闲的）
     → NO：进入 ②

  ② 任务队列 workQueue 是否已满？
     → 没满：把任务放入队列排队等待
     → 满了：进入 ③

  ③ 当前线程数 < maximumPoolSize？
     → YES：创建新的非核心线程执行任务
     → NO：进入 ④

  ④ 执行拒绝策略 handler.rejectedExecution()
```

```
流程图：

                      提交任务
                        │
                ┌───────▼───────┐
                │ 线程数 < 核心数？│
                └───┬───────┬───┘
                   YES      NO
                    │       │
              创建核心线程  ┌──▼──────────┐
              执行任务     │ 队列是否已满？ │
                          └──┬───────┬──┘
                           没满      满了
                            │       │
                       放入队列  ┌───▼───────────┐
                       排队    │ 线程数 < 最大数？ │
                              └──┬──────────┬──┘
                               YES          NO
                                │           │
                          创建非核心线程   执行拒绝策略
                          执行任务
```

**注意顺序**：先核心线程 → 再队列 → 再非核心线程 → 最后拒绝。不是先填满线程再放队列！

### 四、任务队列类型

| 队列类型 | 特点 | 适用场景 |
|---------|------|---------|
| **LinkedBlockingQueue** | 无界队列（默认 Integer.MAX_VALUE） | FixedThreadPool、SingleThreadPool 用的。队列永远不满 → 永远不会创建非核心线程 → maximumPoolSize 无效 |
| **ArrayBlockingQueue** | 有界队列（指定大小） | 生产中推荐。可以控制内存，队列满了会触发创建非核心线程和拒绝策略 |
| **SynchronousQueue** | 不存储任务，直接交给线程 | CachedThreadPool 用的。来一个任务就必须有线程接，没有就创建新线程 |
| **PriorityBlockingQueue** | 按优先级排序 | 需要优先级调度的场景 |
| **DelayQueue** | 延迟执行 | ScheduledThreadPool 用的 |

### 五、四种拒绝策略

当队列满了 + 线程数达到 maximumPoolSize 时，新任务怎么处理：

| 策略 | 行为 | 适用 |
|------|------|------|
| **AbortPolicy**（默认） | 直接抛 RejectedExecutionException | 需要感知任务丢失的场景 |
| **CallerRunsPolicy** | 让提交任务的线程自己执行 | 不想丢任务，且能接受提交线程被阻塞 |
| **DiscardPolicy** | 静默丢弃，不抛异常 | 允许丢任务且不关心的场景 |
| **DiscardOldestPolicy** | 丢弃队列中最老的任务，然后重试提交 | 只关心最新任务的场景 |

```java
// 自定义拒绝策略（生产中常用）
new RejectedExecutionHandler() {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        // 记录日志、持久化到 DB、发告警等
        log.warn("任务被拒绝: {}", r.toString());
    }
}
```

### 六、Executors 预定义的线程池（以及为什么不推荐用）

```java
// 1. FixedThreadPool —— 固定大小
Executors.newFixedThreadPool(10);
// corePoolSize = maximumPoolSize = 10
// 队列：LinkedBlockingQueue（无界）
// 风险：队列无界 → 任务堆积 → OOM

// 2. SingleThreadExecutor —— 单线程
Executors.newSingleThreadExecutor();
// corePoolSize = maximumPoolSize = 1
// 队列：LinkedBlockingQueue（无界）
// 风险：同上，队列无界 → OOM

// 3. CachedThreadPool —— 可缓存（弹性伸缩）
Executors.newCachedThreadPool();
// corePoolSize = 0, maximumPoolSize = Integer.MAX_VALUE
// 队列：SynchronousQueue（不存储）
// 风险：maximumPoolSize 无界 → 线程数暴增 → OOM

// 4. ScheduledThreadPool —— 定时任务
Executors.newScheduledThreadPool(5);
// 支持延迟执行和周期执行
// 队列：DelayedWorkQueue
// 风险：队列无界 → OOM
```

**阿里规范要求不用 Executors 创建线程池，必须用 ThreadPoolExecutor 手动指定参数**：

```java
// 生产推荐写法
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10,                                    // 核心线程数
    20,                                    // 最大线程数
    60, TimeUnit.SECONDS,                  // 非核心线程 60 秒空闲销毁
    new ArrayBlockingQueue<>(200),         // 有界队列，容量 200
    new ThreadFactoryBuilder()
        .setNameFormat("biz-pool-%d")      // 自定义线程名（方便排查问题）
        .build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略：调用方自己执行
);
```

### 七、线程数怎么设置

#### CPU 密集型任务

```
特点：计算为主，几乎不阻塞（如加密、压缩、排序）
瓶颈：CPU 算力

推荐：核心线程数 = CPU 核数 + 1
      +1 是为了在某个线程偶尔阻塞时还有一个线程能利用 CPU
      maximumPoolSize 和 corePoolSize 相同即可
```

#### IO 密集型任务

```
特点：大量 IO 等待（如 DB 查询、HTTP 调用、文件读写）
瓶颈：IO 等待时间，CPU 大部分时间是空闲的

推荐：核心线程数 = CPU 核数 × 2（经验值）
      或更精确的公式：
      线程数 = CPU 核数 × (1 + IO 等待时间 / CPU 计算时间)

      例：CPU 核数 = 8，IO 等待 80ms，CPU 计算 20ms
      线程数 = 8 × (1 + 80/20) = 8 × 5 = 40
```

#### 实际生产

```
上面都是理论值，实际要通过压测调整：
  1. 先用经验值设一个初始值
  2. 压测观察 CPU 利用率、线程池队列长度、响应时间
  3. CPU 利用率 70%~80% 为最佳
  4. 队列经常堆积 → 增加线程数或优化任务执行时间
  5. CPU 经常 100% → 减少线程数
```

### 八、线程池的生命周期（5 种状态）

```java
// ThreadPoolExecutor 用一个 int 的高 3 位存状态，低 29 位存线程数
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
```

```
RUNNING（运行中）
  → 接受新任务，处理队列中的任务
  ↓ 调用 shutdown()
SHUTDOWN（关闭中）
  → 不接受新任务，但继续处理队列中剩余的任务
  ↓ 队列空了且线程都终止
TIDYING（整理中）
  → 所有任务完成，即将调用 terminated()
  ↓
TERMINATED（终止）
  → terminated() 执行完毕，线程池彻底死亡

另一条路：
RUNNING → 调用 shutdownNow() → STOP
  → 不接受新任务，中断正在执行的任务，丢弃队列中的任务
  → 线程都终止后 → TIDYING → TERMINATED
```

```java
// 优雅关闭线程池的标准写法
executor.shutdown();                          // 不再接受新任务
try {
    if (!executor.awaitTermination(60, TimeUnit.SECONDS)) {  // 等 60 秒
        executor.shutdownNow();               // 超时强制关闭
        if (!executor.awaitTermination(60, TimeUnit.SECONDS)) {
            log.error("线程池未能正常关闭");
        }
    }
} catch (InterruptedException e) {
    executor.shutdownNow();
    Thread.currentThread().interrupt();
}
```

### 九、execute() vs submit()

```java
// execute()：提交 Runnable，没有返回值，异常直接抛出
executor.execute(() -> doSomething());

// submit()：提交 Callable/Runnable，返回 Future，异常被封装在 Future 里
Future<String> future = executor.submit(() -> {
    return doSomethingWithResult();
});
String result = future.get();  // 阻塞获取结果
```

| | execute() | submit() |
|---|---|---|
| 参数 | Runnable | Runnable / Callable |
| 返回值 | void | Future |
| 异常处理 | 直接抛出（线程的 UncaughtExceptionHandler 捕获） | 封装在 Future 中，调用 get() 时才抛出 |

**submit 的坑**：如果不调用 `future.get()`，异常会被吞掉，你完全不知道任务失败了。

```java
// 解决方案 1：用 execute 替代 submit（不需要返回值时）
executor.execute(() -> {
    try { doSomething(); }
    catch (Exception e) { log.error("任务异常", e); }
});

// 解决方案 2：submit 后检查 Future
Future<?> future = executor.submit(task);
try { future.get(); }
catch (ExecutionException e) { log.error("任务异常", e.getCause()); }
```

### 十、线程池的监控

```java
ThreadPoolExecutor pool = ...;

pool.getPoolSize();           // 当前线程数
pool.getActiveCount();        // 正在执行任务的线程数
pool.getCorePoolSize();       // 核心线程数
pool.getMaximumPoolSize();    // 最大线程数
pool.getQueue().size();       // 队列中等待的任务数
pool.getCompletedTaskCount(); // 已完成的任务总数
pool.getTaskCount();          // 已提交的任务总数（完成 + 执行中 + 队列中）
pool.getLargestPoolSize();    // 历史最大线程数
```

生产中应该把这些指标接入监控系统（Prometheus + Grafana），设置告警：
- 队列长度持续增长 → 任务处理不过来
- 活跃线程数 == 最大线程数 → 线程池打满了
- 拒绝任务数增加 → 需要扩容或优化

### 十一、面试回答模板

> "线程池核心是 **ThreadPoolExecutor**，7 个参数：核心线程数、最大线程数、非核心线程存活时间、时间单位、任务队列、线程工厂、拒绝策略。
>
> **执行流程**：任务来了先看核心线程数够不够 → 不够就创建核心线程执行；核心线程满了 → 放入任务队列排队；队列也满了 → 创建非核心线程执行；线程数到了最大值且队列也满了 → 执行拒绝策略。注意是**先队列后非核心线程**，不是先创建线程再放队列。
>
> **线程数设置**：CPU 密集型用 CPU 核数 + 1，IO 密集型用 CPU 核数 × (1 + IO 等待时间 / CPU 计算时间)，实际通过压测调整。
>
> **为什么不用 Executors**：FixedThreadPool 和 SingleThreadPool 用无界队列会 OOM，CachedThreadPool 线程数无上限也会 OOM。阿里规范要求用 ThreadPoolExecutor 手动指定参数。
>
> **关闭**：`shutdown()` 优雅关闭（不接新任务但处理完剩余的），`shutdownNow()` 强制关闭（中断执行中的任务）。
>
> **execute vs submit**：execute 没有返回值且异常直接抛出，submit 返回 Future 但异常被封装，不调 get 就会吞掉异常。"
