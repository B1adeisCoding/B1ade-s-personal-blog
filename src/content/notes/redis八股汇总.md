## 缓存与数据库一致性的解决方案

**类别**：Redis / 缓存 / 数据一致性

### 一、先明确：为什么会不一致

缓存和数据库是两个独立的存储，任何"先写 A 再写 B"的操作都存在中间状态——A 写成功了但 B 还没写，此时如果有读请求进来，就会读到不一致的数据。所以问题的本质是：**没有分布式事务保证两者的原子性**。

### 二、常见方案（从简单到复杂）

#### 方案 1：Cache Aside Pattern（旁路缓存，最常用）

**写流程**：先更新 DB → 再删除缓存（不是更新缓存）

**读流程**：先读缓存 → miss 则读 DB → 回填缓存

```
写：
  1. UPDATE db SET value = newValue WHERE id = 1;
  2. DELETE cache WHERE key = "item:1";

读：
  1. value = cache.get("item:1")
  2. if value == null:
       value = db.query("SELECT * FROM items WHERE id = 1")
       cache.set("item:1", value, TTL)
  3. return value
```

**为什么删缓存而不是更新缓存？**
- 更新缓存在并发下有问题：线程 A 先更新 DB，线程 B 后更新 DB 但先更新缓存，线程 A 再更新缓存 → 缓存里是 A 的旧值，DB 里是 B 的新值
- 删除缓存则让下次读自然回源，始终拿到 DB 最新值

**仍存在的不一致窗口**：
- DB 更新成功 → 删缓存之前挂了 → 缓存里还是旧数据
- 解决：设合理 TTL 作为兜底（最终一致），或用下面的方案增强

#### 方案 2：延迟双删

在 Cache Aside 基础上加一次延迟删除：

```
1. 删除缓存
2. 更新 DB
3. sleep(N ms)  // 等读请求可能回填的旧数据
4. 再次删除缓存
```

**目的**：防止步骤 2 期间有读请求读到旧 DB 数据并回填到缓存。第二次删除把这个"脏回填"清掉。

**问题**：
- sleep 时间不好定（太短没用，太长影响性能）
- 第二次删除也可能失败
- 实际生产中用得不多，更多是面试概念

#### 方案 3：基于 Binlog 的异步缓存更新（最优雅）

**核心思想**：不在业务代码里操作缓存，而是监听 DB 的 binlog 变更，异步更新/删除缓存。

```
业务代码：只写 DB（不碰缓存）
    ↓
MySQL binlog
    ↓
Canal / Debezium（binlog 监听）
    ↓
MQ（Kafka / RocketMQ）
    ↓
消费者：根据变更事件删除/更新缓存
```

**优点**：
- **业务代码解耦**：业务只管写 DB，不用关心缓存失效逻辑
- **可靠性高**：binlog 是 DB 的持久化日志，不会丢；MQ 有重试机制
- **天然有序**：binlog 保证顺序，不会出现并发写导致的乱序问题
- **适用所有写入路径**：不管是 API 写入、后台脚本、还是手动 SQL，只要改了 DB 就会被捕获

**缺点**：
- 架构复杂度增加（需要部署 Canal/Debezium + MQ + 消费者）
- 有延迟（通常几十 ms ~ 几百 ms），不是强一致
- 消费者处理失败需要重试和死信队列兜底

#### 方案 4：写请求串行化

对同一个 key 的写操作通过队列串行化处理：

```
写请求 → 按 key hash 到固定队列 → 单线程顺序执行：更新 DB → 删缓存
```

**优点**：彻底消除并发写导致的不一致
**缺点**：吞吐下降，热点 key 成瓶颈，实际用得少

#### 方案 5：分布式事务（强一致，但重）

用 Seata 等分布式事务框架把 DB 写入和缓存操作放在一个事务里。

**几乎不会这么做**，因为：
- 缓存本身就是为了性能，再套分布式事务把性能优势全吃掉了
- 缓存操作不支持标准事务语义（Redis 没有 prepare/commit）

### 三、生产中最常用的组合

```
Cache Aside + TTL 兜底 + Binlog 异步删除

即：
- 写时先更新 DB 再删缓存（Cache Aside）
- 设合理 TTL（如 5min）作为最终一致性兜底
- 部署 Canal 监听 binlog，异步再删一次缓存（补偿删除失败的情况）
```

这个组合在一致性、性能、复杂度之间取得了最好的平衡，是大厂最常见的实践。

### 四、一致性等级对照

| 方案 | 一致性 | 性能影响 | 复杂度 | 适用场景 |
|------|--------|---------|--------|---------|
| Cache Aside + TTL | 最终一致（秒级） | 低 | 低 | 大部分业务 |
| 延迟双删 | 最终一致（ms 级） | 中 | 低 | 面试概念为主 |
| Binlog + MQ | 最终一致（百 ms 级） | 低 | 中 | 一致性要求较高的核心业务 |
| 写串行化 | 强一致 | 高 | 中 | 热点少、写 QPS 低的场景 |
| 分布式事务 | 强一致 | 很高 | 高 | 几乎不用于缓存场景 |

### 五、面试回答模板

> "缓存和 DB 一致性，我常用的是 **Cache Aside 模式——写时先更新 DB 再删缓存，读时 miss 回源并回填**。删缓存而不是更新缓存，是为了避免并发写导致的顺序问题。这个方案存在'DB 更新成功但删缓存失败'的不一致窗口，兜底靠 **TTL 过期**实现最终一致。如果一致性要求更高，可以引入 **Canal 监听 binlog + MQ 异步删缓存**作为补偿机制，业务代码完全解耦，binlog 保证不丢变更、MQ 保证重试。"

## Redis 热 Key 问题及解决方案

**类别**：Redis / 缓存 / 高并发

### 一、什么是热 Key

某个 Redis key 被大量并发请求集中访问，导致该 key 所在的 Redis 节点**单点负载过高**。典型场景：

- 热门商品详情页（秒杀、爆款）
- 热搜词/热门话题的缓存
- 明星出轨等突发事件的相关数据
- 直播间实时数据

**危害**：
- 单个 Redis 节点 CPU 打满，其他 key 的请求也被拖慢
- 极端情况下节点 OOM 或连接池耗尽，影响整个集群的可用性
- Redis Cluster 下数据按 slot 分片，热 key 无法靠增加节点来分摊（因为同一个 key 只在一个 slot 上）

### 二、解决方案

#### 方案 1：本地缓存（L1 Cache）

**最常用、最直接的方案**。在应用进程内增加一层本地缓存（Caffeine / Guava Cache），热 key 的请求根本不走 Redis。

```
请求 → 本地缓存（命中直接返回）→ Redis → DB
```

**优点**：
- 零网络开销，微秒级响应
- 彻底消除 Redis 热点压力
- 实现简单

**注意点**：
- 本地缓存 **TTL 要短**（如 1-5s），避免各实例数据不一致时间过长
- 多实例之间本地缓存不共享，数据更新时需要广播失效（可用 Redis Pub/Sub 或 MQ 通知各实例清本地缓存）
- 适合**读多写少**的场景；如果热 key 频繁更新，短 TTL 导致命中率低，效果打折

#### 方案 2：Key 分片（读副本打散）

把一个热 key **拆成多个子 key**，分散到不同 Redis 节点上：

```
原始 key：  product:1001
拆分后：    product:1001:0, product:1001:1, ..., product:1001:N

读取时：    随机选一个子 key 读取（或 hash(requestId) % N）
写入时：    更新所有子 key
```

**优点**：
- 读请求被均匀打散到 N 个节点，单节点压力降为 1/N
- 对客户端透明（封装在 SDK 里）

**缺点**：
- 写放大 N 倍（每次更新要写 N 个子 key）
- 需要预判哪些 key 是热 key（或动态识别后再拆分）
- 数据一致性窗口：N 个子 key 的更新不是原子的，短暂不一致

**适用**：读远大于写的热 key（如商品详情、配置信息）

#### 方案 3：热 Key 探测 + 动态升级

不提前知道哪些是热 key，靠**实时监测**发现并自动处理：

```
监控层：统计每个 key 的 QPS
  → 超过阈值 → 标记为热 key
  → 自动将该 key 加载到本地缓存 / 自动拆分副本

工具：
  - Redis 4.0+ 的 `redis-cli --hotkeys`（基于 LFU）
  - 客户端 SDK 内置计数器（如 JD 的 HotKey 框架）
  - Proxy 层统计（如 Twemproxy、Codis 的监控）
```

**京东 HotKey 框架的思路**：
- 客户端 SDK 上报访问频次到 etcd/探测中心
- 探测中心发现热 key 后推送给所有客户端
- 客户端自动将热 key 缓存到本地 JVM
- 热度下降后自动降级回 Redis 读取

**优点**：全自动、不需要提前预判
**缺点**：有探测延迟（热 key 刚出现的前几秒仍会打到 Redis）

#### 方案 4：读写分离 + 多从节点

利用 Redis 主从架构，读请求分散到多个从节点：

```
写 → 主节点
读 → 负载均衡到多个从节点
```

**优点**：架构简单，天然支持
**缺点**：
- 主从同步有延迟（异步复制），可能读到旧数据
- 从节点数量有限，不能无限扩
- 如果是 Cluster 模式，同一个 slot 的从节点数量也有限

#### 方案 5：Proxy 层限流

在 Redis 前面加一层代理（或在客户端 SDK 里），对热 key 的访问做限流：

```
请求 → Proxy/SDK 限流 → 超过阈值的请求直接返回降级数据/排队等待 → Redis
```

**适用**：极端场景的兜底保护，防止 Redis 被打挂

### 三、方案对比

| 方案 | 效果 | 复杂度 | 写放大 | 一致性影响 | 适用场景 |
|------|------|--------|--------|-----------|---------|
| 本地缓存 | ⭐⭐⭐⭐⭐ | 低 | 无 | 短暂不一致（TTL 控制） | 最通用，首选 |
| Key 分片 | ⭐⭐⭐⭐ | 中 | N 倍 | 短暂不一致 | 读远大于写 |
| 热 Key 探测 | ⭐⭐⭐⭐ | 中高 | 无 | 同本地缓存 | 热点不可预知 |
| 读写分离 | ⭐⭐⭐ | 低 | 无 | 主从延迟 | 已有主从架构 |
| Proxy 限流 | ⭐⭐ | 中 | 无 | 无 | 极端兜底 |

### 四、生产中最常用的组合

```
本地缓存（Caffeine，短 TTL）
  + 热 Key 探测（自动识别并升级到本地缓存）
  + Key 分片（对已知的超高频热 key 预先拆分）
```

第一层用本地缓存挡住绝大部分热 key 流量，探测机制自动发现新热 key 并动态升级，对已知的超级热 key（如秒杀商品）预先做 key 分片多一层保障。

### 五、面试回答模板

> "热 key 问题的本质是单个 Redis 节点承受了不成比例的流量。我的解决思路分三层：**第一层是本地缓存**，用 Caffeine 在 JVM 内缓存热 key 数据，TTL 设短（如 3-5s）保证一致性，热 key 请求根本不走 Redis；**第二层是 Key 分片**，对已知的超高频 key 拆成多个子 key 分散到不同节点，读时随机选一个，写时更新所有副本；**第三层是动态探测**，在客户端 SDK 内置访问计数，QPS 超阈值自动将该 key 升级到本地缓存，热度下降后自动降级。我在百度做图谱优化时就用了类似思路——Caffeine 本地缓存 + Redis 二级缓存 + TTL 随机化，防止热点节点打穿缓存层。"

## Redis 大 Key 问题及解决方案

**类别**：Redis / 缓存 / 性能优化

### 一、什么是大 Key

大 Key 不是指 key 名字长，而是指 **value 占用的内存过大**：

| 数据类型 | 大 Key 判定标准（经验值） |
|---------|----------------------|
| String | value > 10KB（有些团队以 1MB 为界） |
| Hash | field 数量 > 5000 或 总 value > 10MB |
| List | 元素数量 > 5000 |
| Set | 成员数量 > 5000 |
| ZSet | 成员数量 > 5000 |

### 二、大 Key 有什么危害

**1. 读写耗时长，阻塞其他请求**

Redis 是单线程模型（6.0 前网络 IO 单线程，6.0 后命令执行仍然是单线程）。读写一个大 Key 期间，其他所有请求都在排队等：

```
一个 10MB 的 String：
  GET 耗时 ~1-5ms（正常 key ~0.1ms）
  网络传输 ~10ms（正常 key ~0.01ms）
  → 这期间所有其他命令都被阻塞
```

**2. 内存不均衡**

Redis Cluster 按 slot 分片，大 Key 所在的节点内存使用远高于其他节点，导致集群内存倾斜，甚至触发单节点 OOM。

**3. 删除导致卡顿**

`DEL` 一个大 Key 时，Redis 需要释放大量内存，可能导致主线程阻塞几百毫秒甚至几秒（尤其是 Hash/Set/ZSet 几百万元素时），期间整个 Redis 实例不可用。

**4. 主从同步 / 持久化受影响**

- 大 Key 写入导致 AOF 缓冲区暴涨
- 主从全量同步时 RDB 文件变大，同步时间延长
- 过期淘汰时和 DEL 一样会阻塞

### 三、如何发现大 Key

```bash
# 方式 1：redis-cli 内置扫描（推荐，不阻塞）
redis-cli --bigkeys

# 方式 2：redis-cli + --memkeys（Redis 7.0+，按内存排序）
redis-cli --memkeys

# 方式 3：SCAN + DEBUG OBJECT（线上慎用 DEBUG）
# 逐个扫描，检查 serializedlength

# 方式 4：RDB 离线分析（最安全）
# 用 redis-rdb-tools 解析 RDB 文件，输出每个 key 的内存占用
rdb --command memory dump.rdb --bytes 10240 -f big_keys.csv

# 方式 5：MEMORY USAGE（Redis 4.0+，单个 key 查询）
MEMORY USAGE mykey
```

### 四、解决方案

#### 方案 1：拆分大 Key（最核心的解法）

**String 大 Value → 拆成多个小 Key**

```
原始：
  SET product:1001:detail  "{...10MB 的 JSON...}"

拆分后：
  SET product:1001:basic    "{name, price, category}"
  SET product:1001:desc     "{description 前半段}"
  SET product:1001:desc2    "{description 后半段}"
  SET product:1001:images   "{图片URL列表}"
```

按业务含义垂直拆分，读取时按需取（不需要图片就不读 images key），类似数据库的垂直拆表——和你在百度做的物料数据库垂直拆分是同一个思路。

**Hash 大 Key → 按字段分桶**

```
原始：
  HSET user:followers  uid1 "data1"  uid2 "data2"  ...  uid100000 "data100000"

拆分后（按 uid hash 取模分桶）：
  HSET user:followers:0  uid1 "data1"  uid3 "data3" ...
  HSET user:followers:1  uid2 "data2"  uid4 "data4" ...
  ...
  HSET user:followers:99  ...

读取时：bucket = hash(uid) % 100 → HGET user:followers:{bucket} uid
```

**List/ZSet 大 Key → 分段存储**

```
原始：
  LPUSH timeline:user1  msg1 msg2 ... msg1000000

拆分后（按时间分段）：
  timeline:user1:202603  → 当月数据
  timeline:user1:202602  → 上月数据
  ...
```

#### 方案 2：压缩 Value

如果 value 是文本/JSON，可以压缩后存储：

```
写入：value → gzip/snappy 压缩 → SET key compressed_value
读取：GET key → 解压 → 使用
```

**效果**：JSON 文本压缩率通常 60-80%，10MB → 2-4MB
**代价**：CPU 开销（压缩/解压），需评估是否值得

适合**读少写少但必须完整存储**的场景（如配置快照、报表缓存）。

#### 方案 3：转移到更合适的存储

大 Key 往往是因为 Redis 被当成了不该当的角色：

| 场景 | 不该用 Redis | 应该用 |
|------|-------------|-------|
| 存大文本/文件内容 | String 存 10MB 文本 | MinIO / OSS + Redis 只存 URL |
| 存完整用户列表 | Set 存百万 UID | MySQL / ES + Redis 只存热数据 |
| 存历史消息 | List 存所有消息 | Kafka / MySQL + Redis 只存最近 N 条 |
| 存完整 JSON 对象 | String 存整个对象 | MySQL 存全量 + Redis 只存热字段 |

**核心原则**：Redis 存**热数据的索引或摘要**，不存原始大对象。

#### 方案 4：安全删除大 Key

发现大 Key 后要删除时，**不能直接 DEL**（会阻塞主线程）：

```bash
# Redis 4.0+：UNLINK（异步删除，后台线程处理，不阻塞）
UNLINK bigkey

# Redis 4.0 之前：分批渐进删除
# Hash：HSCAN + HDEL 每次删一小批
# Set：SSCAN + SREM 每次删一小批
# ZSet：ZREMRANGEBYRANK 每次删一段
# List：LTRIM 每次缩短一段
```

**UNLINK vs DEL**：
- DEL：同步删除，主线程阻塞直到内存释放完毕
- UNLINK：将 key 从 keyspace 摘除（O(1)），实际内存释放交给后台线程异步完成

#### 方案 5：设置合理的过期策略

避免大 Key 长期驻留：
- 给大 Key 设置**合理 TTL**，到期自动清理
- 注意：Redis 的过期删除是惰性+定期的，大 Key 过期时删除同样会阻塞（同 DEL）
- Redis 4.0+ 配置 `lazyfree-lazy-expire yes`，过期删除也走异步

### 五、预防措施（写入时控制）

```
1. 业务规范：写入前校验 value 大小，超过阈值拒绝或拆分
2. 监控告警：定期扫描（redis-cli --bigkeys）+ 自动告警
3. 数据建模：设计 key 结构时就考虑上限（Hash field 数量、List 长度）
4. 淘汰策略：对容易膨胀的 key（如计数器集合、用户列表），定期归档历史数据到 MySQL
```

### 六、方案对比

| 方案 | 效果 | 适用场景 | 注意事项 |
|------|------|---------|---------|
| 拆分大 Key | ⭐⭐⭐⭐⭐ | 所有大 Key | 需改业务读写逻辑 |
| 压缩 Value | ⭐⭐⭐ | 文本类大 Value | CPU 开销，需评估 |
| 转移存储 | ⭐⭐⭐⭐ | Redis 存了不该存的数据 | 架构改动较大 |
| UNLINK 异步删 | ⭐⭐⭐⭐ | 已有大 Key 需删除 | 需 Redis 4.0+ |
| 写入时控制 | ⭐⭐⭐⭐⭐ | 预防 | 规范落地需推动 |

### 七、面试回答模板

> "大 Key 的危害主要有三个：**阻塞主线程**（Redis 单线程，读写大 Key 期间其他命令排队）、**内存倾斜**（Cluster 下大 Key 所在节点内存远高于其他节点）、**删除卡顿**（DEL 大 Key 释放内存可能阻塞几秒）。解决思路：**首先是拆分**——String 按业务垂直拆成多个小 key，Hash/Set 按字段哈希分桶，和数据库垂直拆表是同一个思路；**其次是评估是否该用 Redis 存**——大文本存 OSS 只存 URL，全量列表存 MySQL 只缓存热数据；**删除时用 UNLINK 而不是 DEL**，异步释放不阻塞主线程。预防层面，写入时校验 value 大小，定期 `--bigkeys` 扫描 + 告警。我在百度做物料数据库治理时也遇到类似问题——大字段冗余存储导致记录膨胀，解法就是垂直拆分抽维表，思路是相通的。"

## RedLock（Redis 分布式锁算法）

**类别**：Redis / 分布式锁 / 分布式系统

### 一、先回顾：单节点 Redis 分布式锁

最基本的 Redis 分布式锁：

```bash
# 加锁（原子操作）
SET lock_key unique_value NX PX 30000
# NX：key 不存在才设置（互斥）
# PX 30000：30 秒自动过期（防死锁）

# 解锁（Lua 脚本保证原子性）
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

**为什么解锁要用 Lua 判断 unique_value？**
防止误删别人的锁：A 获取锁 → A 执行超时锁自动过期 → B 获取锁 → A 执行完 DEL 删的是 B 的锁。用 unique_value 校验确保只删自己的。

**单节点锁的致命问题**：Redis 主节点挂了怎么办？
- 主节点加锁成功 → 还没同步到从节点 → 主节点挂了 → 从节点升主 → 锁丢了 → 另一个客户端也能加锁成功
- **两个客户端同时持有锁 → 互斥性被破坏**

这就是 RedLock 要解决的问题。

### 二、RedLock 算法（Antirez 提出）

**核心思想**：不依赖单个 Redis 实例，而是向**N 个独立的 Redis 主节点**（无主从关系、互不复制）同时加锁，**多数派成功则视为加锁成功**。

**前提**：部署 N 个独立 Redis 实例（通常 N=5），它们之间无任何复制关系。

#### 加锁流程

```
客户端执行以下步骤：

1. 记录当前时间 T1

2. 依次向 N 个 Redis 实例发送加锁请求：
   SET lock_key unique_value NX PX TTL
   每个请求设一个很短的超时时间（如 5-50ms），
   防止某个实例挂了导致长时间阻塞

3. 记录当前时间 T2，计算加锁耗时 = T2 - T1

4. 判断是否加锁成功，需同时满足两个条件：
   a. 在 >= N/2 + 1（多数派）个实例上加锁成功
   b. 加锁总耗时 < 锁的 TTL

5. 如果加锁成功：
   锁的有效时间 = 原始 TTL - 加锁耗时
   （扣除了加锁过程消耗的时间）

6. 如果加锁失败：
   向所有实例发送解锁请求（包括加锁失败的实例，
   因为可能加锁成功了但响应丢了）
```

用一张图表示（N=5）：

```
客户端 ──SET NX──→ Redis①  ✓
       ──SET NX──→ Redis②  ✓
       ──SET NX──→ Redis③  ✗（挂了/超时）
       ──SET NX──→ Redis④  ✓
       ──SET NX──→ Redis⑤  ✓

成功 4/5 >= 3（多数派）且耗时 < TTL → 加锁成功！
```

#### 解锁流程

```
向所有 N 个实例发送解锁请求（Lua 脚本，校验 unique_value）
不管加锁时是否成功都要发，确保清理干净
```

### 三、RedLock 为什么要多数派

**容错**：N=5 时，允许最多 2 个实例同时不可用（挂了/网络不通），仍能正常加锁。

**互斥性保证**：如果客户端 A 在 3 个实例上加锁成功，那客户端 B 最多只能在剩下 2 个实例上加锁成功（不够多数派），所以 B 必定加锁失败。**同一时刻只有一个客户端能获得多数派 → 互斥**。

### 四、RedLock 的争议（Martin Kleppmann vs Antirez）

RedLock 在业界有**著名的争论**，面试可能会被追问：

#### Martin Kleppmann 的批评（《How to do distributed locking》）

**核心论点**：RedLock 不安全，因为它依赖时间假设。

**问题 1：GC / 进程暂停导致锁失效**

```
时间线：
  T1: 客户端 A 获取 RedLock（TTL=30s），有效期到 T1+30s
  T2: 客户端 A 发生 GC 暂停（或进程挂起），暂停了 35 秒
  T3 = T1+35s: 锁已过期，客户端 B 获取了锁
  T4: 客户端 A 从 GC 恢复，以为自己还持有锁，继续操作共享资源
  → A 和 B 同时操作 → 互斥被破坏
```

这个问题不只是 RedLock 的问题，**所有基于 TTL 自动过期的分布式锁都有这个风险**。

**问题 2：时钟跳变**

```
客户端 A 在 Redis①②③ 上加锁成功
Redis③ 的系统时钟突然向前跳了（NTP 校准或人为修改）
→ Redis③ 上的锁提前过期
→ 客户端 B 在 Redis③④⑤ 上加锁成功（③ 的锁已过期可以重新获取）
→ A 和 B 同时持有锁
```

RedLock 假设各实例的时钟大致同步且单调递增，但现实中 NTP 跳变是可能发生的。

**Martin 的建议**：如果要真正的安全性，用 **fencing token**（单调递增的令牌）——获取锁时同时获取一个递增 token，操作共享资源时带上 token，资源端拒绝旧 token 的操作。但 Redis 原生不支持 fencing token。

#### Antirez（Redis 作者）的回应

- GC 暂停问题：所有分布式锁都有，不是 RedLock 特有的
- 时钟跳变：可以通过运维保证（禁止大幅 NTP 跳变，用单调时钟）
- RedLock 的安全性是建立在"合理的系统模型假设"上的

### 五、生产中怎么选

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| **一般业务**（接口幂等、防重复提交） | 单节点 Redis 锁（SET NX PX） | 简单够用，挂了靠业务兜底 |
| **核心业务**（扣款、库存） | Redis 锁 + **业务层兜底**（数据库唯一约束/乐观锁） | 锁是"尽力而为"，数据一致性由 DB 保证 |
| **强一致性要求** | **Zookeeper / etcd** 分布式锁 | 基于共识协议（ZAB/Raft），不依赖时间假设 |
| **较高可靠性 + Redis 生态** | RedLock（N=5） | 比单节点强，但仍有理论漏洞 |

**实际生产中 RedLock 用得不多**，原因：
- 需要部署 5 个独立 Redis 实例，运维成本高
- 理论上仍有 Martin 指出的安全漏洞
- 大部分场景用单节点锁 + 业务层兜底就够了
- 真正需要强一致锁的场景直接上 ZooKeeper/etcd

### 六、补充：Redisson 的看门狗机制

Java 生态中常用 Redisson 框架，它用**看门狗（Watchdog）** 来解决"业务执行时间超过锁 TTL"的问题：

```
1. 加锁时默认 TTL = 30s
2. 看门狗线程每 10s（TTL/3）检查一次
3. 如果业务还在执行（锁还被持有），自动续期到 30s
4. 业务完成主动释放锁时，看门狗停止
5. 如果客户端进程崩了，看门狗也没了 → 锁自然 30s 后过期
```

这解决了"业务执行久了锁自动过期被别人抢"的问题，但**不能解决 GC 暂停后恢复的问题**（GC 暂停期间看门狗线程也暂停了）。

### 七、面试回答模板

> "单节点 Redis 分布式锁用 `SET NX PX` 加锁 + Lua 脚本解锁，核心问题是**主节点故障时锁可能丢失**（主从异步复制）。RedLock 通过向 **N 个独立 Redis 实例**同时加锁、**多数派成功**才视为持有锁来解决这个问题。但 RedLock 有争议——Martin Kleppmann 指出它依赖时间假设，**GC 暂停**可能导致客户端以为持有锁但锁已过期、**时钟跳变**可能导致提前过期破坏互斥。所以生产中的实践是：一般业务用单节点锁就够了；核心业务**锁只做'尽力互斥'，数据安全靠 DB 层保证**（唯一约束/乐观锁）；真正要强一致锁用 ZooKeeper 或 etcd（基于共识协议，不依赖时间假设）。"

## Redis Cluster 分片集群与哈希槽

**类别**：Redis / 集群 / 分片 / 高可用

### 一、为什么需要分片集群

单机 Redis 的瓶颈：

| 瓶颈 | 表现 |
|------|------|
| **内存上限** | 单机内存有限（通常 64GB-256GB），数据量超过就存不下 |
| **写入瓶颈** | 单机写 QPS 有上限（~10 万），无法水平扩展 |
| **主从复制的局限** | 主从只能分担读压力，写还是只能走主节点 |

Redis Cluster 通过**将数据分散到多个节点**来解决这些问题——每个节点只存一部分数据，读写都可以分摊。

### 二、哈希槽（Hash Slot）

Redis Cluster 把整个数据空间划分为 **16384 个哈希槽**（编号 0 ~ 16383），每个 key 通过哈希函数映射到其中一个槽。

#### key → 槽 的映射

```
slot = CRC16(key) % 16384

例：
  CRC16("user:1001") % 16384 = 5461  → 这个 key 属于槽 5461
  CRC16("order:2002") % 16384 = 12000 → 这个 key 属于槽 12000
```

#### 槽 → 节点 的映射

```
集群启动时，16384 个槽被分配给各个主节点：

假设 3 个主节点：
  Node A：负责槽 0 ~ 5460       （5461 个槽）
  Node B：负责槽 5461 ~ 10922   （5462 个槽）
  Node C：负责槽 10923 ~ 16383  （5461 个槽）

所以：
  "user:1001" → 槽 5461 → Node B 处理
  "order:2002" → 槽 12000 → Node C 处理
```

#### 完整的请求路由过程

```
客户端发送命令 GET user:1001

情况 1：客户端连的是 Node B（正确节点）
  → Node B 有槽 5461 → 直接执行并返回

情况 2：客户端连的是 Node A（错误节点）
  → Node A 发现槽 5461 不在自己这 → 返回 MOVED 重定向
  → MOVED 5461 192.168.1.2:6379
  → 客户端重新连接 Node B 执行命令
  → 客户端更新本地的槽-节点映射表（下次就直接连 Node B 了）
```

### 三、为什么是 16384 个槽

面试常问的点。Redis 作者 antirez 解释过：

```
1. 节点间心跳包需要携带槽位图（bitmap）
   16384 个槽 → bitmap 大小 = 16384 / 8 = 2KB
   如果用 65536 个槽 → bitmap = 8KB → 心跳包太大，浪费带宽

2. Redis Cluster 官方建议最多不超过 1000 个节点
   16384 / 1000 = 16 个槽/节点 → 每个节点至少分到十几个槽，足够均匀

3. 所以 16384 是一个在 "心跳包大小" 和 "槽粒度" 之间的平衡点
```

### 四、槽的分配与重新分配

#### 初始分配

```
创建集群时手动或自动分配：
  redis-cli --cluster create node1:6379 node2:6379 node3:6379
  → 自动均匀分配 16384 个槽给 3 个节点
```

#### 扩容（新增节点）

```
原来 3 个节点，现在加一个 Node D：

之前：
  Node A：0 ~ 5460
  Node B：5461 ~ 10922
  Node C：10923 ~ 16383

加入 Node D 后，从每个旧节点迁移一部分槽过去：
  Node A：0 ~ 4095          （迁出 4096~5460 给 D）
  Node B：5461 ~ 9556       （迁出 9557~10922 给 D）
  Node C：10923 ~ 15018     （迁出 15019~16383 给 D）
  Node D：4096~5460, 9557~10922, 15019~16383

迁移过程是在线的，不需要停机
```

#### 迁移过程中的请求处理

```
槽 5000 正在从 Node A 迁移到 Node D：

客户端请求 GET key（key 属于槽 5000）→ 连到 Node A

情况 1：key 还在 Node A → 正常返回
情况 2：key 已经迁到 Node D → Node A 返回 ASK 重定向
  → ASK 5000 192.168.1.4:6379
  → 客户端先发 ASKING 命令给 Node D，再发 GET key
  → Node D 返回结果

ASK vs MOVED 的区别：
  MOVED：槽已经永久转移，客户端要更新本地映射
  ASK：槽正在迁移中，这次临时去新节点，下次还是先问旧节点
```

#### 缩容（移除节点）

```
把要下线节点的所有槽迁移到其他节点 → 然后移除空节点
和扩容是反向操作
```

### 五、集群的高可用（主从 + 故障转移）

```
每个主节点配一个从节点（副本）：

  Node A (主) ←→ Node A' (从)    槽 0~5460
  Node B (主) ←→ Node B' (从)    槽 5461~10922
  Node C (主) ←→ Node C' (从)    槽 10923~16383

如果 Node B 宕机：
  1. 其他主节点通过 Gossip 协议检测到 Node B 失联
  2. 超过半数主节点认为 Node B PFAIL → 标记为 FAIL
  3. Node B' 自动升级为主节点，接管槽 5461~10922
  4. 集群继续对外服务

整个故障转移过程自动完成，类似 Sentinel，但不需要额外的 Sentinel 进程
```

### 六、Hash Tag —— 让相关的 key 落到同一个槽

```
默认情况下，不同 key 会被分散到不同的槽/节点：
  user:1001  → 槽 A
  order:1001 → 槽 B
  → 无法对这两个 key 做原子操作（事务/Lua 脚本要求 key 在同一节点）

解决：用 Hash Tag，Redis 只对 {} 里的部分做 CRC16：
  user:{1001}  → CRC16("1001") % 16384 = 槽 X
  order:{1001} → CRC16("1001") % 16384 = 槽 X
  → 同一个 user 的相关 key 一定在同一个槽 → 同一个节点
  → 可以在同一个事务/Lua 脚本中操作
```

**注意**：Hash Tag 如果设计不当会导致**数据倾斜**——如果大量 key 都用同一个 tag 值，会集中到同一个槽/节点，形成热点。

### 七、Redis Cluster vs 一致性哈希

面试常问：Redis 为什么用哈希槽而不是一致性哈希？

| | 哈希槽（Redis Cluster） | 一致性哈希 |
|---|---|---|
| 映射方式 | key → 固定 16384 个槽 → 节点 | key → 哈希环上顺时针找最近节点 |
| 数据迁移 | 以**槽**为单位迁移，粒度可控 | 以 key 为单位，粒度太细 |
| 数据倾斜 | 槽均匀分配即可 | 需要虚拟节点解决 |
| 扩容 | 迁移若干槽到新节点 | 只影响相邻节点 |
| 实现复杂度 | 低（槽映射表固定大小） | 中（需要维护哈希环 + 虚拟节点） |

> "Redis 选哈希槽的核心原因是**迁移粒度可控**。一致性哈希以 key 为粒度，迁移时不好控制范围和进度。哈希槽以槽为粒度，一个槽里的所有 key 整体迁移，进度清晰可控，而且节点间心跳只需要传 2KB 的槽位图就能同步整个集群的数据分布状态。"

### 八、面试回答模板

> "Redis Cluster 把数据空间划分为 **16384 个哈希槽**，每个 key 通过 `CRC16(key) % 16384` 映射到一个槽，每个槽分配给一个主节点。客户端请求时先根据本地缓存的槽-节点映射找到目标节点，如果找错了节点会返回 **MOVED 重定向**（槽已永久转移）或 **ASK 重定向**（槽正在迁移中）。
>
> 选 16384 个槽是在心跳包大小（2KB bitmap）和槽粒度之间的平衡。扩容时从已有节点迁移若干槽到新节点，迁移过程在线进行不停服。每个主节点配从节点做副本，主节点宕机时从节点自动升主实现故障转移。
>
> 相关 key 需要做原子操作时用 **Hash Tag**（`{tag}`）让它们落到同一个槽。Redis 选哈希槽而不是一致性哈希，核心原因是**迁移以槽为粒度，进度可控**，而且心跳只需传 2KB 位图就能同步整个集群状态。"
