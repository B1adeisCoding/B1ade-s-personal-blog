## 消息队列基础

**类别**：消息队列 / 基础概念 / 应用场景

### 一、消息队列是什么

消息队列（Message Queue）是一个**异步通信的中间件**——生产者把消息发到队列里就返回，消费者从队列里取消息处理。两者不直接通信，通过队列解耦。

```
同步调用：
  服务 A → 调用服务 B → 等 B 返回 → 继续
  （A 必须等 B 完成，耦合度高）

异步消息：
  服务 A → 发消息到 MQ → 直接返回（不用等）
  服务 B → 从 MQ 取消息 → 处理
  （A 和 B 解耦，A 不关心 B 什么时候处理）
```

### 二、三大核心作用

#### 1. 异步

```
下单流程（同步）：
  创建订单(50ms) → 扣库存(50ms) → 发短信(200ms) → 推积分(100ms)
  总耗时：400ms

下单流程（异步）：
  创建订单(50ms) → 发消息到 MQ → 返回（50ms）
  MQ → 消费者 1：扣库存
  MQ → 消费者 2：发短信
  MQ → 消费者 3：推积分
  用户只等 50ms，其他操作异步完成
```

#### 2. 解耦

```
没有 MQ：
  订单服务直接调用库存服务、短信服务、积分服务
  新增一个服务 → 订单服务要改代码
  某个服务挂了 → 订单服务受影响

有 MQ：
  订单服务只管发消息到 MQ
  谁想消费谁自己订阅
  新增服务 → 加一个消费者就行，订单服务不用改
  某个消费者挂了 → 消息在队列里等着，不影响生产者
```

#### 3. 削峰

```
没有 MQ：
  秒杀瞬间 10 万请求 → 直接打到数据库 → 数据库被打垮

有 MQ：
  秒杀瞬间 10 万请求 → 写入 MQ（MQ 扛得住）
  消费者按固定速率从 MQ 取消息 → 数据库压力平稳
  MQ 起到了缓冲池的作用
```

### 三、引入 MQ 带来的问题

| 问题 | 描述 |
|------|------|
| **系统复杂度** | 多了一个中间件要维护 |
| **消息丢失** | 生产者发了但 MQ 没收到 / MQ 收了但消费者没处理 |
| **消息重复** | 网络抖动导致重发 → 消费者处理了两次 |
| **消息顺序** | 多个消费者并发消费 → 顺序被打乱 |
| **消息积压** | 消费速度跟不上生产速度 → 队列越来越长 |
| **一致性** | 消息发了但下游处理失败 → 数据不一致 |

## 主流 MQ 对比

**类别**：消息队列 / 选型

| 特性    | **Kafka**        | **RocketMQ**     | **RabbitMQ** |
| ----- | ---------------- | ---------------- | ------------ |
| 开发语言  | Scala/Java       | Java             | Erlang       |
| 吞吐量   | **极高**（百万级 TPS）  | 高（十万级 TPS）       | 中（万级 TPS）    |
| 延迟    | ms 级             | ms 级             | **μs 级**（最低） |
| 消息可靠性 | 高（可配置）           | **极高**（金融级）      | 高            |
| 顺序消息  | 分区内有序            | 队列内有序            | 队列内有序        |
| 事务消息  | 支持（0.11+）        | **原生支持**         | 不支持          |
| 延迟消息  | 不原生支持            | **原生支持**（18 个级别） | 支持（插件）       |
| 消息回溯  | **支持**（按 offset） | 支持（按时间）          | 不支持          |
| 适用场景  | 大数据、日志、流处理       | 电商、金融、业务消息       | 中小规模、需要灵活路由  |

**选型建议**：
- 大数据/日志采集 → **Kafka**（吞吐量最高）
- 业务系统/电商/金融 → **RocketMQ**（可靠性高、功能全）
- 中小系统/需要灵活路由 → **RabbitMQ**（延迟低、社区成熟）

## 如何保证消息不丢失

**类别**：消息队列 / 可靠性 / 消息丢失

### 消息丢失的三个环节

```
生产者 ──①──→ MQ Broker ──②──→ 消费者
                  │
                  ③
                  ↓
                磁盘/副本

① 生产阶段丢失：消息发出去了但 Broker 没收到（网络问题）
② 消费阶段丢失：Broker 投递了但消费者没处理完就 ack 了
③ 存储阶段丢失：Broker 收到了但还没持久化就宕机了
```

### 每个环节的解决方案

#### ① 生产阶段：确认机制

```
Kafka：
  acks=0：不等确认（最快但可能丢）
  acks=1：Leader 写入即确认（Leader 挂了可能丢）
  acks=all：所有 ISR 副本都写入才确认（最安全）

RocketMQ：
  同步发送：send() 等待 Broker 确认，失败会重试
  异步发送：send(callback)，通过回调感知成功/失败

通用做法：
  发送失败 → 重试（设重试次数）
  重试都失败 → 记录到本地 DB / 日志，后续补偿
```

#### ② 存储阶段：持久化 + 副本

```
Kafka：
  - 消息写入 Page Cache 后异步刷盘（默认）
  - 配置 flush.messages / flush.ms 控制刷盘频率
  - 多副本机制：ISR 副本同步，Leader 挂了 Follower 接替
  - 配置 min.insync.replicas >= 2 保证至少 2 个副本有数据

RocketMQ：
  - 同步刷盘（SYNC_FLUSH）：写入磁盘才返回确认 → 最安全但慢
  - 异步刷盘（ASYNC_FLUSH）：写入内存就返回 → 快但可能丢
  - 主从同步：SYNC_MASTER 同步复制到从节点
```

#### ③ 消费阶段：手动 ack

```
错误做法：
  收到消息 → 先 ack → 再处理
  如果处理过程中宕机 → 消息已经 ack 了 → 丢了

正确做法：
  收到消息 → 先处理 → 处理成功再 ack
  如果处理过程中宕机 → 没有 ack → Broker 会重新投递

Kafka：
  关闭自动提交 offset（enable.auto.commit=false）
  处理完成后手动 commitSync()

RocketMQ：
  返回 ConsumeConcurrentlyStatus.CONSUME_SUCCESS 才算消费成功
  返回 RECONSUME_LATER → Broker 会重新投递
```

### 一句话总结

> 生产端用确认 + 重试，Broker 用持久化 + 多副本，消费端用手动 ack。三个环节都不丢才真的不丢。

## 如何保证消息不重复消费（幂等性）

**类别**：消息队列 / 可靠性 / 幂等

### 为什么会重复

```
场景 1：生产者重试
  发送超时 → 重试 → Broker 实际收到了两次

场景 2：消费者重平衡
  消费者 A 处理完了但还没 ack → 重平衡发生 → 消息被分配给消费者 B → B 又处理一次

场景 3：消费者处理完但 ack 失败
  处理成功 → ack 网络超时 → Broker 认为没消费 → 重新投递
```

**MQ 本身不保证 exactly-once，只保证 at-least-once。幂等性要业务侧自己做。**

### 幂等方案

#### 方案 1：唯一 ID + 去重表

**适用场景：** Insert 新增类操作（比如：创建订单、流水入账）。
- **怎么做：** 生产消息时，必须带上一个**全局唯一的业务ID**（比如 order_id 或支付流水号 trace_id）。在消费端的数据库表中，给这个 ID 建一个**唯一索引（Unique Index）**。
- **执行流程：** 消费端收到消息后，直接往数据库里 Insert。
    - 如果是第一次来，正常插入成功。
    - 如果是重复消息，数据库会报错 DuplicateKeyException（主键/唯一冲突）。
- **精髓处理：** 我们在代码里捕获这个异常，**不抛出错误，而是直接给 MQ 返回消费成功（ACK）**，把这条重复消息吃掉。

```sql
-- 每条消息带一个全局唯一 ID（业务 ID 或消息 ID）
-- 消费前先查去重表

BEGIN;
INSERT INTO msg_dedup (msg_id) VALUES ('xxx');  -- 唯一键，重复会失败
-- 如果插入成功 → 第一次消费，执行业务逻辑
-- 如果插入失败（唯一键冲突）→ 重复消息，跳过
COMMIT;
```

#### 方案 2：数据库唯一约束

```sql
-- 利用业务表的唯一约束天然防重
INSERT IGNORE INTO orders (order_id, user_id, amount)
VALUES ('ORD_001', 123, 99.9);
-- 重复的 order_id 会被忽略
```

#### 方案 3：Redis SetNX
- **怎么做：** 消费者一收到消息，第一步先去 Redis 里执行 SETNX（Set if Not eXists），Key 就是 业务ID，Value 可以是状态，设置一个合理的过期时间（比如 1 小时）。
- **执行流程：**
    - 如果 SETNX 返回 1（成功）：说明是新消息，开始执行业务逻辑。
    - 如果 SETNX 返回 0（失败）：说明已经被别的线程消费过了，直接丢弃并 ACK。
```
SETNX msg:{msgId} 1 EX 3600
-- 如果返回 1 → 第一次处理
-- 如果返回 0 → 已处理过，跳过
```

#### 方案 4：乐观锁 / 版本号
- **怎么做：** 电商业务是有严格状态流转的（比如：待支付 0 -> 已支付 1 -> 已发货 2）。
- **执行流程：** 我们在执行 SQL 更新时，把**前置状态**作为 WHERE 条件。
- **为什么幂等：**
    - 第一条消息来了，status 是 0，更新成功，status 变成 1，影响行数为 1。
    - 重复的第二条消息来了，这时候 status 已经是 1 了，找不到 status = 0 的记录，SQL 执行成功但影响行数为 0。业务代码判断影响行数为 0，就知道是重复消费，直接 ACK。

```sql
UPDATE account SET balance = balance - 100, version = version + 1
WHERE user_id = 123 AND version = 5;
-- 版本号不对 → 说明已经被处理过了 → 不会重复扣款
```

## 如何保证消息的顺序性

**类别**：消息队列 / 可靠性 / 顺序消费

### 为什么会乱序

```
生产者发送：消息 1 → 消息 2 → 消息 3

场景 1：多分区/队列
  消息 1 → 分区 A
  消息 2 → 分区 B
  消息 3 → 分区 A
  两个消费者分别消费 A 和 B → 顺序无法保证

场景 2：消费者并发消费
  同一个分区的消息被多个线程并发处理 → 顺序无法保证

场景 3：重试
  消息 2 处理失败重试 → 消息 3 先处理完了 → 顺序反了
```

### 解决方案

#### 全局有序（代价大，一般不用）

```
方案：只用一个分区 / 队列 + 一个消费者 + 单线程消费
代价：吞吐量极低，失去了 MQ 并行消费的优势
适用：几乎不用
```

#### 局部有序（常用）

```
方案：保证同一个业务 ID 的消息发到同一个分区 → 同一个消费者顺序消费

Kafka：
  指定 partition key = 业务 ID（如 orderId）
  → 同一个 orderId 的消息一定在同一个 partition
  → 同一个 partition 只有一个消费者 → 顺序消费

RocketMQ：
  使用 MessageQueueSelector 指定队列：
  SendResult result = producer.send(msg, (mqs, msg, arg) -> {
      int index = arg.hashCode() % mqs.size();
      return mqs.get(index);
  }, orderId);

消费端：
  单线程消费 + 同一个分区/队列不并发
  或者用内存队列按 key 分组 → 同一个 key 的消息串行处理
```

## 消息积压怎么处理

**类别**：消息队列 / 运维 / 消息积压

### 为什么会积压

```
生产速度 > 消费速度 → 队列越来越长

常见原因：
  - 消费者处理逻辑太慢（如调用了慢接口、大量 DB 操作）
  - 消费者挂了 / 数量不够
  - 消息突然暴增（流量高峰、上游重放）
  - 消费者有 bug 导致消费失败反复重试
```

### 解决方案

#### 紧急处理（先止血）

```
1. 扩消费者数量
   Kafka：增加消费者数量（不能超过分区数，否则多余的消费者闲置）
   如果分区数不够 → 先扩分区，再加消费者

2. 消费者提速
   - 跳过非关键逻辑（如日志记录、非核心通知）
   - 批量处理替代逐条处理
   - 异步化消费逻辑中的 IO 操作

3. 临时方案：转移消息
   新建一个临时 Topic，分区数多一些
   写一个临时消费者：从积压的 Topic 取消息 → 不处理，直接转发到临时 Topic
   临时 Topic 上部署大量消费者并行消费
```

#### 长期优化

```
1. 消费者性能优化（减少单条消息处理时间）
2. 合理设置分区/队列数（匹配消费能力）
3. 监控告警（队列长度、消费延迟超阈值就告警）
4. 消费端限流 + 背压机制
```

## 如何保证消息的可靠传输（事务消息）

**类别**：消息队列 / 事务 / 一致性

### 问题场景

```
下单流程：
  ① 在 DB 创建订单
  ② 发消息通知扣库存

如果 ① 成功但 ② 失败 → 订单创建了但库存没扣
如果 ② 成功但 ① 失败 → 库存扣了但订单没创建
需要保证"本地事务"和"发消息"的一致性
```

### 方案 1：RocketMQ 事务消息（推荐）

```
流程：

  ① 生产者发送半消息（Half Message）到 Broker
     → Broker 存储但对消费者不可见

  ② 生产者执行本地事务（如创建订单）

  ③ 根据本地事务结果：
     成功 → 发 Commit → Broker 让消息对消费者可见
     失败 → 发 Rollback → Broker 删除半消息

  ④ 如果 ③ 超时没收到（网络问题）：
     Broker 主动回查生产者"这个事务成功了没？"
     生产者查本地事务状态 → 返回 Commit / Rollback

  生产者                     Broker                    消费者
    │                         │                         │
    │── ① 半消息 ──────────→  │ (存储，不投递)            │
    │                         │                         │
    │  ② 执行本地事务          │                         │
    │                         │                         │
    │── ③ Commit ──────────→  │── 投递消息 ──────────→   │
    │                         │                         │
```

### 方案 2：本地消息表

```
流程：

  ① 在同一个 DB 事务中：插入订单 + 插入消息表
     → 两者在同一个事务，要么都成功要么都失败

  ② 后台定时任务扫描消息表，把未发送的消息发到 MQ

  ③ MQ 消费者消费成功 → 更新消息表状态为"已消费"

  优点：不依赖 MQ 的事务特性，任何 MQ 都能用
  缺点：需要维护消息表 + 定时任务，有延迟
```

### 方案 3：最大努力通知

```
适用于对一致性要求不那么高的场景（如通知类）：

  ① 发消息到 MQ
  ② 消费失败 → 重试 N 次
  ③ N 次都失败 → 记录日志，人工介入或定时补偿

  不保证一定成功，但尽最大努力
```

## Kafka 核心概念

**类别**：消息队列 / Kafka / 架构

### 架构概念

```
Producer（生产者）→ Topic → Partition → Consumer Group（消费者组）

┌─────────────────────────────────────┐
│              Kafka Cluster           │
│                                     │
│  Topic: order_topic                 │
│  ┌────────────┐ ┌────────────┐      │
│  │ Partition 0 │ │ Partition 1 │     │
│  │ msg0,msg2.. │ │ msg1,msg3.. │     │
│  │ (Broker 1)  │ │ (Broker 2)  │     │
│  └────────────┘ └────────────┘      │
│                                     │
└─────────────────────────────────────┘

Consumer Group A:
  Consumer 1 ← Partition 0
  Consumer 2 ← Partition 1

Consumer Group B（独立消费，互不影响）:
  Consumer 3 ← Partition 0 + Partition 1
```

| 概念 | 含义 |
|------|------|
| **Topic** | 消息的分类（一个 Topic 是一个逻辑队列） |
| **Partition** | Topic 的物理分片，消息在 Partition 内有序 |
| **Broker** | Kafka 服务节点，一个集群有多个 Broker |
| **Producer** | 消息生产者 |
| **Consumer** | 消息消费者 |
| **Consumer Group** | 消费者组，组内每个 Partition 只能被一个消费者消费 |
| **Offset** | 消息在 Partition 内的偏移量（位置编号） |
| **ISR** | In-Sync Replicas，和 Leader 保持同步的副本集合 |

### Kafka 为什么快

```
1. 顺序写磁盘
   消息追加到 Partition 文件末尾，顺序 IO 比随机 IO 快几个数量级

2. Page Cache
   利用 OS 的页缓存，写入和读取都先走内存

3. 零拷贝（Zero Copy）
   发送数据时用 sendfile() 系统调用
   数据从磁盘 → Page Cache → 网卡，不经过用户态
   省去两次内存拷贝

4. 批量发送 + 压缩
   Producer 攒一批消息一起发，减少网络往返
   支持 gzip/snappy/lz4 压缩

5. 分区并行
   多个 Partition 并行读写，水平扩展
```

### Consumer Group 与 Rebalance

```
Consumer Group 内的消费者分摊 Partition：

  3 个 Partition，2 个消费者：
    Consumer 1 ← Partition 0, Partition 1
    Consumer 2 ← Partition 2

  3 个 Partition，3 个消费者：
    Consumer 1 ← Partition 0
    Consumer 2 ← Partition 1
    Consumer 3 ← Partition 2

  3 个 Partition，4 个消费者：
    Consumer 1 ← Partition 0
    Consumer 2 ← Partition 1
    Consumer 3 ← Partition 2
    Consumer 4 ← 空闲（消费者数 > 分区数，多余的闲着）

Rebalance（重平衡）：
  当消费者加入/离开/宕机时，Partition 会重新分配给消费者
  Rebalance 期间消费暂停 → 尽量避免频繁 Rebalance
```

## 面试回答模板

> **为什么用 MQ**："三大作用：异步（非核心流程异步化降低响应时间）、解耦（上下游通过消息通信，互不依赖）、削峰（高峰流量先写 MQ，消费端匀速消费保护下游）。"
>
> **消息丢失**："三个环节分别保障：生产端用确认机制 + 重试；Broker 用持久化（同步刷盘）+ 多副本（ISR）；消费端关闭自动 ack，处理完再手动确认。"
>
> **消息重复**："MQ 只保证 at-least-once，幂等性靠业务侧做：唯一 ID + 去重表、数据库唯一约束、Redis SETNX、乐观锁版本号。"
>
> **消息顺序**："全局有序代价太大（单分区单消费者）。实际用局部有序——同一个业务 ID 发到同一个分区，分区内有序 + 单线程消费。"
>
> **消息积压**："短期：扩消费者数量、消费者提速、临时 Topic 分流。长期：优化消费逻辑、合理设置分区数、监控告警。"
>
> **事务消息**："RocketMQ 的半消息机制：先发半消息 → 执行本地事务 → 成功 Commit / 失败 Rollback → Broker 超时回查。或者用本地消息表：业务操作和插入消息表在同一个事务，后台定时扫描发送。"

## 死信队列（Dead Letter Queue）

**类别**：消息队列 / 可靠性 / 异常处理

### 一、什么是死信队列

死信队列（DLQ, Dead Letter Queue）是专门用来存放**无法被正常消费的消息**的队列。当一条消息反复消费失败、超过最大重试次数后，不会被直接丢弃，而是被转移到死信队列中，等待后续人工排查或自动补偿处理。

```
正常流程：
  Producer → Topic → Consumer → 消费成功 ✓

异常流程：
  Producer → Topic → Consumer → 消费失败
                              → 重试第 1 次 → 失败
                              → 重试第 2 次 → 失败
                              → ...
                              → 重试第 N 次 → 仍然失败
                              → 转入死信队列（DLQ）
```

**核心思想**：把"有毒消息"（Poison Message）隔离出来，不要让它阻塞正常消息的消费，同时也不丢弃，留着后续处理。

### 二、什么消息会变成死信

| 原因 | 说明 |
|------|------|
| **消费失败超过最大重试次数** | 最常见的原因。消息反复被消费者处理失败（如空指针、数据异常），超过重试上限后转入 DLQ |
| **消息过期（TTL 超时）** | 消息在队列中等待超过了设定的存活时间，没有被消费 |
| **队列满了被拒绝** | 队列达到最大长度限制，新消息被拒绝投递 |
| **消费者主动拒绝且不重新入队** | 消费者明确告诉 Broker "这条消息我不要了，也别再给我了" |

### 三、各 MQ 的死信机制

#### RocketMQ 的死信队列

```
RocketMQ 的重试机制：

  消息消费失败 → 返回 RECONSUME_LATER
  → Broker 自动将消息放入 %RETRY%{ConsumerGroup} 重试队列
  → 按延迟等级递增重试：1s, 5s, 10s, 30s, 1min, 2min, ... 最多 16 次
  → 16 次都失败 → 消息转入 %DLQ%{ConsumerGroup} 死信队列

关键点：
  - 重试队列 Topic：%RETRY%{ConsumerGroup}
  - 死信队列 Topic：%DLQ%{ConsumerGroup}
  - 每个 Consumer Group 有自己独立的死信队列
  - 死信队列中的消息默认保留 3 天（可配置）
  - 死信消息不会被自动消费，需要人工处理
```

```
RocketMQ 重试时间间隔（16 个等级）：

  第 1 次：10s    第 5 次：1min    第 9 次：7min     第 13 次：1h
  第 2 次：30s    第 6 次：2min    第 10 次：8min    第 14 次：2h
  第 3 次：1min   第 7 次：3min    第 11 次：9min    第 15 次：3h
  第 4 次：2min   第 8 次：4min    第 12 次：10min   第 16 次：4h（还失败 → 进死信）
```

#### RabbitMQ 的死信队列

```
RabbitMQ 中没有内置的重试队列概念，但提供了 Dead Letter Exchange（DLX）机制：

  声明队列时指定 DLX：
    x-dead-letter-exchange: dlx.exchange
    x-dead-letter-routing-key: dlx.routing.key

  消息变成死信的条件：
    ① 消费者 basic.reject / basic.nack 且 requeue=false
    ② 消息 TTL 过期
    ③ 队列达到最大长度

  触发后：消息被路由到 DLX 对应的死信队列

原理：
  ┌──────────────┐         ┌───────────────┐
  │ 正常 Exchange  │ ──→── │  正常 Queue     │
  └──────────────┘         │  (配置了 DLX)    │
                           └───────┬────────┘
                                   │ 消息被拒绝/过期/队列满
                                   ↓
                           ┌───────────────┐         ┌──────────────┐
                           │  DL Exchange   │ ──→── │  Dead Letter   │
                           │  (死信交换机)    │        │  Queue (DLQ)  │
                           └───────────────┘         └──────────────┘
```

```
RabbitMQ 利用 DLX 实现延迟重试（常用 pattern）：

  正常队列 → 消费失败 → 发到延迟队列（设 TTL）
  延迟队列 TTL 到期 → 通过 DLX 路由回正常队列 → 重新消费
  超过最大重试次数 → 发到最终的死信队列

  ┌──────┐    失败     ┌──────────┐   TTL 到期    ┌──────┐
  │正常队列│ ──────→  │延迟队列     │ ──────────→ │正常队列│ (重试)
  └──────┘           │(TTL=30s)  │              └──────┘
                     └──────────┘
  重试 N 次都失败 → 最终死信队列
```

#### Kafka 的死信队列

```
Kafka 原生不提供死信队列机制，需要业务侧自行实现：

  常见做法：
    消费失败 → 重试 N 次 → 仍然失败
    → 将消息发送到一个专门的 DLQ Topic（如 order_topic.DLQ）
    → 后续由人工或补偿服务消费 DLQ Topic

  代码模板（伪代码）：
    try {
        process(message);
        consumer.commitSync();
    } catch (Exception e) {
        retryCount++;
        if (retryCount > MAX_RETRY) {
            // 发到死信 Topic
            producer.send(new ProducerRecord("order_topic.DLQ", message));
            consumer.commitSync();  // 原 Topic 不再重试
        } else {
            // 重试逻辑
        }
    }
```

### 四、死信队列的处理方案

```
消息进入死信队列后怎么办？

方案 1：人工排查
  监控 DLQ 的消息量 → 报警 → 开发排查根因 → 修复 bug → 重新消费
  适合：偶发故障、未知异常

方案 2：自动补偿消费者
  专门写一个消费者订阅 DLQ
  → 对消息做特殊处理（降级逻辑、记录到 DB、发通知）
  适合：有明确降级策略的场景

方案 3：重新投递
  修复 bug 后，将 DLQ 中的消息重新发送回原 Topic
  → 让正常消费者重新消费
  适合：消费逻辑有 bug 但消息本身没问题

方案 4：归档存储
  将 DLQ 中的消息导出到 DB / 日志系统
  → 便于后续分析和审计
  适合：对账、合规场景
```

### 五、死信队列的最佳实践

```
1. 一定要设最大重试次数
   不要无限重试 → 会阻塞后续消息消费
   推荐：3~5 次（业务可配）

2. 重试间隔递增
   第一次 1s → 第二次 5s → 第三次 30s
   避免短时间内重复打爆下游

3. 一定要监控 DLQ
   DLQ 有消息堆积 → 立即告警
   否则消息悄悄进了死信没人管 = 丢消息

4. 死信消息要保留足够的上下文
   原 Topic、原消费者组、失败原因、重试次数、原始消息体
   方便排查

5. 幂等性
   死信消息被重新投递消费时要保证幂等
   因为消息可能已经被部分处理过了

6. 死信消息设过期时间
   不要让 DLQ 无限膨胀
   RocketMQ 默认 3 天，业务侧按需调整
```

### 六、面试话术

> **什么是死信队列？**
> "死信队列是专门存放无法被正常消费的消息的队列。消息消费失败超过最大重试次数、消息 TTL 过期、或队列满被拒绝时，就会变成死信，被转移到 DLQ 中。核心目的是把'有毒消息'隔离出来，不阻塞正常消费，同时保留消息用于后续排查和补偿。"
>
> **各 MQ 怎么实现的？**
> "RocketMQ 原生支持——消费失败自动进 %RETRY% 重试队列，16 次都失败后转入 %DLQ% 死信队列；RabbitMQ 通过 Dead Letter Exchange 机制实现，队列声明时配置 DLX，消息被拒绝或过期后路由到死信队列；Kafka 没有原生 DLQ，需要业务侧自己实现，消费失败超过阈值后手动发到一个 DLQ Topic。"
>
> **死信消息怎么处理？**
> "四种方式：人工排查修复后重新消费、自动补偿消费者做降级处理、修复 bug 后重新投递回原 Topic、归档到 DB 用于对账审计。关键是一定要监控 DLQ 的堆积量，否则消息悄悄变成死信等于变相丢消息。"
