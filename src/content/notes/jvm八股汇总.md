## 垃圾回收机制（GC）

**类别**：JVM / 内存管理 / 垃圾回收

### 一、为什么需要 GC

Java 程序员不需要手动 `free()` 内存，JVM 自动回收不再使用的对象。GC 的核心任务就是：**找出哪些对象是垃圾（不再被引用），然后回收它们占用的内存**。

### 二、怎么判断对象是垃圾

#### 方法 1：引用计数法（Java 不用）

每个对象维护一个引用计数器，被引用 +1，引用断开 -1，计数为 0 就是垃圾。

**致命缺陷**：循环引用。A 引用 B，B 引用 A，两者计数都不为 0，但实际都是垃圾。

#### 方法 2：可达性分析（Java 使用）

从一组 **GC Roots** 出发，沿引用链往下搜索，能到达的对象就是存活的，不可达的就是垃圾。

```
GC Roots 包括：
  1. 虚拟机栈（栈帧中的局部变量表）引用的对象
  2. 方法区中类静态属性引用的对象
  3. 方法区中常量引用的对象
  4. 本地方法栈中 JNI（Native 方法）引用的对象
  5. 被 synchronized 持有的对象
  6. JVM 内部引用（基本类型的 Class 对象、系统类加载器等）
```

```
GC Root → A → B → C    （A、B、C 可达，存活）
           ↓
           D            （D 可达，存活）

E → F → E              （E、F 虽然互相引用，但从 GC Root 不可达 → 垃圾）
```

### 三、JVM 堆内存分代模型

```
堆内存
├── 新生代（Young Generation）—— 占堆 1/3
│   ├── Eden 区（占新生代 80%）
│   ├── Survivor From（S0）（占 10%）
│   └── Survivor To（S1）（占 10%）
└── 老年代（Old Generation）—— 占堆 2/3
```

**为什么要分代**：绝大部分对象"朝生夕死"（在 Eden 创建，很快就不再使用）。分代后可以对不同区域用不同的回收策略——新生代用轻量快速的算法，老年代用更彻底的算法。

### 四、GC 分类

| GC 类型 | 回收范围 | 触发条件 | 频率 |
|---------|---------|---------|------|
| **Minor GC（Young GC）** | 新生代（Eden + Survivor） | Eden 区满 | 频繁 |
| **Major GC（Old GC）** | 老年代 | 老年代空间不足 | 较少 |
| **Full GC** | 整个堆 + 方法区 | 老年代满 / 元空间满 / System.gc() / 晋升失败等 | 很少，但很慢 |

### 五、新生代 GC 流程（Minor GC）

```
第 1 次 GC：
  Eden 区满 → 触发 Minor GC
  存活对象复制到 S0，年龄 = 1
  Eden 清空

第 2 次 GC：
  Eden 区又满 → 触发 Minor GC
  Eden + S0 中的存活对象复制到 S1，年龄 +1
  Eden 和 S0 清空

第 3 次 GC：
  Eden + S1 中的存活对象复制到 S0，年龄 +1
  Eden 和 S1 清空
  （S0 和 S1 交替使用，始终有一个是空的）

当对象年龄达到阈值（默认 15）→ 晋升到老年代
```

**对象提前晋升的情况**：
- 年龄达到阈值（默认 15，`-XX:MaxTenuringThreshold`）
- **动态年龄判断**：Survivor 中相同年龄的对象总大小 > Survivor 空间的 50%，则该年龄及以上的对象直接晋升
- **大对象直接进老年代**：超过 `-XX:PretenureSizeThreshold` 的对象直接分配到老年代，避免在新生代来回复制

### 六、垃圾回收算法

#### 1. 标记-清除（Mark-Sweep）

```
第 1 步：标记所有从 GC Root 可达的存活对象
第 2 步：清除所有未标记的对象

优点：简单
缺点：产生内存碎片（已回收的空间不连续），大对象可能找不到连续空间
```

#### 2. 标记-复制（Copying）

```
把内存分成两块，每次只用一块：
第 1 步：标记存活对象
第 2 步：把存活对象复制到另一块
第 3 步：整块清空当前使用的内存

优点：无碎片，分配快（指针碰撞）
缺点：可用内存只有一半
适用：新生代（因为大部分对象都死了，复制的少，效率高）
       → Eden + S0/S1 就是这个思路的优化版（不是 1:1 分，而是 8:1:1）
```

#### 3. 标记-整理（Mark-Compact）

```
第 1 步：标记存活对象
第 2 步：把存活对象向内存一端移动压缩
第 3 步：清除边界以外的内存

优点：无碎片
缺点：移动对象有开销，需要更新引用
适用：老年代（对象存活率高，复制不划算，整理更合适）
```

#### 算法对比

| 算法 | 碎片 | 效率 | 空间利用率 | 适用区域 |
|------|------|------|-----------|---------|
| 标记-清除 | 有 | 中 | 高 | 老年代（CMS） |
| 标记-复制 | 无 | 高（存活少时） | 低（一半浪费） | 新生代 |
| 标记-整理 | 无 | 低（要移动） | 高 | 老年代 |

## STW（Stop The World）

**类别**：JVM / 垃圾回收 / 性能

### 什么是 STW

GC 执行时**暂停所有用户线程**，整个应用"冻住"，等 GC 完成后再恢复。这段暂停时间就叫 **Stop The World**。

### 为什么需要 STW

可达性分析需要一个**一致的快照**——在分析引用关系的时候，对象之间的引用不能在变。如果用户线程还在跑，一边分析引用一边修改引用，结果就不准确了（可能把活对象当垃圾回收了）。

### STW 的影响

```
STW 时间长 → 用户感知到卡顿（接口超时、页面卡死）

不同 GC 的 STW 表现：
  Serial GC：     全程 STW（单线程回收）
  Parallel GC：   全程 STW（多线程回收，但还是全停）
  CMS：           大部分并发，只有初始标记和重新标记短暂 STW
  G1：            可控的 STW（目标停顿时间可配置）
  ZGC：           STW < 1ms（几乎无感知）
```

### 安全点（Safepoint）

JVM 不是随时都能 STW 的，必须等所有线程到达**安全点**才能暂停。安全点是代码中特定的位置（方法调用、循环跳转、异常跳转等），在这些位置线程的状态是确定的，可以安全暂停。

```
如果某个线程在执行一个很长的循环且循环内没有安全点
→ 其他线程已经到达安全点在等它
→ STW 时间被拉长
→ 这是一个实际中的坑（可数循环可能不放安全点）
```

## 三色标记法

**类别**：JVM / 垃圾回收 / 并发标记

### 为什么需要三色标记法

传统的标记过程需要 STW——全停下来标记完才能继续。为了**减少 STW 时间**，CMS 和 G1 等垃圾回收器引入了**并发标记**：标记过程和用户线程同时运行。三色标记法就是并发标记的核心算法。

### 三种颜色的含义

```
白色：还没被 GC 访问过的对象
      → GC 结束后仍然是白色的对象 = 垃圾，要被回收

灰色：自己被访问了，但它引用的对象还没全部访问完
      → 相当于"正在处理中"的对象

黑色：自己被访问了，且它引用的所有对象也都被访问了
      → 确认存活，不会被回收
      → 不会再被重新扫描
```

### 标记过程

```
初始状态：所有对象都是白色，GC Root 入队标记为灰色

循环处理：
  1. 从灰色集合中取出一个对象
  2. 将它引用的所有白色对象标记为灰色
  3. 将它自己标记为黑色
  4. 重复，直到灰色集合为空

结束：黑色 = 存活，白色 = 垃圾

示例：
  GC Root → A → B → C
                ↓
                D

  初始：Root(灰) A(白) B(白) C(白) D(白)
  处理 Root：→ A 变灰，Root 变黑
  处理 A：  → B 变灰，A 变黑
  处理 B：  → C 变灰、D 变灰，B 变黑
  处理 C：  → C 变黑
  处理 D：  → D 变黑
  结束：全黑，没有白色，全部存活
```

### 并发标记的问题：漏标和多标

标记过程和用户线程并发运行时，用户线程可能修改引用关系，导致两种问题：

#### 多标（浮动垃圾）—— 不严重

```
标记过程中：
  对象 A 已经被标记为黑色（存活）
  用户线程断开了对 A 的引用 → A 实际已经是垃圾了
  但 GC 不会再扫描黑色对象 → A 在本次 GC 中不会被回收

结果：A 成了"浮动垃圾"，要等下次 GC 才能回收
→ 不影响正确性，只是浪费一点空间，可以接受
```

#### 漏标（对象消失）—— 严重！

```
漏标发生需要同时满足两个条件：
  条件 1：一个黑色对象新增了对白色对象的引用
  条件 2：所有灰色对象到该白色对象的引用都断开了

例：
  B(黑) ----新增引用---→ C(白)     ← 条件 1
  A(灰) --断开引用--✕-→ C(白)     ← 条件 2

  C 是白色，没有灰色对象引用它，B 是黑色不会再扫描
  → C 不会被标记 → 被当成垃圾回收了
  → 但 C 实际被 B 引用着，是活的！
  → 回收了活对象 = 程序崩溃！
```

### 解决漏标：两种写屏障

**破坏条件 1：增量更新（Incremental Update）—— CMS 使用**

```
思路：记录所有"黑色对象新增指向白色对象的引用"
      在重新标记阶段把这些黑色对象重新扫描一遍

当黑色对象 B 新增引用指向白色对象 C 时：
  → 写屏障拦截这个赋值操作
  → 记录下 B → C 这个新引用
  → 重新标记时，把 B 当作灰色重新处理

效果：破坏了条件 1（黑色对象新增引用会被感知到）
```

**破坏条件 2：原始快照（SATB, Snapshot At The Beginning）—— G1 使用**

```
思路：当灰色对象删除引用时，把被删除的引用记录下来
      保证被删引用指向的对象不会丢失

当灰色对象 A 删除对白色对象 C 的引用时：
  → 写屏障拦截这个删除操作
  → 把 C 标记为灰色（或记录下来后续处理）

效果：破坏了条件 2（灰色对象删除引用时，被引用的对象不会变成不可达）
      代价是可能多标一些对象（本来该回收的没回收），但不会漏标
```

**两种方案对比**：

| | 增量更新（CMS） | SATB（G1） |
|---|---|---|
| 拦截时机 | 黑色对象新增引用时 | 灰色对象删除引用时 |
| 重新标记工作量 | 较大（要重新扫描被记录的黑色对象） | 较小 |
| 浮动垃圾 | 少 | 多一些 |
| 实现复杂度 | 中 | 中 |

## 垃圾回收器

**类别**：JVM / 垃圾回收 / 回收器实现

### 回收器总览

```
新生代回收器           老年代回收器
┌────────────┐        ┌────────────┐
│ Serial      │───────→│ Serial Old  │
│ (单线程复制) │        │ (单线程整理) │
└────────────┘        └────────────┘

┌────────────┐        ┌────────────┐
│ ParNew      │───────→│ CMS         │
│ (多线程复制) │        │ (并发标记清除)│
└────────────┘        └────────────┘

┌────────────┐        ┌────────────┐
│ Parallel    │───────→│ Parallel Old│
│ Scavenge    │        │ (多线程整理) │
│ (多线程复制) │        │             │
└────────────┘        └────────────┘

┌────────────────────────────────────┐
│ G1（不分代，Region 化）              │
│ 整堆回收，可控停顿                    │
└────────────────────────────────────┘

┌────────────────────────────────────┐
│ ZGC（JDK 11+，超低延迟）             │
│ 整堆回收，STW < 1ms                 │
└────────────────────────────────────┘
```

### 1. Serial / Serial Old

```
单线程回收，全程 STW

新生代：标记-复制
老年代：标记-整理

优点：简单高效（单核场景）
缺点：STW 时间长，不适合多核服务器
适用：客户端模式（-client）、小堆内存
```

### 2. Parallel Scavenge / Parallel Old（JDK 8 默认）

```
多线程回收，全程 STW

新生代：标记-复制（多线程并行）
老年代：标记-整理（多线程并行）

优点：吞吐量高（CPU 时间花在应用上的比例高）
缺点：STW 时间仍然较长
适用：后台计算任务、对延迟不敏感的场景

关键参数：
  -XX:MaxGCPauseMillis=<N>   最大停顿时间目标
  -XX:GCTimeRatio=<N>        吞吐量目标（默认 99，即 GC 占 1%）
```

### 3. ParNew + CMS

```
ParNew（新生代）：多线程标记-复制，STW
CMS（老年代）：并发标记-清除，大部分阶段不 STW
```

**CMS 的四个阶段**：

```
阶段 1：初始标记（Initial Mark）     → STW ✦
  只标记 GC Root 直接引用的对象，很快

阶段 2：并发标记（Concurrent Mark）  → 和用户线程并发 ✓
  从初始标记的对象出发遍历整个对象图
  使用三色标记法 + 增量更新写屏障

阶段 3：重新标记（Remark）           → STW ✦
  修正并发标记期间用户线程修改的引用
  处理增量更新记录的"黑色新增引用"

阶段 4：并发清除（Concurrent Sweep） → 和用户线程并发 ✓
  清除未标记的垃圾对象
```

**CMS 的问题**：

| 问题 | 原因 | 后果 |
|------|------|------|
| **内存碎片** | 标记-清除算法不整理 | 大对象分配失败 → 触发 Full GC（退化到 Serial Old） |
| **浮动垃圾** | 并发清除阶段产生新垃圾 | 本次 GC 无法回收，需等下次 |
| **CPU 敏感** | 并发阶段占用 CPU | 和用户线程抢 CPU |
| **Concurrent Mode Failure** | 并发清除期间老年代满了 | 退化到 Serial Old 全停顿回收 |

### 4. G1（Garbage First）—— JDK 9+ 默认

```
核心思想：把堆划分为大小相等的 Region（默认 2048 个），
         每个 Region 可以动态扮演 Eden / Survivor / Old / Humongous
         优先回收垃圾最多的 Region（Garbage First 名字由来）

┌─────┬─────┬─────┬─────┬─────┬─────┐
│ Eden│ Old │ Sur │ Eden│  H  │ Old │
├─────┼─────┼─────┼─────┼─────┼─────┤
│ Old │ Eden│ Old │ Sur │ Old │Eden │
├─────┼─────┼─────┼─────┼─────┼─────┤
│ Old │ Old │Eden │ Old │ Eden│ Old │
└─────┴─────┴─────┴─────┴─────┴─────┘
H = Humongous（大对象，占多个连续 Region）
```

**G1 的回收过程**：

```
Young GC：
  Eden Region 满 → 存活对象复制到 Survivor Region → 清空 Eden
  全程 STW，但只回收 Young Region，范围小，速度快

Mixed GC（混合回收）：
  阶段 1：初始标记（STW，搭在 Young GC 上一起做）
  阶段 2：并发标记（和用户线程并发，三色标记 + SATB）
  阶段 3：最终标记（STW，处理 SATB 记录）
  阶段 4：筛选回收（STW）
    → 对所有 Region 按回收价值排序
    → 在目标停顿时间内选择回收价值最高的若干 Region
    → 存活对象复制到空 Region，清空被回收的 Region
```

**G1 的核心优势**：

| 特性 | 说明 |
|------|------|
| **可预测的停顿** | `-XX:MaxGCPauseMillis=200`（默认 200ms），G1 会尽量控制 STW 不超过目标值 |
| **Region 化** | 不再物理分代，Region 动态分配角色，大小灵活 |
| **优先回收** | 优先回收垃圾比例高的 Region，效率高 |
| **整理而非清除** | Region 间是复制算法 → 无碎片 |

### 5. ZGC（JDK 11+）

```
核心特性：STW < 1ms（几乎无停顿）

关键技术：
  - 着色指针（Colored Pointers）：在指针里存标记信息，不需要遍历对象头
  - 读屏障（Load Barrier）：读对象时检查并修正指针
  - 并发整理：标记和整理都和用户线程并发

适用：超大堆（TB 级）、对延迟极其敏感的场景
```

### 回收器选择指南

| 场景 | 推荐回收器 | 原因 |
|------|-----------|------|
| 小堆、客户端 | Serial | 简单高效 |
| 大吞吐量、后台计算 | Parallel Scavenge | 吞吐优先 |
| Web 应用、延迟敏感 | G1 | 可控停顿，JDK 9+ 默认 |
| 超低延迟、大堆 | ZGC | STW < 1ms |
| 遗留系统（JDK 8） | ParNew + CMS | 低延迟（但有碎片问题） |

## 面试回答模板

> **判断垃圾**："Java 用可达性分析——从 GC Roots（虚拟机栈、静态属性、常量、JNI 引用等）出发，不可达的对象就是垃圾。不用引用计数是因为解决不了循环引用。"
>
> **回收算法**："三种基础算法：标记-清除（有碎片）、标记-复制（新生代用，无碎片但浪费空间）、标记-整理（老年代用，无碎片但要移动对象）。"
>
> **分代模型**："堆分新生代和老年代。新生代 Eden + S0/S1 用复制算法，大部分对象朝生夕死所以效率高。年龄到阈值或 Survivor 空间不够就晋升到老年代。"
>
> **STW**："GC 需要暂停用户线程来保证引用关系的一致性，这就是 STW。减少 STW 是所有现代 GC 的目标——CMS 用并发标记减少 STW 到两个短阶段，G1 用 Region 化 + 优先回收控制停顿时间，ZGC 做到 STW < 1ms。"
>
> **三色标记**："并发标记的核心算法。白色未访问、灰色处理中、黑色已完成。并发标记的风险是漏标——黑色对象新增引用白色且灰色对象删除引用白色时会发生。CMS 用增量更新（记录黑色新增引用，重新标记时重扫）解决，G1 用 SATB（记录灰色删除引用，保证被引用对象不丢失）解决。"
>
> **回收器**："JDK 8 默认 Parallel Scavenge + Parallel Old，吞吐优先。JDK 9+ 默认 G1，Region 化 + 可控停顿。CMS 已废弃但面试常问——四阶段（初始标记 STW → 并发标记 → 重新标记 STW → 并发清除），问题是碎片和 Concurrent Mode Failure。ZGC 是终极方案，着色指针 + 读屏障做到 < 1ms 停顿。"

## 类加载机制

**类别**：JVM / 类加载 / 生命周期

### 一、什么是类加载

Java 源码编译后生成 `.class` 字节码文件，JVM 不会一启动就加载所有类，而是在**第一次使用时**才把 `.class` 文件加载到内存、解析成运行时数据结构、最终生成可以使用的 `Class` 对象。这个过程就是类加载。

### 二、类的生命周期（7 个阶段）

```
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
       └── 连接（Linking）──┘
```

#### 1. 加载（Loading）

```
做三件事：
  ① 通过类的全限定名找到 .class 文件（从磁盘、JAR、网络等）
  ② 将字节流转化为方法区的运行时数据结构
  ③ 在堆中生成一个 java.lang.Class 对象，作为方法区数据的访问入口
```

#### 2. 验证（Verification）

```
确保 .class 文件的字节流符合 JVM 规范，不会危害虚拟机安全：
  - 文件格式验证：魔数 0xCAFEBABE、版本号等
  - 元数据验证：语义检查（是否有父类、是否继承了 final 类等）
  - 字节码验证：数据流和控制流分析，确保语义合法
  - 符号引用验证：确保解析阶段能找到引用的类、字段、方法
```

#### 3. 准备（Preparation）

```
为类的静态变量分配内存并设置默认零值（不是代码中赋的值）：
  static int a = 10;
  → 准备阶段：a = 0（int 的零值）
  → 初始化阶段：a = 10（真正赋值）

特殊情况：static final 常量在准备阶段就直接赋值：
  static final int b = 20;
  → 准备阶段：b = 20（编译期常量，直接赋值）
```

#### 4. 解析（Resolution）

```
将常量池中的符号引用替换为直接引用：
  符号引用：用字符串表示的类名、方法名（如 "java/lang/Object"）
  直接引用：内存地址或偏移量（可以直接定位到目标）
```

#### 5. 初始化（Initialization）

```
执行类构造器 <clinit>() 方法：
  - 按顺序执行类中所有静态变量的赋值语句和静态代码块
  - JVM 保证 <clinit>() 是线程安全的（加锁，只执行一次）

这也是为什么"静态内部类实现单例"是线程安全的：
  类初始化时 JVM 会加锁，保证只有一个线程能执行 <clinit>()
```

### 三、什么时候会触发类初始化

JVM 规范定义了 **6 种必须初始化** 的情况（主动引用）：

```
1. new 对象、读/写静态字段、调用静态方法
2. 反射调用（Class.forName()）
3. 初始化子类时发现父类还没初始化 → 先初始化父类
4. JVM 启动时的主类（包含 main() 方法的类）
5. MethodHandle 解析结果对应的类
6. 接口中定义了 default 方法，实现类初始化时先初始化接口
```

**不会触发初始化的情况（被动引用）**：

```
1. 通过子类引用父类的静态字段 → 只初始化父类，不初始化子类
2. 创建数组：MyClass[] arr = new MyClass[10] → 不初始化 MyClass
3. 引用类的 static final 常量 → 常量在编译期已经进入常量池，不需要初始化类
```

## 双亲委派机制

**类别**：JVM / 类加载 / 类加载器

### 一、类加载器的层次结构

```
                ┌───────────────────────┐
                │ Bootstrap ClassLoader  │  启动类加载器
                │ 加载 rt.jar 等核心类库  │  （C++ 实现，Java 中为 null）
                │ java.lang.*、java.util.*│
                └───────────┬───────────┘
                            │ 父加载器
                ┌───────────▼───────────┐
                │ Extension ClassLoader  │  扩展类加载器
                │ 加载 jre/lib/ext 目录   │  （JDK 9+ 改名 Platform ClassLoader）
                └───────────┬───────────┘
                            │ 父加载器
                ┌───────────▼───────────┐
                │ Application ClassLoader│  应用类加载器
                │ 加载 classpath 下的类   │  （用户代码的默认加载器）
                └───────────┬───────────┘
                            │ 父加载器
                ┌───────────▼───────────┐
                │ Custom ClassLoader     │  自定义类加载器
                │ 用户自己实现            │
                └───────────────────────┘
```

### 二、双亲委派的工作流程

```
当一个类加载器收到加载请求时：

  ① 先检查这个类是否已经被加载过 → 加载过就直接返回
  ② 没加载过 → 委派给父加载器去加载（递归向上）
  ③ 父加载器也没加载过 → 继续委派给更上层的父加载器
  ④ 一直到 Bootstrap ClassLoader
  ⑤ 如果 Bootstrap 能加载 → 加载并返回
  ⑥ 如果 Bootstrap 加载不了 → 回到子加载器尝试加载
  ⑦ 如果一路回到发起请求的加载器都加载不了 → ClassNotFoundException
```

```
示例：加载 com.example.MyClass

  Custom ClassLoader："我先问问我爸"
    → Application ClassLoader："我先问问我爸"
      → Extension ClassLoader："我先问问我爸"
        → Bootstrap ClassLoader："这不是我管的核心类，我加载不了"
      ← Extension ClassLoader："也不在我的 ext 目录，我也不行"
    ← Application ClassLoader："在 classpath 下找到了！我来加载"
  返回 Class 对象
```

**源码（简化版）**：

```java
protected Class<?> loadClass(String name, boolean resolve) {
    // 1. 检查是否已加载
    Class<?> c = findLoadedClass(name);
    if (c == null) {
        try {
            // 2. 委派给父加载器
            if (parent != null) {
                c = parent.loadClass(name, false);
            } else {
                // 到顶了，用 Bootstrap 加载
                c = findBootstrapClassOrNull(name);
            }
        } catch (ClassNotFoundException e) {
            // 父加载器加载失败
        }
        if (c == null) {
            // 3. 父加载器加载不了，自己加载
            c = findClass(name);
        }
    }
    return c;
}
```

### 三、为什么要双亲委派

**核心目的：保证类的唯一性和安全性。**

#### 1. 避免重复加载

```
没有双亲委派：
  Application ClassLoader 加载了 java.lang.String → String_A
  Custom ClassLoader 也加载了 java.lang.String → String_B
  String_A ≠ String_B（不同类加载器加载的同名类不是同一个类）
  → 类型混乱

有双亲委派：
  不管谁发起加载 java.lang.String，最终都委派到 Bootstrap 加载
  → 全 JVM 只有一个 String 类
```

#### 2. 防止核心类被篡改

```
如果有人写了一个恶意的 java.lang.String：
  没有双亲委派 → 恶意 String 可能被加载 → 安全漏洞
  有双亲委派 → 委派到 Bootstrap，Bootstrap 已经加载了真正的 String
              → 恶意类永远不会被加载
```

### 四、打破双亲委派

有些场景**需要打破**双亲委派：

#### 场景 1：SPI 机制（Service Provider Interface）

```
问题：
  JDBC 的 Driver 接口定义在 rt.jar（Bootstrap 加载）
  但 Driver 的实现类（如 MySQL 的 com.mysql.cj.jdbc.Driver）在 classpath（Application 加载）
  Bootstrap 加载 Driver 时需要用到实现类 → 但 Bootstrap 看不到 Application 的类

解决：线程上下文类加载器（Thread Context ClassLoader）
  → 在 Bootstrap 加载的代码中，通过 Thread.currentThread().getContextClassLoader()
     获取 Application ClassLoader 来加载 SPI 实现类
  → "父加载器委托子加载器"，打破了向上委派的规则
```

#### 场景 2：热部署 / 热加载

```
Tomcat 需要支持：
  - 不同 Web 应用加载同名但不同版本的类（如两个应用用了不同版本的 Spring）
  - 不重启服务器更新某个应用的类

做法：
  每个 Web 应用一个独立的 WebAppClassLoader
  WebAppClassLoader 先自己加载（打破委派），加载不了再委派给父加载器
  → 不同应用的同名类互相隔离
```

#### 场景 3：OSGi 模块化

```
OSGi 的类加载是网状结构，不是树状的：
  每个 Bundle 有自己的类加载器
  Bundle 之间可以声明导入/导出包
  → 完全打破了双亲委派的树状层级
```

### 五、面试常见追问

**Q1："JVM 中两个类相等的条件是什么？"**

> "两个条件都要满足：①全限定类名相同；②加载它们的**类加载器**相同。同一个 .class 文件被不同的类加载器加载，产生的是两个不同的类，`instanceof` 判断会返回 false。"

**Q2："自定义类加载器怎么写？"**

> "继承 `ClassLoader`，重写 `findClass()` 方法（不是 `loadClass()`）。在 `findClass()` 里自己读取 .class 文件的字节流，调用 `defineClass()` 转换成 Class 对象。重写 `findClass()` 而不是 `loadClass()` 就能保持双亲委派机制。如果要打破双亲委派，才需要重写 `loadClass()`。"

**Q3："Tomcat 为什么要打破双亲委派？"**

> "两个原因：一是**隔离**——不同 Web 应用可能用了同名但不同版本的类（比如不同版本的 Spring），如果走双亲委派会被同一个加载器加载同一个版本，无法共存；二是**热加载**——重新部署应用时只需要丢弃旧的 WebAppClassLoader 创建新的，不影响其他应用。"

## 面试回答模板（类加载 + 双亲委派）

> **类加载过程**："类的生命周期分 7 个阶段：加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载。其中验证、准备、解析合称连接。加载阶段找到 .class 文件并在堆中生成 Class 对象；准备阶段给静态变量分配内存赋零值（static final 常量直接赋值）；初始化阶段执行 `<clinit>()`，JVM 保证线程安全且只执行一次。"
>
> **双亲委派**："类加载器分四层：Bootstrap（核心类）→ Extension（扩展类）→ Application（classpath）→ 自定义。加载类时先委派给父加载器，父加载器加载不了才自己加载。目的是保证核心类的唯一性和安全性——不管谁请求加载 `java.lang.String`，最终都由 Bootstrap 加载，防止核心类被篡改。"
>
> **打破双亲委派**："三个典型场景：SPI 机制用线程上下文类加载器让 Bootstrap 加载的接口找到 Application 加载的实现类；Tomcat 用独立的 WebAppClassLoader 优先自己加载实现应用间类隔离和热部署；OSGi 用网状类加载实现模块化。"
