claude code的六层记忆架构机制：
1、休眠重塑auto dream 2、摘要记忆Session memory 3、长期记忆Memdir 4、工作记忆 task store 5、短期记忆 conversation 6、指令记忆 CLAUDE.md。这六个维度层层递进

这六层记忆架构解决了三个核心问题：
长程对话的上下文遗忘问题、多终端和团队之间的同步问题、以及token的预算控制问题

### 第一层 指令记忆

“它对应的就是claude.md文件，这是一套多层级、优先级递增的静态指令加载系统，可以理解他为你写好的规矩，告诉ai用什么风格做事”

指令记忆的核心载体就是CLAUDE.md文件族，可以把它理解问AI的行为准则手册
具体来说，他一共分为四层，从低到高分别是：
1、Manager，路径在etc下的claude-code/CLAUDE.md，这是全局策略，通常由组织管理员设定，所有用户强制适用
2、user，路径在个人目录home下的.claude/CLAUDE.md，这是用户自己的私有全局指令，横跨所有项目生效
3、Project，项目根目录下的CLAUDE.md，这是代码库的、团队共享的项目级的记忆指令
4、Local，CLAUDE.local.md，这是你的私有项目指令，不会检入版本控制

我感觉这里最值得注意的是他的加载顺序。系统从当前工作目录向根目录遍历所有文件，然后反转顺序，从根到CWD的顺序处理，这意味着离当前工作目录越近的规则文件，加载越靠后。我觉得这样会让模型对靠后加载的记忆的关注度越高（最后加载的规则优先级较高），他既保证了全局策略的基础约束力，又给了每个项目足够的灵活性

除了上述的加载逻辑，指令记忆还支持三种扩展机制，但是这部分我还没看完，现在不太好讲。
我感觉从这一层可以看出来claude的记忆理念：选择性、按需、分层注入，claude的记忆不是全部一股脑加载完的

在这里我要强调一个关键的架构设计----**双轨注入**  ，所有的记忆内容并不是通过system prompt注入模型的，claude code将记忆注入分为了两个独立的通道，通道A负责注入**指令记忆** （CLAUDE.md的内容），走的是对话消息通道（作为对话列表的第一条user meta message注入）；通道B负责注入memdir的行为规范，这个才是放进system prompt数组里的
为什么要分成两个通道？我的理解是指令记忆是用户写的、内容多变且频繁更新的，而行为规范是系统内建的，相对稳定的，通道B的内容只需要注入一次就可以缓存下来了，如果不做区分的话，由于CLAUDE.md的多变，可能会导致KV Cache break的情况


### 第二层 短期记忆
他是当前会话里的完整对话历史，每条消息都存在内存中，没有经过压缩

### 第三层 工作记忆
他跟当前正在执行的任务相关，比如任务的进度、偏移量、投机响应状态这些

### 第四层 叫长期记忆
“这是最核心的部分，他基于磁盘上的markdown文件，构建了一个分层的知识库引擎，系统会自动在用户目录下创建专门的记忆文件夹，按照用户画像、行为反馈、项目上下文、外部引用，这四种类型来组织知识”
这是claude code最核心的记忆模块，文件默认存放在~/.claude/projects/<sanitized-root>/memory/
下。
claude code为了明确什么是应该记住的，什么是不应该记住的，设计了四个应该要记忆的类型：
1、user类型，这是关于用户本人的。比如角色、目标、技能水平、工作习惯等用户画像，让AI可以更个性化的协作
2、feedback，用户对AI行为的纠正和确认，这一步有个特别值得注意的设计，它不仅记录哪里做错了，还记录哪里做对了。why?因为如果只记录错误，模型会变得过度保守，记录成功的反馈是为了告诉AI这样做是对的，让以后可以继续这么做。
3、project类型，这是不可从代码推导的项目上下文，比如项目的截止日期、设计目标、团队协作约定
4、reference类型，外部系统的指针
同时也规定了什么是不能存的：代码模式、架构分析、文件路径、Git历史、调试方案，why?因为他们可以从代码本身推导出来，而且具备时效性。如果存有一个副本并且过时了，可能会导致严重的后果。
这两套组合拳打下来，让记忆系统保证一个高信噪比的状态，避免变成一个什么都往里塞的注意力涣散的记事本

长期记忆在存储上采用了两层结构。
第一层是Memory.md，这是一个纯索引文件，每行就是一个指向具体记忆文件的链接加上一句话摘要，整个文件限制在200行以内、25KB以内。
第二层就是具体的记忆文件了，每个文件都有标准的格式，包含名称、描述、类型。

那么问题来了，memory.md会始终加载到上下文里，如果记忆文件有几十上百个，怎么决定加载哪些呢？claude code采用了一种叫“异步预加载流程”：对话开始时，系统会异步起动一个prefetch的预加载流程（注意是异步的，跟模型的响应并行执行，不会阻塞主流程）。预加载的过程又是这样的：先扫描记忆目录下的所有md文件，但是每个文件只读前30行的内容提取出描述信息，然后调用sonnet做一次side query（旁路查询），让sonnet判断哪些记忆跟当前上下文最相关，sonnet的选择有几个约束：最多返回5篇；不确定的不选；最近使用过的工具的相关文档优先级会被降低，避免工具文档污染记忆召回。
这里还有一个记忆新鲜度系统，召回的记忆都会标注他的年龄，这个年龄使用自然语言描述的（因为模型不擅长日起计算，用自然语言对ai更友好），记忆超过一天，会附带一个警告让AI引用之前先验证。我的理解是，他是为了解决“记忆存在，但是不等于他现在还存在时效性”
上面讲的是记忆的存储和召回，那记忆是怎么写进去的？
这就要说到自动记忆提取机制（Extract Memory）：每一轮对话完成后，主agent不会自己去写记忆（会干扰到主agent的上下文）而是fork一个子agent出来回顾所有对话内容，然后把值得长期保留的信息存到记忆文件里，这个依旧是异步调用非阻塞，用户感知不到。但如果主agent在最近的对话中直接修改了记忆文件，那么子agent会跳过该次记忆提取，这避免了主agnet和子agent的记忆冲突
子代理的prompt设计也很有讲究，它规定了一个两回合策略：第一轮，并行发出所有需要读取的文件请求；第二轮，并行发出所有写入请求。这样可以保证最大化并行效率。
子agent的权限也被严格限定：可以读任意文件、可以grep搜索，但写操作被限制在memdir路径下的文件里，不能调用mcp或者skill避免造成用户感知不到的错误后果，也不能触发其他agent（避免陷入调用循环）

###  第五层，叫摘要记忆 
"这也就是压缩级记忆，当对话太长，Token快要超窗时，系统会触发压缩，但是claude code不是简单让llm压缩就完事了，他引入了一个叫“session memory”的机制，通过后台子agent持续维护一份会话笔记，压缩的时候直接用这份笔记替代临时生成的摘要"
当对话越来越长的时候，系统不得不触发压缩，传统的做法是让LLM生成一段针对历史消息的有损压缩，但这种方式的问题是，摘要是事后一次性生成的，不可避免会丢失细节。
session memory则完全不同，他不是等到压缩的时才生成摘要，而是在对话过程中持续维护一份会话笔记。具体来说，fork一个子agent持续更新一个叫session - memory.md的文件，这个文件有固定的章节结构，包括：会话标题、当前工作状态、任务规格、涉及的关键文件和函数、工作流步骤、遇到的错误和修正。触发条件是（上下文的token达到某个阈值 && 自上次更新以来有足够的token增长）保证笔记在有足够新内容的时候才更新，不会每轮都触发。当压缩真正发生的时候，session memory compact不会让llm从头生成摘要，而是直接用session - memory.md文件作为压缩后保留的上下文，这样可以保留足够的细节（渐进式维护）
然而压缩时到底保留什么消息，claude code用了calculateMessagesToKeepIndex算法，这个具体的我还没看。
我学习了一下这个session memory compact的流程。
主要分为三层，第一层是micro-compact，他将上下文中调用工具的结果用一个特殊的占位符来表示；第二层是auto-compact，负责压缩内容；第三层是context-collapse
第一层触发最频繁，超过soft阈值就调用；第二层是token接近auto阈值时自动触发，第三层则是特殊feature，普通用户用不了，必须手动，并且跟第二层的策略是互斥的，当开启context-collapse时就不会采用auto-compact，并且context-collapse会阻塞对话，对用户体验影响比较大。
在fork子agent来做compact的时候会检查上下文的来源,因为如果这个子 Agent 自己的上下文也满了，又触发 auto-compact……就无限套娃了。所以代码里强制：`querySource === 'compact'` 的请求直接跳过 auto-compact。


### 第六层 休眠重塑记忆
"离线级记忆，当满足一定时间和会话次数的时候，系统会自动进入一个整合流程，把碎片化的记忆清理、合并、去除矛盾，然后更新全局索引"
Extract memory是每轮对话记日记，那么AutoDream就是定期复盘整理
他的触发条件是“双重门控”：至少距离上次整合过去24小时,并且在这期间至少有5个不同的会话产生了新记忆，才会触发AutoDream。why?因为整合是一个重量级操作，频繁触发会导致成本跟延迟都很高。
触发后的流程分为四个阶段：1、Orient定向探索，子agent浏览记忆目录，看看有哪些文件、memory.md索引长什么样、有没有重复或者近似的主题。 2、Gather信息收集，查看最近的日志，检查是否有跟代码库当前状态矛盾的旧记忆 3、consolidate整合，把新的信号覆写到已有的记忆文件里，被推翻的旧事实直接删掉，直接删除 4、prune and index修剪与更新索引，确保memory.md在200行以内，每行索引不超过150个字符。
为了防止多个claude code实例同时触发AutoDream，系统使用了一个锁文件，锁文件的修改时间就是上次整合的时间，文件内容就是持有者的进程id。实例获取锁的时候会有一个CAS机制。
