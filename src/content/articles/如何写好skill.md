## 一、开场定义（30秒讲清楚 Skill 是什么）

Skill 是 AI Agent 的能力扩展单元，本质上解决两个问题：**模型上下文长度有限** 和 **能力复用**。

可以这样讲：

> "大模型的上下文窗口是有限的，不可能把所有业务知识一次性塞进去。Skill 的设计思路是**渐进披露**——模型先看一句话的触发条件判断要不要用，决定用了再加载详细指令，需要查细节时再去读附件。这样既省 token，又让每个能力模块可以独立维护和分享。"

---

## 二、核心设计原则（面试重点，体现设计能力）

### 2.1 单一职责 + 可组合

**一句话**：一个 Skill 只做一件事，复杂流程由 Agent 编排多个 Skill 完成。

**为什么**：每次调用 Skill 会注入其全部上下文，功能越多 token 越稀释，模型越容易抓不住重点。单一职责也让测试和复用变得容易。

**举例**：在百度内部做过一个 `baidu-elastic-debug` Skill，它只负责根据 task_id 查日志和监控数据、输出结论。不负责修复、不负责发告警、不负责建工单——这些由其他 Skill 或 Agent 自行判断。

### 2.1.1 在单一职责基础上，skill本身不负责多skill的流程编排，交给上游workflow、agnet去做

### 2.2 渐进披露的三层结构

| 层级 | 内容 | 大小 | 作用 |
|------|------|------|------|
| Metadata（description） | 触发条件 | ~100 token | 模型判断"要不要用" |
| Instructions | 操作指令 | < 5k token | 模型了解"怎么用" |
| Resources | 附件/参考文档 | 按需加载 | 查细节时才读 |

**面试可以这样讲**：

> "这个三层结构的本质是**把决策信息前置，执行细节后置**。模型决定要不要调用某个 Skill，只需要看 description 那一两句话，不需要把整份文档都读一遍。这对上下文管理非常关键。"

### 2.3 Description 是触发器，不是功能说明

这是最容易犯的错。Description 应该写**什么时候用**（触发场景），而不是**能做什么**（功能清单）。

| 类型 | 示例 |
|------|------|
| 错误写法 | "这个 Skill 可以查询知识库文档、创建文档、修改权限" |
| 正确写法 | "当用户提到'知识库URL'、'查询文档'、'创建文档'、'文档权限'时触发" |

**面试加分点**：

> "我在实际落地时发现，很多社区热门 Skill 触发不了，不是模型笨，是 description 写成了使用手册。我对几个高频 Skill 做了 description 优化后，触发准确率明显提升。"

## 三、九条实践踩坑点（挑 3-4 条重点讲）

面试不需要全讲，挑和自己经历相关的展开：

### 1. 只写团队特有逻辑，不写通用知识
模型本身会写代码、发请求，Skill 的价值在于补充模型不可能知道的业务约定。比如百度内部 task_id 的格式是 `数字-类型`（如 `123-dh_material`），这种约定不写进 Skill 模型就猜不到。

### 2. 必须加 Gotchas（踩坑清单）
每个 Skill 都应该有 Gotchas 节。真实案例：排查素材检索的 JSON 解析失败，追到上游发现是画面规划大模型输出重复爆炸导致数据被截断。如果 Gotchas 里不写"沿数据链往上追"的判断条件，Agent 会一直在素材检索这层绕圈。

### 3. 预制脚本放 scripts/，不塞进 SKILL.md
脚本可能几千 token，大模型能执行就行，加载进上下文既占长度又分散注意力。比如 `elastic-query.sh` 统一处理所有 Elastic 查询，SKILL.md 里只写调用方式。


### 4. 危险操作加 Hook 确认
删除、覆盖等不可逆操作，设计 Hook 机制——平时不加载，触发时才介入校验，要求用户明确确认。这条来自真实事故：有人用知识库管理 Skill 误删了所有文档。


### 5. 知识库里的内容在重要性跟时效性
知识库里的内容在时效性跟重要性方面，呈现一条u型的曲线，所以在知识库沉淀的时候需要注意及时剔除掉完全失效的、降低不那么重要的内容的权重，不要把无用的内容放在里面造成注意力的分散。

## 四、团队实践经验（体现工程落地能力）

### Session-Learning：把解决问题的经验沉淀回 Skill

> "多轮对话中 AI 容易'越跑越偏'。我们的做法是，每完成一个复杂排查任务，主动把这次的经验固化到 Skill 的 Gotchas 里。比如第一次排查发现 processor 接口和 Elastic 日志都要看，就写进 Gotchas：'同类型失败优先查 processor 接口，不够再查 Elastic'。下次 Agent 就能直接用上这条经验。"

### 代码优先：把团队 SOP 变成 Skill

> "比如部署流程，以前是文档里一步步写'先去 XX 系统申请权限，再登录 XX 主机执行 XX 命令'。模型每次都要重新理解，还容易漏细节。做成 deploy Skill 后，新人说一句'帮我部署'就行了。"

### 按需加载：description 精准 = 省 token + 减干扰

> "不是所有 Skill 都要在每次对话中激活。description 写得精准，AI 只在真正相关时才加载，上下文越小模型响应越快，无关 Skill 的指令也不会干扰推理。"

---

## 五、自检清单（面试可以作为总结收尾）

回答完可以用这四句话做总结：

1. **触发器要精准**——description 让模型一看就知道该不该用
2. **指令要专注**——只写团队知识，不写通用常识
3. **结构要渐进**——核心在前，细节按需加载
4. **坑要提前标**——Gotchas 是经验沉淀，省掉重复踩坑

## 六、面试追问预判

| 可能的追问 | 回答方向 |
|------------|----------|
| Skill 和 Function Calling 有什么区别？ | Function Calling 是模型调用外部函数的机制，Skill 是更上层的能力封装，包含触发条件、操作指令、参考资料、踩坑经验，是可复用可分享的知识包 |
| 怎么评估一个 Skill 写得好不好？ | 看触发准确率（该触发时触发、不该触发时不触发）、上下文占用大小、是否有 Gotchas、是否遵循渐进披露 |
| 遇到 Skill 触发不准怎么排查？ | 先看 description 是不是写成了功能说明而非触发条件，再看是否和其他 Skill 的 description 有冲突导致模型困惑 |
| 多个 Skill 之间怎么编排？ | 由 Agent 或 Workflow 负责编排，Skill 本身不关心调用顺序。保持 Skill 单一职责，组合逻辑放在调用方 |
| 上下文长度不够怎么办？ | 渐进披露的三层结构就是解法：description 控制在 100 token，Instructions 控制在 5k 以内，Resources 按需加载。同时预制脚本不放进上下文 |
