Claude Code 设计了一套六层记忆架构，层层递进：

| 层级  | 名称   | 英文标识           | 生命周期 |
| --- | ---- | -------------- | ---- |
| 第一层 | 指令记忆 | CLAUDE.md      | 跨会话  |
| 第二层 | 短期记忆 | Conversation   | 单次会话 |
| 第三层 | 工作记忆 | Task Store     | 单次会话 |
| 第四层 | 长期记忆 | Memdir         | 跨会话  |
| 第五层 | 摘要记忆 | Session Memory | 单次会话 |
| 第六层 | 休眠重塑 | Auto Dream     | 跨会话  |

这六层记忆架构解决了三个核心问题：

1. **长程对话的上下文遗忘问题**
2. **多终端和团队之间的同步问题**
3. **Token 预算控制问题**

---

## 第一层：指令记忆（CLAUDE.md）

指令记忆是一套多层级、优先级递增的静态指令加载系统——可以理解为预先写好的规矩，告诉 AI 用什么风格做事。核心载体是 CLAUDE.md 文件族，相当于 AI 的行为准则手册。

### 四层优先级（从低到高）

| 层级 | 路径 | 说明 |
|------|------|------|
| Manager | `/etc/claude-code/CLAUDE.md` | 全局策略，组织管理员设定，所有用户强制适用 |
| User | `~/.claude/CLAUDE.md` | 用户私有全局指令，横跨所有项目生效 |
| Project | 项目根目录 `CLAUDE.md` | 团队共享的项目级指令，检入版本控制 |
| Local | `CLAUDE.local.md` | 私有项目指令，不检入版本控制 |

### 加载顺序

系统从当前工作目录向根目录遍历所有文件，然后**反转顺序**，从根到 CWD 处理。这意味着离当前工作目录越近的规则文件加载越靠后，优先级越高。这样既保证了全局策略的基础约束力，又给了每个项目足够的灵活性。

### 双轨注入机制（关键架构设计）

所有记忆内容并不是通过 system prompt 一股脑注入模型的，Claude Code 将记忆注入分为两个独立通道：

- **通道 A**：注入**指令记忆**（CLAUDE.md 内容），走对话消息通道，作为对话列表的第一条 user meta message 注入
- **通道 B**：注入 Memdir 的行为规范，放进 system prompt 数组

**为什么要分两个通道？** 指令记忆是用户写的，内容多变且频繁更新；而行为规范是系统内建的，相对稳定。通道 B 的内容只需注入一次就可以缓存。如果不做区分，CLAUDE.md 的多变可能导致 KV Cache break。

> 从这一层可以看出 Claude Code 的记忆理念：**选择性、按需、分层注入**——记忆不是全部一股脑加载完的。

## 第四层：长期记忆（Memdir）

这是 Claude Code 最核心的记忆模块，基于磁盘上的 Markdown 文件构建了一个分层知识库引擎。文件默认存放在 `~/.claude/projects/<sanitized-root>/memory/` 下。

### 记忆类型分类

Claude Code 明确定义了什么应该记、什么不应该记：

**应该记的四种类型：**

| 类型 | 说明 |
|------|------|
| **User** | 用户画像：角色、目标、技能水平、工作习惯，让 AI 更个性化地协作 |
| **Feedback** | 用户对 AI 行为的纠正和确认。不仅记录做错了什么，**也记录做对了什么**——避免模型因只记录错误而变得过度保守 |
| **Project** | 不可从代码推导的项目上下文：截止日期、设计目标、团队协作约定 |
| **Reference** | 外部系统的指针 |

**不能存的内容：** 代码模式、架构分析、文件路径、Git 历史、调试方案——因为它们可以从代码本身推导出来，且具备时效性，存有过时副本可能导致严重后果。

> 这两套组合拳保证了记忆系统的**高信噪比**，避免变成一个什么都往里塞的注意力涣散的记事本。

### 两层存储结构

- **Memory.md**（索引层）：纯索引文件，每行是一个指向具体记忆文件的链接加一句话摘要，限制在 200 行以内、25KB 以内
- **具体记忆文件**（数据层）：每个文件有标准格式，包含名称、描述、类型

### 异步预加载召回机制

Memory.md 会始终加载到上下文里，但如果记忆文件有几十上百个，怎么决定加载哪些？

对话开始时，系统**异步**启动 prefetch 预加载流程（与模型响应并行执行，不阻塞主流程）：

1. 扫描记忆目录下的所有 `.md` 文件，但每个文件**只读前 30 行**提取描述信息
2. 调用 Sonnet 做一次 side query（旁路查询），让 Sonnet 判断哪些记忆与当前上下文最相关
3. Sonnet 的选择约束：最多返回 **5 篇**；不确定的不选；最近使用过的工具的相关文档优先级降低，避免工具文档污染记忆召回

**记忆新鲜度系统：** 召回的记忆都会标注"年龄"，使用自然语言描述（因为模型不擅长日期计算）。记忆超过一天，会附带警告让 AI 引用前先验证——解决"记忆存在 ≠ 记忆仍然有效"的问题。

### 自动记忆提取（Extract Memory）

每一轮对话完成后，主 Agent 不会自己写记忆（避免干扰主 Agent 的上下文），而是 **fork 一个子 Agent** 回顾所有对话内容，把值得长期保留的信息存到记忆文件里。这个过程是异步非阻塞的，用户感知不到。

**冲突避免：** 如果主 Agent 在最近的对话中直接修改了记忆文件，子 Agent 会跳过该次记忆提取，避免主 Agent 和子 Agent 的写入冲突。

**子 Agent 的两回合策略：**
- **第一轮**：并行发出所有需要读取的文件请求
- **第二轮**：并行发出所有写入请求
- 最大化并行效率

**子 Agent 的权限限定：**
- 可以读任意文件、可以 grep 搜索
- 写操作限制在 memdir 路径下
- 不能调用 MCP 或 Skill（避免用户感知不到的副作用）
- 不能触发其他 Agent（避免调用循环）

## 第五层：摘要记忆（Session Memory）

当对话越来越长、Token 快要超窗时，系统不得不触发压缩。传统做法是让 LLM 事后一次性生成摘要，但不可避免会丢失细节。

Session Memory 则完全不同：**不是等到压缩时才生成摘要，而是在对话过程中持续维护一份会话笔记。**

### Session Memory 的工作方式

Fork 一个子 Agent 持续更新 `session-memory.md` 文件，文件有固定的章节结构：

- 会话标题
- 当前工作状态
- 任务规格
- 涉及的关键文件和函数
- 工作流步骤
- 遇到的错误和修正

**触发条件：** 上下文的 Token 达到某个阈值 **且** 自上次更新以来有足够的 Token 增长——保证在有足够新内容的时候才更新，不会每轮都触发。

当压缩真正发生时，系统直接用 `session-memory.md` 作为压缩后保留的上下文，而非让 LLM 从头生成摘要。渐进式维护保留了更多细节。

### 三层压缩策略

| 层级 | 名称 | 触发条件 | 说明 |
|------|------|----------|------|
| 第一层 | **Micro-compact** | 超过 soft 阈值（触发最频繁） | 将上下文中工具调用的结果替换为特殊占位符 |
| 第二层 | **Auto-compact** | Token 接近 auto 阈值时自动触发 | 压缩对话内容 |
| 第三层 | **Context-collapse** | 需手动触发，普通用户不可用 | 与 Auto-compact 互斥，会阻塞对话 |

**防套娃机制：** Fork 子 Agent 做 compact 时会检查上下文来源——如果子 Agent 自身的上下文也满了，又触发 auto-compact，就会无限套娃。所以代码里强制 `querySource === 'compact'` 的请求直接跳过 auto-compact。

---

## 第六层：休眠重塑记忆（Auto Dream）

如果说 Extract Memory 是每轮对话记日记，那么 Auto Dream 就是定期复盘整理。

### 双重门控触发条件

- 至少距离上次整合过去 **24 小时**
- 期间至少有 **5 个不同的会话**产生了新记忆

整合是一个重量级操作，频繁触发会导致成本和延迟都很高，因此需要双重门控。

### 四阶段整合流程

| 阶段 | 名称 | 操作 |
|------|------|------|
| 1 | **Orient（定向探索）** | 子 Agent 浏览记忆目录，查看文件和 Memory.md 索引，识别重复或近似主题 |
| 2 | **Gather（信息收集）** | 查看最近的日志，检查是否有与代码库当前状态矛盾的旧记忆 |
| 3 | **Consolidate（整合）** | 将新信号覆写到已有记忆文件，被推翻的旧事实直接删除 |
| 4 | **Prune & Index（修剪与索引）** | 确保 Memory.md 在 200 行以内，每行索引不超过 150 字符 |

### 并发控制

为防止多个 Claude Code 实例同时触发 Auto Dream，系统使用锁文件机制：

- 锁文件的修改时间 = 上次整合时间
- 文件内容 = 持有者的进程 ID
- 获取锁时采用 CAS（Compare-And-Swap）机制

## 总结

| 维度 | 跨会话 | 单次会话 |
|------|--------|----------|
| 静态配置 | 指令记忆（CLAUDE.md） | — |

| 上下文压缩 | — | 摘要记忆（Session Memory） |

## 第一块：指令记忆——CLAUDE.md（1分钟）

最底层是指令记忆，核心载体就是 CLAUDE.md 文件。它本质上是一套分层优先级的静态规则系统，一共四级：最低是组织管理员设的全局策略，然后是用户级的私有指令，再然后是项目根目录下团队共享的指令，最高优先级是 `.local.md`，个人的、不提交到 Git 的私有规则。

加载顺序上有个巧妙的设计：系统先从当前目录往根目录遍历收集所有规则文件，然后**反转**，从根到当前目录的顺序加载。这样越靠近当前目录的规则加载越晚，优先级越高——既保住了全局策略的约束力，又给了项目级足够的灵活度。

这里我要强调一个关键的架构设计叫**双轨注入**。Claude Code 不是把所有记忆都塞进 System Prompt 的，它分了两个通道：通道 A 把 CLAUDE.md 的内容作为对话列表的第一条 user message 注入；通道 B 把系统内建的行为规范放进 System Prompt。为什么要这么分？因为 CLAUDE.md 是用户写的，经常变，如果放进 System Prompt，每改一次就会导致 KV Cache 失效。把多变的内容走对话通道，稳定的走 System Prompt，就能最大程度保护缓存命中率。

---

## 第二块：长期记忆——Memdir（2-3分钟）

这是整套架构里最核心的部分。它在磁盘上维护了一个 Markdown 文件组成的知识库，存在用户目录下的 memory 文件夹里。

首先是**记什么、不记什么**这个问题。Claude Code 定义了四种该记的类型：用户画像、行为反馈、项目上下文、外部引用。同时明确规定代码模式、架构分析、文件路径、Git 历史、调试方案这些**不能存**——因为它们可以从代码本身推导出来，而且有时效性，存了一份过时的副本反而有害。这两套规则组合起来保证了记忆的高信噪比。

其中 Feedback 类型有一个我觉得特别值得注意的设计：它不仅记录用户纠正 AI 的地方，**也记录用户确认 AI 做对了的地方**。为什么？因为如果只记错误，模型会变得过度保守。记录正向反馈是在告诉 AI"这样做是对的，以后继续"。

**存储上是两层结构**：一个 Memory.md 索引文件，限制在 200 行 25KB 以内，每行就是一个链接加一句话摘要；然后是具体的记忆文件。

那记忆文件几十上百个，怎么决定加载哪些？这里有一套**异步预加载机制**：对话开始时，系统异步起一个预加载流程——注意是跟模型响应并行的，不阻塞——先扫描所有记忆文件但每个只读前 30 行提取描述，然后调用 Sonnet 做一次旁路查询，让 Sonnet 判断哪些跟当前上下文最相关。约束是最多选 5 篇，不确定的不选，而且最近用过的工具的文档优先级会被降低，避免工具文档污染记忆召回。

召回的记忆还会标注"年龄"，用自然语言描述——比如"3 天前创建"——因为模型不擅长日期计算。超过一天的记忆会附带警告，让 AI 引用前先验证。这是在解决"记忆存在不等于记忆仍然有效"的问题。

然后是**记忆怎么写进去**。每轮对话结束后，主 Agent 不会自己写记忆——那会干扰它的上下文——而是 fork 一个子 Agent 出来回顾对话，提取值得长期保留的信息。这个过程是异步非阻塞的，用户感知不到。子 Agent 的 prompt 设计也很讲究，规定了一个**两回合策略**：第一轮并行发出所有读请求，第二轮并行发出所有写请求，最大化 IO 并行效率。

子 Agent 的权限也被严格限定：能读任意文件、能 grep 搜索，但写操作只限 memory 目录，不能调用 MCP 或 Skill 避免产生用户感知不到的副作用，也不能触发其他 Agent 避免调用循环。

## 第三块：摘要记忆——Session Memory（1-2分钟）

当对话越来越长、Token 快超窗的时候要做压缩。传统做法是压缩时让 LLM 生成一段摘要，但问题是事后一次性压缩不可避免地丢失细节。

Claude Code 的做法完全不同：它不是等到压缩时才生成摘要，而是**在对话过程中持续维护一份会话笔记**。具体来说，fork 一个子 Agent 持续更新一个 `session-memory.md` 文件，里面有固定的章节：会话标题、当前状态、任务规格、关键文件和函数、工作流步骤、遇到的错误和修正。触发条件是 Token 超过阈值且自上次更新以来有足够的增量，不会每轮都触发。

等到压缩真正发生的时候，系统直接拿这个文件作为压缩后保留的上下文，而不是从头让 LLM 生成摘要。因为是渐进式维护的，保留的细节要多得多。

压缩本身分三层：第一层 Micro-Compact，最频繁，就是把工具调用结果替换成占位符；第二层 Auto-Compact，Token 接近阈值时自动触发内容压缩；第三层 Context-Collapse，需要手动触发，跟第二层互斥。

这里有个防套娃的设计：fork 出来的压缩子 Agent 如果自己的上下文也满了，又触发 auto-compact，就无限递归了。所以代码里强制 `querySource === 'compact'` 的请求直接跳过 auto-compact。

---

## 第四块：休眠重塑——Auto Dream（1分钟）

如果说 Extract Memory 是每轮对话记日记，那 Auto Dream 就是**定期复盘整理**。

触发条件是双重门控：至少距离上次整合过去 24 小时，并且期间至少有 5 个不同的会话产生了新记忆。因为整合是重量级操作，不能频繁触发。

整合分四个阶段：先定向探索，看看有哪些文件、有没有重复主题；然后信息收集，检查有没有跟代码库当前状态矛盾的旧记忆；第三步是整合覆写，把新的信号写入已有文件，过时的旧事实直接删除；最后修剪索引，确保 Memory.md 在 200 行以内。

为了防止多个 Claude Code 实例同时触发 Auto Dream，系统用了**锁文件加 CAS 机制**做并发控制，跟分布式系统里的乐观锁是同一个思路。

---

## 收尾总结（15秒）

总结一下，我觉得 Claude Code 这套记忆架构最核心的设计理念是三个词：**分层注入、异步非阻塞、高信噪比**。分层注入保证不同生命周期的记忆走不同的加载路径；异步非阻塞让所有记忆操作对用户透明；高信噪比通过严格定义什么该记什么不该记来保证记忆质量。它不是一个什么都往里塞的记事本，而是一个有取舍的知识管理系统。

## 如果面试官追问

### Q："这套记忆系统跟 OpenClaw 的记忆机制有什么区别？"

最大的区别在于 Claude Code 是**六层完整架构**，从指令层到离线整合层全部覆盖，而且每一层都有明确的生命周期和触发机制。相比之下 OpenClaw 的记忆机制更偏向于（结合自己项目的实际情况作答）。另一个区别是 Claude Code 大量使用异步子 Agent 来做记忆提取和整合，主 Agent 的上下文完全不受干扰，这个设计在工程上非常干净。

### Q："你觉得这套设计有什么不足？"

我觉得有两点。第一，记忆召回依赖 Sonnet 做旁路查询，这本身有成本也有延迟，而且 Sonnet 的选择不一定总是最优的，它最多只选 5 篇，在记忆量很大的场景下可能漏掉重要信息。第二，Auto Dream 的双重门控是硬编码的——24 小时加 5 个会话——没有根据用户的使用频率做自适应调整。高频用户可能整合不够及时，低频用户可能很久都触发不了。

### Q："如果让你改进这套系统，你会怎么做？"

两个方向。一是记忆召回可以引入**向量检索**替代或辅助 Sonnet 的旁路查询，用 embedding 做语义匹配，成本更低、延迟更小，也不受 5 篇的硬限制。二是 Auto Dream 的触发条件可以做成自适应的，根据用户活跃度和记忆增长速率动态调整门控阈值，而不是一刀切的固定数字。
