## 开场（30秒）

我之前研究过 Claude Code 的源码，市面上大部分分析都是在讲工具怎么注册、消息怎么传给 API 这些流程层面的东西。但我比较关注的是三个更底层的问题：**上下文管理、KV Cache 复用、还有权限隔离**。因为这三个才是真正影响产品体验和使用成本的核心机制。

---

## 第一块：上下文管理（2-3分钟）

首先说上下文管理。我们知道大模型本身是没有记忆的，它之所以能"记得"你之前说了什么，完全靠的是每次请求时把所有历史对话重新发一遍。这个"所有历史对话"加上 System Prompt，就是所谓的"上下文"。

Claude Code 的上下文窗口是 20 万 token，大概能装 15 万汉字。听起来很多，但实际用起来消耗非常快——因为 Claude Code 会读文件、执行命令，这些工具返回的结果全都要塞进上下文里。比如它读了一个 2000 行的文件，这 2000 行就会一直占着上下文空间。

所以 Claude Code 设计了一套**多级压缩策略**来管理上下文，从轻到重分几层：

**第一层叫 Micro-Compact**，它是每次 API 调用都在静默执行的。做的事情很简单——把之前的工具返回结果清掉，替换成一个占位符 `[Old tool result content cleared]`。因为 Claude 其实已经"看过"这些内容了，不需要原文一直占着空间。如果 Claude 后面还需要，重新读一遍就是了。

这里有个精妙的设计：Micro-Compact 分两条路径。如果服务端的 KV Cache 还是热的，它会用一个叫 `cache_edits` 的 API，只在服务端删掉工具结果的缓存，本地消息一个字不改——这样就不会导致缓存失效。如果 Cache 已经过期了，那就没这个顾虑了，直接暴力改本地消息内容，简单粗暴。**两条路的目的一样，区别只是要不要保护现有缓存。**

**第二层是 Auto-Compact**，当上下文用到大概 83%——也就是 16.7 万 token 的时候触发。它会启动一个专门的压缩子 Agent，把整段对话历史浓缩成一段摘要，比如"用户让我做 TypeScript 迁移，我已经改了 10 个文件，还剩 2 个没改"。然后用这段摘要替换掉原来的对话历史，一下子能省掉大量空间。

这里有几个工程细节我觉得很值得讲：

第一个是**防递归死锁**。因为压缩子 Agent 在写摘要的时候，它自己也有上下文。如果它的上下文也满了，又去触发 auto-compact，就无限套娃了。所以代码里做了一个判断，如果请求来源是 compact，就直接跳过 auto-compact。

第二个是**熔断机制**。他们从 BigQuery 数据里发现，有些 session 会陷入死循环——上下文溢出了，compact 也救不了，但系统还在反复重试。全局加起来一天浪费 25 万次 API 调用。所以他们加了个熔断器，连续失败 3 次就停掉，不再重试。这个就是微服务里经典的断路器模式。

还有一个 83% 这个阈值，不是拍脑袋定的，是从 BigQuery 的真实使用数据里算出来的。源码注释里甚至写了查询日期，比如 `BQ 2026-03-22`。改这个数字的人，必须拿出新的数据来支撑。

另外还有个反直觉的设计：默认的 max_output_tokens 是 8000 不是 32000。因为 BQ 数据显示 99% 的回复只有不到 5000 token，设成 32000 的话服务端要预留太多槽位，影响整体吞吐量。碰到那 1% 确实需要长输出的情况，再自动升到 64000 重试一次就行。

## 第二块：KV Cache 复用（1-2分钟）

然后说 KV Cache。这个要先解释一下它是什么。

传统缓存是缓存最终结果，命中了就直接返回。但 KV Cache 不一样，它缓存的是**模型处理前缀时的中间状态**。

打个比方：每次你给 Claude 发消息，Claude 都要先"读完"所有的上下文再回答。System Prompt 加上工具描述大概有 5 到 8 万 token，每次都一样，但每次都要重新处理，很费时间也费钱。

KV Cache 做的事情就是——把"读完这个前缀之后的状态"缓存起来。下次请求时，如果前缀没变，直接恢复到"读完了"的状态，从新内容开始处理。**答案仍然是重新生成的，只是跳过了重复读前缀的过程。**

这就引出一个关键问题：**Cache Break**，就是缓存失效。

一旦 Cache Break，之前缓存的 5 到 10 万 token 全部要重新计算，费用可能瞬间翻好几倍。触发原因有很多——System Prompt 变了、工具描述变了、切换了模型、甚至开启了某个 beta 功能。

Claude Code 为此做了一个专门的诊断模块 `promptCacheBreakDetection.ts`。有两个设计我觉得很巧妙：

第一个是 **per-tool hash 追踪**。BQ 数据显示 77% 的 Cache Break 是某个工具的 schema 悄悄变了，不是工具数量变化。所以他们对每个工具单独算 hash，能精确定位到是哪个工具导致的缓存失效。

第二个是 **Sticky-On 设计**。某些 beta 功能的开关一旦在 session 里激活，就永远不关掉。为什么？因为如果开了又关，请求的 header 变了，缓存就失效了。来回切 N 次就失效 N 次。所以干脆"一旦开了就锁死"，代码里叫 latched。**这是一个用功能灵活性换缓存稳定性的 trade-off。**

## 第三块：权限隔离（1-2分钟）

最后是权限隔离。Claude Code 能执行 Shell 命令、读写文件，理论上可以删代码、改系统配置、往外发数据。所以权限管理不是锦上添花，是必须的安全底线。

这里有几个设计让我印象比较深：

第一个是 **Object.freeze 防篡改**。每次工具调用，系统会创建一个权限决策对象，创建完立刻调用 Object.freeze 冻结。防的是什么呢？假设 Claude 执行了一段含恶意代码的用户脚本，这个脚本可能尝试找到权限对象然后修改它——比如把"是否允许"的判断函数替换成永远返回 true 的。冻结之后，任何运行时篡改都直接失败。这是**纵深防御**的思路。

第二个是**路径大小写归一化**。macOS 和 Windows 的文件系统大小写不敏感，如果不统一转小写，攻击者可以用混合大小写的路径绕过文件保护。比如 `.cLauDe/Settings.locaL.json` 和 `.claude/settings.local.json` 其实是同一个文件。

第三个是**宽泛规则自动剥离**。进入 Auto 模式时，如果用户之前设过类似 `Bash(python:*)` 这种规则——意思是"所有 python 开头的命令都自动批准"——系统会自动删掉它。因为这等于允许执行任意 Python 代码，AI 安全分类器完全没用了。

第四个是**远程开关**。Anthropic 可以不发新版本，通过 Statsig 特性开关平台直接远程关闭某个组织的 bypassPermissions 功能。这是紧急情况下的止血手段。

还有一个设计是**子 Agent 的故障隔离**——子 Agent 被拒绝权限时不会中断整个对话，而是把错误返回给父 Agent 处理。子 Agent 没资格"掀桌子"。

---

## 收尾：三者怎么协调（30秒）

这三套机制不是各自独立的，它们之间有协调逻辑。比如 Auto-Compact 完成后，会通知 Cache Break 检测器"下次缓存读取量下降是正常的，别误报"——因为 BQ 数据显示 20% 的告警都是 compact 后的正常下降被误判的。

还有 Auto-Compact 和 Context Collapse 之间有互斥机制，防止两套策略同时操作上下文互相冲突。

---

## 总结一句话（10秒）

总结来说，Claude Code 底层的设计哲学就是三个词：**数据驱动决策、降级链层层兜底、可观测性优先**。每一个参数都有 BigQuery 数据支撑，每一个机制都有降级方案，出了问题都能从结构化日志里精确定位原因。

## 如果面试官追问

### Q: "你觉得这套设计有什么不足？"

我觉得有两个可以讨论的点。第一，Micro-Compact 是静默执行的，用户完全不知道自己的工具结果被清了，GitHub issue 里有人抱怨过这个问题。第二，很多高级功能比如 Cached Micro-Compact、Context Collapse 都是 ant-only 的，外部用户享受不到最优的上下文管理策略。

### Q: "如果让你设计一个类似的系统，你会怎么做？"

整体架构我会参考这个降级链的思路，但我可能会加一个用户可见的上下文使用指示器，让用户知道当前还剩多少空间、什么时候会触发压缩。另外 Micro-Compact 的清理策略可以更智能一些——比如不是按时间或数量一刀切，而是根据工具结果被后续对话引用的频率来决定保留优先级。

### Q: "KV Cache 和传统缓存有什么区别？"

传统缓存是缓存最终结果，命中了直接返回，不再计算。KV Cache 缓存的是模型处理前缀时的中间状态——具体来说是注意力层的 Key 和 Value 矩阵。命中后跳过前缀计算，但**仍然会重新生成回答**。每次的答案都是新的，只是"读前缀"这一步被跳过了。
